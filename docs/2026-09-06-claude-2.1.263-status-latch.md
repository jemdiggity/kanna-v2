# Claude 2.1.263 latches every session's runtime status

Two opposite sidebar failures were reported on 2026-09-06, on Kanna Staging
(`desktop-aa43ab36`, `0.3.0-staging.10`, port 48121):

1. Task `69764248` showed **unread** in the sidebar while it was visibly
   working for more than ten minutes.
2. Task `6a32813a` showed **busy** when it was not.

They are one defect. `crates/daemon/src/headless_terminal.rs` classified
**every** frame a Claude 2.1.263 session draws as `None` — no verdict, busy or
parked — and a `None` verdict deliberately leaves the previous status in place.
Each session therefore kept reporting whatever status it last had, forever, and
which direction that looked wrong in depended only on what it had last been.

## Evidence

Every claim below is from replayed frames, not from reading the matcher.

- **32 live session snapshots** from the reporting machine's
  `terminal-recovery/` directory, replayed through `HeadlessTerminal`. Before
  the fix, 24 of the 24 Claude sessions classified `None`; one older frame
  (`3d43f346`) classified `Idle` only because its status bar happened to fit on
  one row. The remaining 8 are Codex sessions.
- **118 frames captured from a live `claude` 2.1.263 PTY** at 171x65, driven
  with a shell-command prompt. Three are committed as fixtures under
  `crates/daemon/tests/fixtures/claude/`.
- Task detail read through the supported API at the time of the incident:
  `69764248` reported `runtimeState: "idle"` with `latestRun.status:
  "running"` and a rendered footer of `✶ Effecting… (17s · ↓ 963 tokens)`;
  `6a32813a` reported `runtimeState: "busy"` with a `succeeded` run that had
  finished at 20:55:28 and a summary ending "Parking at the manual stage."

## Cause

`claude_status_from_lines` had two positive matchers, and 2.1.263 satisfies
neither.

**Busy.** The only spinner-independent busy signal was `INTERRUPT_MARKER`
(`esc to interrupt`). 2.1.263 draws that string nowhere: its in-flight footer
is `✻ Tomfoolering… (2s · ↓ 50 tokens)` and the hint is gone. Claude also keeps
drawing its composer while a turn is in flight, so no fallback could infer work
from the composer being absent.

**Idle.** `claude_lines_have_parked_composer` required every row below the
composer to be *measured* provider chrome. 2.1.263 draws its status bar there:
`/rc` (the agent-connection row), `● high · /effort`, `new task? /clear to save
390.7k tokens`, `✔ Update installed · Restart to update`, and a login-expiry
notice. Any one of them failed the check, and `/rc` is present in almost every
real frame.

## Fix

- `claude_line_is_working_footer` makes the in-flight footer the positive busy
  signal: an animation glyph followed by the ellipsis. A finished turn rewrites
  the *same row* to `✻ Worked for 6s · done 3:17 PM` — no ellipsis, always
  ` · done ` — which is the form that persists in the transcript, so the
  ellipsis is what separates live work from history. It is ordered ahead of the
  parked-composer check because Claude draws both at once.
- `claude_lines_have_parked_composer` now reads the composer box's closing
  divider as the status-bar boundary and treats everything past it as chrome by
  construction, instead of enumerating rows Claude is free to change.
- The finished footer is a *second, independent* route to `Idle`, ordered after
  every busy and waiting match. Idle no longer rests solely on the composer
  rule, so a future change to Claude's box structure costs redundancy rather
  than idle detection outright. It cannot outrank a live turn or a permission
  prompt.
- `claude_unclassified_footer` logs one warning per session when Claude draws a
  row that opens with an animation glyph but matches neither form. This is the
  part that addresses *how the defect survived*: the failure was silent. The
  classifier matched nothing, said nothing, and every session kept its last
  status. The warning turns the next vocabulary change into a line in the daemon
  log. It is silent against every frame captured here.

The retired `claude_spinner_without_interrupt_marker_does_not_mark_busy` test
asserted that a spinner row without the interrupt marker is not busy. That
premise held only while the marker existed; under 2.1.263 it leaves Claude with
no busy signal at all. What it was really guarding — a spinner-glyph row that is
not live work — is now pinned by
`claude_done_footer_above_parked_composer_is_idle` against a captured frame.

## The display half

The classifier is why both statuses were wrong. The sidebar is why one of them
could not have been shown even had it been right.

`Sidebar.vue` styled from `activity` alone, which blends the runtime and read
dimensions into one `working | idle | unread`. A task working inside a long tool
call whose latest output nobody has read reads `unread`, exactly like a finished
one, so its working mark was not merely wrong — it was unrepresentable. That
state is reachable independently of this classifier bug: delivering input to an
already-busy session writes `unread` while the daemon's status stays `busy`,
because no status *transition* occurs to rewrite it.

`isTaskWorking`/`isTaskUnread` (`apps/desktop/src/utils/taskActivityDisplay.ts`)
read `runtime_state` and `read_state` as the two independent facts they are, and
fall back to `activity` for remote tasks, which the cloud index projects with no
dimensions of their own. The desktop snapshot now carries both columns so a
reloaded window renders correctly without waiting for the next live change.

By owner decision, **working outranks unread in the styling**: a busy task draws
italic and no bold, because mid-turn "it is working" is the more useful thing to
say and the unread output is still being written. That is a display precedence
(`showsUnreadMark`), not a write — the read dimension is untouched, so the mark
reappears the moment the task settles. That is the whole difference from the old
behaviour, where a busy transition destroyed the unread state outright and it
never came back. A task parked on a prompt is not working, so it keeps its mark.

Nothing about `activity` itself changed: its derivation, the debounce, the
event feed and every other consumer are untouched.

## The test gap that let it recur

This is the second incident of this exact class in four days: the
`idle-composer-2.1.259` fixture was captured on 2026-09-03 for a false-busy
report on task `34ab8c46`, and 2.1.263 broke the same matcher three days later.
Fixture replay cannot prevent a third, because a fixture is frozen at the
version that was captured and proves only that the matcher reads *that* frame.

The repo already holds the right instrument for a different provider:
`tests/cli-contract/tests/live/opencode-tui-status-markers.test.ts` spawns the
installed OpenCode CLI and asserts it still renders each marker the daemon keys
on. Its header records the identical bug — an idle marker pinned only against a
hand-written fixture, the CLI stopped drawing it, no test noticed, live sessions
sat at `Busy` forever (`docs/2026-08-08-opencode-live-idle-detection-e2e-gap.md`).

There is no Claude sibling. The `claude-*` live tests cover model ids, resume
rekey and transcript location, not status markers. A
`claude-tui-status-markers.test.ts` pinning the in-flight footer, the finished
footer and the composer/status-bar shape against the installed binary is the
thing that would have caught this on the day 2.1.263 landed. It is not written
here because it is a test-lane addition rather than a status-correctness fix,
and that lane is gated behind `KANNA_RUN_LIVE_AGENT_CLI_CONTRACTS=1` and does
not run in the normal gate — so it is a canary someone fires on CLI upgrade, not
a safety net. The in-process warning above is the unattended half.

## Not fixed here

A busy transition still overwrites `activity: "unread"` with `"working"`, so
the *derived* `readState` loses the unread mark at that moment even though
nobody read anything. The sidebar no longer depends on that — it reads the two
dimensions — but `readState` remains a projection of `activity` rather than its
own ledger. Giving the read dimension durable storage of its own changes
`readState` for mobile, the cloud publisher, analytics and the event feed, so it
belongs to its own task rather than to a status-correctness fix.
