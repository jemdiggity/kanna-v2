# Account-wide singleton real-relay E2E gap (2026-09-03)

Repository singleton resolution crosses two independently owned SQLite databases, persisted cloud task snapshots, two `kanna-server` processes, the authenticated desktop relay connection, and the destination daemon PTY. The server HTTP harness can instantiate two independent server states and drive the real authenticated tunneled HTTP dispatcher, which now covers durable-directory discovery, sibling lookup, cross-machine input routing, duplicate reporting, an owner that is already unreachable, the no-remote local fallback, and concurrent first signals against one atomic claim coordinator. The relay Firestore-emulator integration suite independently forces two desktops past absence discovery together and proves its transaction produces one reservation and one observed loser. Publication tests deterministically hold the creator in the claim-to-SQLite window, roll its relay publication session, publish an empty snapshot with the same creator-process fence, and prove a sibling remains excluded. They then model an actual server restart with a different process fence and prove the replacement's complete empty snapshot cleans the orphan before a later claimant acquires. Server relay coverage proves a real reconnect republishes the same nonempty process fence.

What it cannot currently express is two long-lived server relay loops connected through one relay instance and Firestore while an HTTP singleton-creation request is paused between the relay claim response and its SQLite insert. The relay integration harness has no reusable two-`kanna-server` fixture that also owns two databases, cloud publication sessions, controllable task-preparation barriers, and daemon endpoints. Consequently it cannot yet prove the deployed WebSocket command transport, Firestore ownership claim, server-process fence, and local insert in one process-spanning test, or preserve the same directory/list/invoke ordering through a real disconnect and reconnect.

Close this gap by adding a two-desktop relay fixture that authenticates two `kanna-server` relay loops under one test account, supplies independent DB, Firestore-emulator, and fake-daemon roots, and exposes connect/disconnect controls. Re-run the concurrent first-signal case and the existing four resolution scenarios through public signal endpoints, including publishing an owner, disconnecting it before the request, and verifying that no task row is created on the requester. Until then, the focused server test uses the production `DesktopRelayRequest` queue and the relay integration test uses the real Firestore transaction; existing relay tests separately prove desktop command and invoke round trips.
