# Account-wide singleton real-relay E2E gap (2026-09-03)

Repository singleton resolution crosses two independently owned SQLite databases, persisted cloud task snapshots, two `kanna-server` processes, the authenticated desktop relay connection, and the destination daemon PTY. The server HTTP harness can instantiate two independent server states and drive the real authenticated tunneled HTTP dispatcher, which now covers durable-directory discovery, sibling lookup, cross-machine input routing, duplicate reporting, an owner that is already unreachable, and the no-remote local fallback. Relay unit tests separately cover singleton snapshot validation and persisted-directory filtering.

What it cannot currently express is two long-lived server relay loops connected through one relay instance and Firestore while one desktop disconnects before a later signal. The relay integration harness scripts one server connection at a time and has no reusable two-desktop fixture that also owns two databases, cloud publication sessions, and daemon endpoints. Consequently it cannot yet prove the deployed WebSocket router and Firestore directory preserve the same directory/list/invoke ordering through a real disconnect and reconnect.

Close this gap by adding a two-desktop relay fixture that authenticates two `kanna-server` relay loops under one test account, supplies independent DB, Firestore-emulator, and fake-daemon roots, and exposes connect/disconnect controls. Re-run the same four scenarios through public signal endpoints, including publishing an owner, disconnecting it before the request, and verifying that no task row is created on the requester. Until then, the focused HTTP test uses the production `DesktopRelayRequest` queue and authenticated in-process dispatcher, while existing relay tests separately prove desktop list/invoke request round trips.
