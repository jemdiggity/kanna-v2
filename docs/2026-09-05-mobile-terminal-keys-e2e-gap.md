# Mobile terminal keys E2E verification gap

The mobile relay Appium journey now taps the native `Esc` and `Enter` controls and observes byte-specific markers in the two-instance desktop PTY. It records the PTY's Enter count before tapping `Esc`, waits for `SCRIPT_KEY:ESC`, proves no `SCRIPT_KEY:ENTER` follows during a 750 ms window, then taps `Enter` and waits for `SCRIPT_KEY:ENTER`. This covers mobile UI → relay KSP → server → daemon → PTY when the suite reaches the journey.

On 2026-09-05, `KANNA_IOS_SIMULATOR_NAME='iPhone 17 Pro' ./kd test remote-e2e --dev --mobile-relay` was attempted twice against the unmodified harness after a successful iOS 26.5 simulator build. Both attempts stopped during existing harness setup, before Appium ran the task journey: the authoritative oversized-snapshot precondition timed out with 7,356 encoded characters while expecting more than 1,000,001. A diagnostic run that bypassed only that precondition reached Appium but stopped before task detail because the cloud task row was not published within 30 seconds. The bypass was reverted.

The narrower executable coverage is green: the RootNavigator integration test taps `Esc` and `Enter` through the real controller, paired LAN transport, and KSP socket and asserts `term_input`/`term_input_boundary` frames with exact base64 bytes; mapping and disabled reasons have unit coverage; all mobile Vitest tests pass. The full E2E becomes runnable once the relay fixture again produces its required authoritative oversized snapshot and publishes its seeded cloud task row.
