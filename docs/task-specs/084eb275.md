# Submit a delivered task input, or say it was not submitted

## Goal

Owner report, 2026-08-20: "we've had a few instances where the input from
mobile is just sitting in the prompt. We made recent changes to how input works
so it could have caused a regression." A reply sent from the phone landed as
text at the agent's prompt and was never submitted — it sat there until someone
pressed Enter at that terminal — while the phone had been told it was
delivered. Intermittent, seen against staging desktop v0.3.0-staging.1.

Pin the mechanism (an intermittent repro without one is not done) and fix it.

## Root cause, as pinned

Two defects, both from the PR #1099/#1104 logical-input protocol:

1. **A latched draft.** `apps/desktop/src/composables/terminalInputProducer.ts`
   declares every non-Enter keydown a draft — arrows, Escape, Tab, Ctrl-keys —
   and `crates/daemon/src/session.rs` only ever cleared
   `raw_input_draft_active` on `RawInputKind::Submission`. A producer can
   declare a draft but never un-declare one, so a single navigation key parked
   every later logical delivery behind a line nobody was typing.
2. **`Ok` meant queued, not submitted.** `SubmitInput` answered the moment the
   message reached the queue, before any byte reached the PTY, so the park was
   invisible: the server answered 204 and (since PR #1123) recorded a delivered
   input for a message the daemon had deliberately withheld.

Reproduced against a real daemon and PTY: `SubmitInput` → `Ok`, nothing written,
then the message appears the instant an `InputBoundary` arrives.

## Scope

In:

- The daemon's logical-input acceptance and acknowledgement contract.
- The server's mapping of the new refusal, and the delivered-input record.
- Mobile's handling of that refusal, so the person who sent the message can act
  on it.
- Tool-catalog descriptions for the tools that can now return it.

Out:

- Reclassifying keys in the desktop producer. Which keys leave a draft is
  unknowable from the key alone — an arrow moves the cursor *inside* a real
  draft — so the fix asks the composer instead of guessing from the keystroke.
- The 150 ms gap between the message write and its Enter. It can fuse the two
  into one agent `read()` when the agent stalls, which is a deviation from the
  design's intent, but Claude Code 2.1.236 tokenizes byte-by-byte and submits on
  any CR regardless of chunking, so there is no demonstrated fault to fix.
- The three non-blocking observations the reviewer recorded for the record only
  (round 1): a concurrent caller told "held" for a message attestation then
  delivers; a queued message crossing a handoff answering `write_failed`; and no
  task-detail visibility for a task held behind a *declared* draft.

## Contract

- **`Ok` to `SubmitInput` means submitted.** The message and its terminating
  Enter are one delivery in two writes; the acknowledgement fires only after the
  second, and travels with the message so a release by a boundary or by
  attestation acknowledges through the same channel. A writer that dies between
  the two writes answers `write_failed`, never a retry invitation.
- **A parked message is not a delivered one.** It answers
  `logical_input_held_by_draft` → HTTP 409 `input_held_by_draft`, stays queued
  for the producer's boundary, and is not written to `task_input`.
- **A stale declared draft clears itself, on evidence that post-dates it.**
  Composer attestation clears an *active* declared draft only when every
  declared-draft write has completed at the PTY and at least one output chunk
  has been mirrored since the last one did. A frame older than the draft says
  nothing about it, and clearing on one would write the queued message behind
  the human's first typed character. The inherited-unknown path is unchanged.
- Draft isolation is otherwise untouched: a composer holding text is never
  attested, the transition stays one-way, no boundary is inferred from bytes.

## Known limits, deliberately accepted

- A message released by a later boundary is written without the server hearing,
  so it is delivered but unrecorded — a hole in the durable input record,
  documented in `docs/kanna-server-boundary.md`. Closing it needs a
  daemon-to-server signal that does not exist. The refusal therefore tells its
  caller the message is still queued rather than inviting a resend.
- Providers whose empty composer has never been captured (opencode, copilot,
  antigravity) cannot be attested, so a latched draft there is reported rather
  than cleared.
- The attested-and-delivered path has no end-to-end coverage; the remote-e2e
  scripted agent cannot render provider composer chrome. See
  `docs/2026-08-20-composer-attestation-e2e-gap.md`.

## Done when

- The pinned interleaving has a regression test at the daemon level, and the
  held-and-refused path has one on the real transports.
- `cargo test -p kanna-daemon -- --test-threads=1`;
  `cargo test -p kanna-server -p kanna-tool-catalog`;
  `pnpm --filter @kanna/mobile test`; the input-related remote-e2e specs run
  individually.

## Changes to the terms

- **Original prompt (2026-08-20).** As above.
- **Review round 1.** Four required fixes, all accepted and implemented: the
  attestation freshness interlock plus its two daemon tests and a SPEC
  amendment; `input_held_by_draft` in the three tool descriptions with a
  catalog assertion; mobile treating a held input as a per-message outcome
  rather than a connection error, carrying the reason as data; and this spec
  file, whose convention (PR #1132) landed on main after this branch forked.
  The reviewer chose "one of" for the attestation E2E; the documented-gap option
  was taken, with the reason recorded in that note.
- **Review round 2.** Two required fixes, both defects introduced by round 1's
  own diff, accepted and implemented. `TaskInputError::HeldByRawDraft` no
  longer releases a transfer-finalization phase claim: a held message is queued
  in the daemon and will be typed at the producer's next boundary, so releasing
  let a retry of the work item queue a second wrap-up or a second `/exit`.
  `InputBlocked` and `Other` still release, because nothing was queued for
  them. And an *empty* declared draft no longer increments the attestation
  interlock's enqueued count: the writer drops an empty raw input without
  completing it, so one such frame from any producer left the completed total
  permanently short and wedged attestation shut for the life of the session —
  reproducing this task's own bug, unrecoverably. Both are covered by unit
  tests at the layer that owns them (a stub-daemon finalization test asserting
  the claim is still held, and its `input_blocked` counterpart; a session test
  for the empty draft), each verified to fail before the fix. The reviewer
  ruled E2E not required for either: the first is a server-internal
  error-to-outcome mapping with no cross-process behaviour of its own, and the
  second is internal to one daemon process with frame timing the remote-e2e
  harness cannot drive, for the reasons already in
  `docs/2026-08-20-composer-attestation-e2e-gap.md`.
- No mid-task directive was delivered into the session outside these.
