# Task 058e51d5 — relay auth cache + perMessageDeflate

## Goal

Cost levers #2 and #3 from the 2026-08-20 per-user cost analysis. Owner
approved all three on 2026-08-20 ("Pull all 3 levers"); lever #1 (the byte
odometer, task `2afa6564`) landed first and this branch is based on it.

- **Lever #2** — `services/relay/src/auth.ts` re-reads
  `desktopCredentials/{desktopId}` from Firestore on *every* published message
  and every invoke. At up to 2 publishes/sec/desktop that is ~1–2M reads/mo per
  active desktop, for a document that changes only at sign-in and sign-out.
- **Lever #3** — the relay's `WebSocketServer` is created bare, so nothing is
  compressed, while the dominant traffic is base64-PTY-in-JSON terminal frames.

`docs/specs/relay-scaling.md` already treats both as landed baseline and names
this task.

## Scope

In:

- A short-TTL in-memory cache of successful `desktopCredentials` validations,
  read by the per-message revalidation path.
- `perMessageDeflate` on the relay's `WebSocketServer` with an explicitly
  bounded zlib configuration, sized against the 1 GB e2-micro.
- Tests: read-count behaviour of the cache across a TTL window, revocation
  bounded by the TTL, a real compression-negotiating WebSocket client, and a
  non-negotiating client.

Out (deliberately):

- Any change to how the byte odometer measures. It already counts application
  bytes on both sides (see Constraints); it stays where it is.
- Lowering the WebSocketServer's `maxPayload`. See "Declined / deferred".
- Distributed or cross-process credential caching, quotas, or entitlement
  gating.
- Compression support in the desktop client. `tokio-tungstenite` 0.26 does not
  implement `permessage-deflate` (verified: no such feature in
  `tungstenite-0.26.2`, only a header-parsing test fixture), so the desktop leg
  stays uncompressed. Adding it is its own task.

## Constraints

- **Conservative failure mode for the cache.** Only successful validations are
  cached; a rejection and a Firestore error are never cached. A transient
  Firestore failure must not flush a good entry, or an outage would close every
  live desktop socket.
- **The cache cannot honour a secret it never validated.** Entries are keyed by
  `desktopId` but store the validated secret's hash; a lookup re-checks the
  presented secret against it with a constant-time compare, so a cache hit
  proves the same secret that Firestore accepted.
- **Connection establishment stays authoritative.** See "Decisions taken".
- **Byte odometer stays pre-compression.** `rawDataByteLength(raw)` measures
  the payload `ws` hands the message handler — already decompressed — and
  `recordBytesSent` measures the string the relay passes to `send()` — not yet
  compressed. Both sides therefore count *application* bytes, unchanged by
  lever #3. That is the correct unit for per-user metering, and it means the
  odometer will **not** show lever #3's win; the win is on the wire, and the
  test measures it there (`net.Socket#bytesRead`).
- **Compression is negotiated, so no client may break.** A client that offers
  no `Sec-WebSocket-Extensions` header keeps working uncompressed.
- Bounded memory on a 1 GB VM; per-connection zlib cost stated below.
- Repo TypeScript conventions: no `any`, `pnpm exec tsc --noEmit` clean.

## Worst-case zlib memory (the 1 GB e2-micro)

Config: `serverMaxWindowBits: 13`, `zlibDeflateOptions.memLevel: 7`,
`concurrencyLimit: 10`, `threshold: 1024`.

zlib's own sizing formulas, per connection that actually negotiates and uses
compression in both directions:

- deflate (server→client): `(1 << (windowBits + 2)) + (1 << (memLevel + 9))`
  = `(1 << 15) + (1 << 16)` = 32 KiB + 64 KiB = **96 KiB**
- inflate (client→server): `1 << windowBits`. `client_max_window_bits` is left
  unconstrained (see "Decisions taken"), so worst case `1 << 15` = **32 KiB**
- Node stream chunk buffers: `chunkSize` 16 KiB per direction = **32 KiB**

**≈ 160 KiB per fully bidirectional compressed connection.** Contexts are
created lazily on the first compressed message in each direction, so idle and
non-negotiating connections cost nothing.

Against `docs/specs/relay-scaling.md`:

- Stage 2 (100 users ≈ 160 sockets): 160 × 160 KiB ≈ **25 MB** — inside the
  spec's "25–50 MB" allowance, and small against the ~700 MB the spec leaves
  after OS + Node + Caddy.
- Stage 3 per-shard target (≤2,500 sockets): 2,500 × 160 KiB ≈ **400 MB** —
  over an e2-micro's budget, which is why that stage shards. Unchanged by this
  task; recorded so the number is not rediscovered later.

`concurrencyLimit: 10` bounds how many zlib operations run at once, not how
many contexts exist; the per-connection figure above is the one that scales.

## Decisions taken while implementing

- **The cache is read by revalidation only; `verifyDesktopCredentials` always
  hits Firestore and *writes through* to the cache.** The task said "cache
  desktopCredentials auth revalidation", and splitting it this way is the
  conservative reading: the per-message hot path (the ~1–2M reads/mo) is
  served from cache, while establishing a *new* connection is always
  authoritative, so a revoked desktop can never open a fresh socket. Because
  the handshake populates the cache, the revalidation that immediately follows
  it (`index.ts`, desktop-secret auth) is already a hit — so the split costs no
  extra read.
- **The relay handles no `desktopCredentials`-mutating path, so there is no
  write-side invalidation hook to add.** Traced as the task asked: `auth.ts`'s
  mutators are `registerDevice` (`devices/{token}`), `registerPushDevice` and
  `unregisterPushDevice` (`users/{uid}/pushDevices/*`) — none of them feed
  `verifyDesktopCredentials`. Sign-in and sign-out write
  `desktopCredentials/{desktopId}` *directly from the desktop app*
  (`apps/desktop/src/services/desktopCloudAssociation.ts`; sign-out sets
  `revokedAt`), never through the relay. So:
  - `invalidateDesktopCredentialCache(desktopId?)` is exported for any future
    relay-side mutator, and
  - it is wired to the one place the relay *does* learn a credential went bad:
    an authoritative rejection inside `verifyDesktopCredentials` purges that
    desktop's entry immediately, so a desktop that reconnects after sign-out
    flushes the stale entry still serving its old socket.
  - **The TTL is therefore the real revocation bound**, not a backstop behind
    an invalidation hook. 60 s, named `DESKTOP_CREDENTIAL_CACHE_TTL_MS`, with
    the tradeoff written at the constant.
- **`client_max_window_bits` is left unconstrained.** `ws` aborts the handshake
  with HTTP 400 when it cannot accept an offer, and setting
  `clientMaxWindowBits` to a number makes `ws` *reject* any client that does
  not advertise that parameter. Bounding the client→server window is worth
  32 KiB and is not worth refusing connections for.
- **`serverMaxWindowBits: 13` accepts one known handshake edge.** A client that
  explicitly offers `server_max_window_bits` *below* 13 is refused with a 400.
  No client in this system does (browsers and okhttp send either nothing or
  15, and the desktop sends no extension header at all), and the alternative —
  leaving the server window at 15 — doubles the deflate window to 128 KiB per
  connection, which is the memory this lever is supposed to bound.
- **Which clients actually compress, verified honestly.** Compression is a
  negotiation, so every path keeps working either way, but the expected win is
  not uniform:
  - desktop (`crates/kanna-server/src/relay.rs`, `tokio-tungstenite` 0.26):
    **does not negotiate** — no `permessage-deflate` implementation in the
    crate. Stays uncompressed.
  - tunnel endpoints: same client library on the desktop side, the mobile
    WebSocket on the phone side; same negotiation, no separate path.
  - mobile (`apps/mobile`, React Native 0.86 platform `WebSocket`): **not
    verified from this worktree.** RN's Android WebSocket is okhttp-backed and
    requests `permessage-deflate`; RN's iOS WebSocket does not. Confirming this
    needs a device run, not a unit test.

  So the realistic near-term win is the relay→phone egress leg on Android
  only — which is the expensive direction (GCP bills egress), but is *not* the
  "3–5x across the board" the task's framing assumed. Recorded here so the
  post-lever cost estimate is not read as proven.

- **The TTL got an env override,
  `KANNA_RELAY_DESKTOP_CREDENTIAL_CACHE_TTL_MS`** (`0` disables the cache),
  following the existing `KANNA_RELAY_BYTE_ROLLUP_INTERVAL_MS` pattern. It
  exists because the integration suite has to *observe* the revocation bound
  rather than wait a production minute for it, and it doubles as the operator
  escape hatch if revocation ever needs to be immediate. Documented in
  `docs/relay-vm-operations.md`; the deploy does not set it.

## Measured, not assumed

Server→client wire bytes for 20 × ~350 KiB base64-PTY-in-JSON frames on one
connection, `net.Socket#bytesRead` on a real `ws` client:

| workload | application bytes | wire bytes | ratio |
|---|---|---|---|
| repeated redraw line | 6,992,320 | 32,604 | **214x** |
| varied build/test log | 6,992,400 | 309,105 | **22.6x** |
| non-negotiating client | 6,992,320 | 6,992,520 | 1.0x |

Far above the task's 3–5x guess, mostly because the payload is base64 inside
JSON — deflate is undoing a 33% encoding overhead before it compresses the text
at all. Treat these as an upper bound on a *single* stream with context
takeover, not as a fleet-wide cost multiplier: the win only lands on legs whose
client negotiates, which today excludes the desktop entirely (see above).

## Three existing tests changed, and why

All three are in `services/relay/test/integration.test.ts`, and all three were
green before this branch. They are called out here because changing a passing
test to accommodate a change is exactly the move a reviewer should be
suspicious of.

1. **The two revocation tests now wait out the credential cache** before
   asserting the rejection. This is the task's intended semantics — revocation
   on an already-open socket is now bounded by the TTL, not immediate — and the
   assertions themselves (rejection message, 4005 close, no invoke routed to
   the sibling) are unchanged. The suite spawns the relay with a 250 ms TTL so
   the wait is real but short.
2. **`tunnel_ready` arrival order is asserted as a set, not a sequence.** The
   test asserted the desktop tunnel socket receives its `tunnel_ready` before
   the client socket receives its own. Those are two independent TCP
   connections, and `attachDesktopTunnel` wires the peer map *before* sending
   either frame, so nothing depends on the order; it held only as an artifact
   of how the two sockets happened to flush. Enabling compression changes the
   upgrade response and perturbs it — measured 4 failures in 6 runs after the
   change, 0 in 4 before. The guarantee that matters (per-socket, `ready`
   precedes any spliced payload) is untouched and still covered.
3. **The companion chunk fixture is now incompressible** (`randomBytes(...)`
   base64 instead of `"x".repeat(...)`). This one is a genuine behavioural
   finding, not a test fix: the tunnel watermarks measure `bufferedAmount`,
   which counts the bytes *actually held* — compressed, once a frame is on the
   socket. 69 MiB of `"x"` now compresses to a few KiB and never reaches the
   32 MiB pause mark, so the test silently stopped exercising the cap it exists
   to bound. The memory guarantee is unchanged and arguably tightened (the
   relay now holds less RAM for the same application throughput), but highly
   compressible traffic travels much further before a source is paused. Real
   companion payloads are images and fonts, so incompressible data is also the
   more faithful worst case. Noted in the ops runbook.

## Declined / deferred

- **`maxPayload` is left at the `ws` default (100 MiB), deliberately.**
  Enabling compression creates a decompression-amplification vector that did
  not exist before: `ws` bounds the *decompressed* size at `maxPayload`, so
  ~100 KiB of compressed upload can force a 100 MiB allocation on a 1 GB VM,
  pre-auth (extension negotiation happens during the HTTP upgrade, before the
  auth handshake). Bounding it is the obvious fix, but the largest legitimate
  frame could not be established with confidence from this worktree: task
  snapshots cap at 512 KiB, task-transfer chunks at 64 KiB and ksp companion
  chunks at 96 KiB, yet `MAX_COMPANION_MATERIALIZED_BYTES` is ~17 MiB and it
  could not be proven that every producer of it chunks. Guessing a ceiling
  would risk closing live connections on a legitimate frame, which is worse
  than the DoS it prevents. **Follow-up:** establish the true maximum frame
  size and set `maxPayload` from it. Flagged to the owner in the run summary.

## Done when

- A burst of publishes on one desktop socket costs exactly one Firestore
  credential read per TTL window, proven by a test that counts reads.
- A revoked credential stops being honoured within the TTL bound, and
  immediately on explicit invalidation — both tested.
- Rejections and Firestore errors are never cached — tested.
- A real WebSocket client that negotiates compression receives a large
  repetitive terminal-frame payload intact, with measured wire bytes far below
  the payload size; a non-negotiating client receives the same payload intact
  uncompressed. Both tested against the relay's real router splice.
- `pnpm --filter kanna-relay test` passes and `pnpm exec tsc --noEmit` is clean.
- The ops runbook documents the compression bounds, the byte odometer's
  pre-compression position, and the cache TTL override.
