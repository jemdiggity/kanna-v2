# Task da8391f0: bound terminal attach replay

## Goal

Fix the staging regression where attaching or reconnecting a mobile client to a long-running task terminal sequentially replays a large historical stream instead of becoming interactive from a bounded current-state snapshot.

## Scope and constraints

- Trace the daemon session buffer through the `kanna-server` KSP stream and mobile client, including the app-state grace behavior introduced by `77ee2f18c`.
- Measure the large-buffer attach payload and identify whether the regression is server-side, client-side, or both.
- Preserve the grace-period contract: a connection that survives a brief background interval must not reconnect or replay terminal data.
- A fresh attach or reconnect must be O(current screen + hard-capped scrollback). A cursor older than retained bounded state must fall back to a fresh bounded snapshot, never unbounded history replay.
- Add cross-boundary coverage that produces a large session buffer, asserts bounded attach delivery, and asserts a within-grace foreground delivers approximately no terminal payload.
- Do not change unrelated terminal behavior or remove the grace period.

## Done when

The cause is documented in the implementation handoff, attach payloads are hard-bounded under a large retained history, within-grace foregrounding remains replay-free, relevant tests and checks pass, and measured before/after payload sizes are available for the PR description.

## Investigation result and implementation decision

The KSP terminal path already uses an atomic daemon snapshot followed by live output; it is not an event journal addressed by a client cursor. Capability clients receive a server-windowed snapshot (400 scrollback lines, 256 KiB ceiling above the irreducible visible-screen floor), and reconnect offsets are accepted only inside a 512 KiB live-output ring; a stale offset falls back to that bounded snapshot. The regression introduced by the 2026-08-22 grace change was client-side: mobile queued every terminal output frame while hidden (up to 1,000,000 base64 characters) and synchronously published the queue to xterm on foreground, making historical timer frames visibly play at accelerated speed even though no reconnect occurred.

Keep the terminal subscription and its retained WebView current during the short grace instead of creating a second historical queue. A within-grace foreground therefore has no attach and no queued terminal payload to render. Grace expiry still closes the attachment and follows the existing bounded snapshot/resume reconnect path.

## Reproduction measurement

The real LAN E2E scripted agent produced 10,050 history rows. Its pre-attach collected terminal stream was 824,258 decoded bytes; a fresh capability attach delivered a 34,069-byte decoded snapshot (24 visible rows plus the bounded recent window), a 95.9% reduction. The same real-session test then simulated background → active inside the grace and observed no new snapshot (`outputEpoch` unchanged), so the foreground attach payload was 0 bytes. Before this change the mobile-only foreground queue could contain up to 1,000,000 base64 characters and published every queued frame to xterm sequentially; after this change that queue does not exist.
