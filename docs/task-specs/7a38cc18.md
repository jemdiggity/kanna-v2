# Task 7a38cc18 — relay `maxPayload` and pre-auth abuse mitigations

## Goal

Close the decompression-amplification vector that task `058e51d5` opened and
deliberately deferred. That task enabled `perMessageDeflate` on the relay's
`WebSocketServer` while leaving `maxPayload` at ws's 100 MiB default, so ~100 KiB
of compressed upload can force a ~100 MiB decompressed allocation on the 1 GB
e2-micro — **pre-auth**, because extension negotiation happens during the HTTP
upgrade, before the 10 s auth handshake. The absolute ceiling predates
compression; the attacker's cost dropped ~1000x. `services/relay/src/index.ts`
also has no per-IP bound of any kind, so nothing stops one host multiplying it.

`058e51d5`'s "Declined / deferred" section names this task and states the
blocker: the true maximum legitimate frame could not be established from that
worktree, and guessing risks closing live connections on a legitimate frame.
Establishing it is step 1 here.

## Scope

In:

- An inventory of every producer that sends a frame **into** the relay
  WebSocket, with file:line citations and the bound each one enforces (below).
- `maxPayload` set from that inventory, as a named constant carrying the
  derivation, with an operator override.
- Cheap pre-auth abuse mitigations that do not change legitimate behaviour: a
  per-IP cap on *unauthenticated* concurrent connections and a per-IP upgrade
  rate bound.
- Tests: the largest legitimate frame of each class still traverses the relay
  intact; an over-limit frame closes only its own connection with the expected
  ws error; the per-IP bounds are enforced while ordinary multi-desktop usage
  is unaffected.

Out (deliberately):

- Changing any producer's own bound. Two frame classes are producer-unbounded
  (see "The two unbounded classes"); fixing that is a change to `kanna-server`
  and the daemon, not to the relay, and it is its own task.
- A separate `WebSocketServer`/path for the task-transfer tunnel. Considered
  and declined — see "Decisions taken".
- Any deploy. This rides the next staging relay deploy.

## Constraints

- **No new dependencies.** Both mitigations are a `Map` and a counter.
- The relay always runs behind Caddy (`services/relay/deploy/Caddyfile`,
  `docker-compose.yml`), so `req.socket.remoteAddress` is Caddy's address on the
  Docker bridge and is **identical for every connection**. A per-IP cap keyed on
  it would cap the entire fleet. See "Decisions taken".
- Repo TypeScript conventions: no `any`, `pnpm exec tsc --noEmit` clean.

### KSP tunnel — phone → relay (`ClientFrame`)

`term_input`, `attach`, `detach` are keystroke- and id-sized. `request` carries
the same 8 MiB task-input body as the `invoke` path above
(`crates/kanna-server/src/ksp.rs:2847`).

### task-transfer tunnel — both legs

**64 KiB per frame.** Both ends of the tunnel splice a TCP socket into the
WebSocket with a 64 KiB read buffer and send each read as one binary frame:

- desktop side: `crates/kanna-server/src/task_transfer_tunnel.rs:80`, sent at `:90`
- initiating side: `crates/kanna-server/src/cloud_transfer_proxy.rs:569`, sent at `:586` (pre-setup path uses 8 KiB, `:398`, bounded by `MAX_PRE_SETUP_LOCAL_BYTES` 64 KiB at `:29`)

The review asked whether the transfer sidecar's 8 MiB stdio frames
(`crates/kanna-server/src/transfer_sidecar.rs:29`) and 40 MiB companion IPC
frames (`:42`) traverse the relay. **They do not.** Both are local IPC between
`kanna-server` and the sidecar process — a stdout line reader and a
length-prefixed local socket — and everything that reaches the relay has already
been re-chunked by the 64 KiB TCP read above. The same is true of the 64 MiB
`CreateTaskRecoverySnapshot.serialized` ceiling
(`crates/kanna-server/src/mobile_api.rs:323`): it travels inside the
task-transfer stream, never as one WebSocket frame.

### The two unbounded classes

`term_snapshot` and `agent_snapshot` have **no producer-side size bound**:

- The agent journal is a plain `Vec<SeqAgentEvent>` with no cap
  (`crates/daemon/src/agent.rs:311`), and an attach replays all of it from
  `from_seq` (`crates/daemon/src/agent.rs:649`, `agent_runtime/commands.rs:412`);
  the shared stream client attaches at `from_seq: 0`
  (`packages/stream-client/src/index.ts:316`). Individual events are capped at
  64 KiB, the count is not.
- The terminal snapshot is the Ghostty serialization of a 10,000-row scrollback
  (`crates/daemon/src/session.rs:1549`, `crates/daemon/src/connection.rs:573`),
  base64-encoded into the frame (`crates/kanna-server/src/ksp.rs:3673`).

Measured, not assumed (probe run against `HeadlessTerminal` in this worktree,
11,000 lines written to fill the retained window):

| content | cols×rows | serialized VT | base64 in the frame |
|---|---|---|---|
| plain ASCII (full 10,000-row scrollback) | 120×42 | 1.28 MiB | 1.71 MiB |
| per-cell 24-bit fg+bg | 120×42 | 41.88 MiB | **55.84 MiB** |
| per-cell 24-bit fg+bg | 240×60 | 86.11 MiB | **114.81 MiB** |

The plain row is the honest everyday ceiling, and it agrees with the field:
snapshots observed on four real sessions were 225 KB, 258 KB, 361 KB and 977 KB
(`docs/2026-08-15-long-lived-codex-terminal-fidelity-diagnosis.md:45`, `:92`).
The styled rows are what a terminal that paints per-cell truecolor — an
image-to-ANSI renderer, a gradient TUI — can leave in 10,000 rows of scrollback.

**This changes the decision the review deferred.** The 240×60 measurement is
already over ws's *current* 100 MiB default, so the status quo is not a safe
ceiling either — it is an unmeasured one. There is no `maxPayload` that cannot
clip a legitimate `term_snapshot`, because the producer has no bound to clip
against. The choice is therefore not "safe cap vs. risky cap" but "which
imperfect cap", and the answer is: the smallest value that clears every
*enforced* class with margin, made observable and reversible.

## The value

`RELAY_MAX_PAYLOAD_BYTES = 16 MiB` (`services/relay/src/webSocketLimits.ts`),
overridable with `KANNA_RELAY_MAX_PAYLOAD_BYTES`.

- 2× the largest enforced legitimate frame (the 8 MiB task-input body).
- ~10× the realistic unchunked companion snapshot, and above its worst case even
  if every byte of the 1536 KiB prepared HTML escaped to `\u00XX`.
- ~9× a *full* plain 10,000-row scrollback snapshot, and ~17× the largest
  field-observed one.
- 6.25× below the ws default, which is what the amplification ceiling actually
  costs: ws's `zlibLimiter` is a **process-wide singleton** with
  `concurrencyLimit` jobs (`services/relay/node_modules/ws/lib/permessage-deflate.js:24`,
  `:65`), and `inflateOnData` aborts the moment the accumulated decompressed
  length passes `maxPayload` (`:486`). So peak concurrent decompression memory is
  `concurrencyLimit × maxPayload` — 10 × 100 MiB = 1 GB today, 10 × 16 MiB =
  160 MiB after. `haveLength` (`lib/receiver.js:418`) bounds the *compressed*
  bytes of one message by the same number, so a fragmented message cannot
  sidestep it.

## Decisions taken while implementing

- **The `WebSocketServer` moved to `noServer: true`.** Admission has to run
  before `ws` allocates anything for the connection, and `ws` in `server` mode
  installs the `upgrade` listener itself with no hook that runs first;
  `verifyClient` is deprecated and runs after the socket is already ws's. The
  relay's own `server.on("upgrade")` (`webSocketLimits.ts`,
  `attachUpgradeAdmission`) now owns it. `handleUpgrade` invokes its callback
  synchronously on success and destroys the socket itself on a malformed
  upgrade, so the slot is released in a `finally` when no `connection` fired.

- **A per-path `WebSocketServer` for the task-transfer tunnel was considered and
  declined.** `maxPayload` is per-`WebSocketServer`, so splitting the tunnel out
  would let it carry its own limit — but every client dials the *same* URL
  (`crates/kanna-server/src/relay_client.rs:220`, `:237`;
  `apps/mobile/src/lib/transports/relayClient.ts:113`) and the socket's class is
  only knowable from its first frame, after the upgrade. Splitting would need a
  path or header change on the Rust desktop *and* the mobile client, with
  version skew, and it would not help the pre-auth attack anyway: an attacker
  simply dials the generous path. It also would not have bought anything —
  task-transfer turns out to be the *smallest* class at 64 KiB, not the largest.

- **The per-IP cap counts *unauthenticated* connections, not all of them.** A
  flat per-IP connection cap is the wrong shape here: mobile carriers put
  thousands of phones behind one CGNAT address, so a cap low enough to matter
  would refuse real users, and one high enough not to would not bound anything.
  The pre-auth population is the only one that can spend `maxPayload` without
  proving who it is, the slot is released on the auth frame — one Firestore
  round trip for a real client, the full 10 s auth timeout for an abusive one —
  and an attacker cannot dodge it, because the inflate happens while the socket
  is open and unauthenticated. Ordinary multi-desktop usage is unaffected
  because the slot is released on auth — which is a property of the wiring in
  `index.ts`, not of the admission table, so it is pinned by a test against the
  **spawned relay** rather than by construction (see "Coverage, precisely").

- **The upgrade-rate bound is a churn bound and is deliberately loose (600/min).**
  Reconnecting faster does not raise the memory ceiling — the concurrency cap
  above does that — so all it buys is protection against free handshake churn.
  Set against refusing a genuine reconnect storm behind one NAT, loose is
  correct.

- **The client address comes from `X-Forwarded-For`, last hop, and only from a
  private peer.** Caddy reverse-proxies to `relay:8080`
  (`services/relay/deploy/Caddyfile`) and `docker-compose.yml` publishes only
  Caddy's ports, so `req.socket.remoteAddress` is Caddy's bridge address and is
  identical for every connection in the fleet — keying on it would cap all users
  together, which would have been worse than having no cap. Caddy *appends* the
  address it observed, so the last entry is the trustworthy one and anything a
  client forges lands earlier. Reading the header only from a private peer means
  a caller that somehow reaches the relay directly cannot choose its own bucket.
  A second proxy hop in front of Caddy would require moving that index; the
  tests pin the current assumption.

- **All three bounds got environment overrides**
  (`KANNA_RELAY_MAX_PAYLOAD_BYTES`,
  `KANNA_RELAY_MAX_UNAUTHENTICATED_CONNECTIONS_PER_IP`,
  `KANNA_RELAY_MAX_UPGRADES_PER_IP_PER_MINUTE`), following the
  `KANNA_RELAY_DESKTOP_CREDENTIAL_CACHE_TTL_MS` precedent. Every one of them can
  produce a false positive a user experiences as "the relay will not let me
  connect" or "my terminal keeps dropping", and none is worth a redeploy to
  relax. A malformed value is ignored with a warning rather than disabling the
  bound. The deploy sets none of them.

- **Oversize closes get their own log line.** `[ws] Oversize frame from
  <address> (authenticated=…, role=…, maxPayload=…)` — with `authenticated` in
  it, because an attack does not need to authenticate, so an authenticated
  oversize frame is almost certainly a real snapshot and the operator's next move
  is different. Documented in `docs/relay-vm-operations.md`.

- **Review added the integration coverage; no production code changed.** Two
  rounds reviewed the same commit and raised the same gap: `releasePreAuthSlot()`
  in `index.ts` — the half of the per-IP bound that decides whether the cap is a
  pre-auth bound or a hard limit on *live* sockets per address — was proven by
  nothing in the shipped relay, because the `webSocketLimits` harness
  substitutes its own release-on-message. Behind Caddy that address is a real
  end user's or a carrier-NAT egress IP, so the regression would refuse
  legitimate desktops and phones. Two cases were added to the spawned-relay
  suite (see "Coverage, precisely"), run against a cap lowered through the spawn
  env, and the no-op mutation was run to confirm the first case fails without
  the release.

## Declined / deferred

- **The two unbounded producers are not fixed here.** `term_snapshot` and
  `agent_snapshot` should be bounded where they are produced — chunked like
  companion snapshots already are, or capped with an explicit truncation flag —
  and that is a change to `kanna-server` and the daemon, not to the relay. Left
  alone deliberately; recorded in the ops runbook so the symptom is diagnosable,
  and flagged in the run summary.
- **`concurrencyLimit` was not retuned.** It is the other multiplier in the
  `concurrencyLimit × maxPayload` peak, it came from `058e51d5`, and lowering it
  trades throughput for memory on a dimension this task has no measurement for.
  Recorded so the interaction is not rediscovered.

## What makes the work done

- `maxPayload` is set from a named constant whose comment carries the derivation
  above, and an operator can raise it without a redeploy.
- A per-IP cap on unauthenticated concurrent connections and a per-IP upgrade
  rate bound exist, keyed on the client address the trusted proxy reports.
- The largest legitimate frame of each class still traverses the relay intact,
  tested.
- An over-limit frame closes its own connection with ws's 1009 and leaves the
  process and every other connection alive, tested.
- **The pre-auth slot lifecycle is proven in the spawned relay process**, not
  only in the `webSocketLimits` harness — see "Coverage, precisely" below.
- `pnpm --filter kanna-relay test` passes, `./kd test all` passes, and
  `pnpm exec tsc --noEmit` is clean in `services/relay`.

### Coverage, precisely

The per-IP bound has two halves, and only one of them is a pure function.

- `test/webSocketLimits.test.ts` covers the shipped `createUpgradeAdmission`
  bookkeeping, `clientAddressForRequest` (including a forged `X-Forwarded-For`
  prefix and a public peer), and the shipped `attachUpgradeAdmission` against a
  real HTTP upgrade. Its harness *substitutes* `ws.once("message", release)` for
  the relay's real release-on-auth, so on its own it does **not** prove that
  wiring.
- The load-bearing half is `releasePreAuthSlot()` in
  `services/relay/src/index.ts`, called from both `authenticated = true`
  branches and from the socket's `close`. It spans the upgrade listener, the
  `WebSocketServer`, and the async auth handler, so it is covered in
  `test/integration.test.ts` against the **spawned relay**. That suite spawns
  the relay with `KANNA_RELAY_MAX_UNAUTHENTICATED_CONNECTIONS_PER_IP=4`, so the
  cases reach the cap in a handful of sockets and the env override itself is
  exercised on the way. 4 rather than 1 or 2 because the whole file shares one
  relay process and a few of its cases deliberately hold a socket that never
  authenticates — the auth-timeout case holds exactly one for the full 10 s
  window — so this leaves three slots of headroom. Both cases read the suite
  constant rather than a literal.
  - `cap + 3` device-token desktops, with distinct `desktop_id`s so
    `setServerConnection` never closes a predecessor and frees a slot for the
    wrong reason, all reach `auth_ok`, all stay open, and the relay logs no
    `[ws] Refused upgrade`. Verified by mutation: making `releasePreAuthSlot`
    a no-op makes this case fail with `[ws] Refused upgrade from ::1: too many
    unauthenticated connections`.

    The sibling call on the **tunnel-socket** branch is the same two lines,
    and it is *not* separately mutation-covered. Control sockets do not take
    that branch, so proving it would need more than the cap in *live tunnels* —
    that many phone sockets each spliced to its own desktop tunnel socket,
    since a tunnel consumes the requesting phone's socket — which is a fixture
    neither review's construction called for. Recorded rather than implied.
  - `cap` sockets that send no auth frame are all admitted; the surplus upgrade
    is refused with HTTP 429 and a logged refusal while every already-open
    socket stays `OPEN`. Closing one then readmits the next, which is the
    release-on-close path.
