# Show progress while a newly paired machine's tasks load

## Goal

Adding a machine by QR code (or by pairing code) leaves the phone looking
empty: the machine is trusted, but its tasks appear only much later, with
nothing on screen saying anything is happening. Make pairing load the new
machine's work immediately, and make the wait visible while it does.

## Diagnosis

`pairMachineByCode`/`pairMachineByPayload` end in `refreshDesktops({force:
true})`, which reads desktop metadata only — never repos or tasks. Task
collections are loaded by `bootstrap()`/`loadCollections()`, so after a claim
the lists refresh only when something unrelated happens to re-bootstrap: a
Bonjour `subscribe` publish (the browser already knows the service it just
claimed against, so no new event is guaranteed) or the 3s background poll,
which only runs once `connectionState === "connected"` and is never started at
all when the phone had no machine. Meanwhile `taskCollectionStatus` is
`"ready"`, so the task list renders "No tasks yet." instead of a loading state,
and the QR path of the pairing sheet shows no busy state at all (the only
spinner lives inside the "Add" button used by the code path).

## Scope

In:

- `pairMachineByCode`/`pairMachineByPayload` connect and load the newly trusted
  machine's collections instead of only refreshing desktop metadata.
- The task surfaces read as loading for that whole wait rather than as empty.
- The pairing sheet shows a busy state on both the scan and code paths.
- Unit tests for the controller and the sheet; an E2E assertion that a QR claim
  surfaces the machine's tasks with no relaunch, plus its coverage note.

Out:

- Discovery, claim, trust persistence, and the pairing protocol itself — the
  claim is not the slow part.
- The Bonjour-publish refresh path and the background poll cadence.
- Desktop-side pairing UI.
- Any redesign of the machines list or task list beyond the loading state they
  already render.

## Constraints

- No polling loops, retry timers, or duplicated refresh logic: pairing reuses
  the existing `bootstrap()` load path.
- A user must never be trapped by the progress state — the sheet stays
  dismissable while the load runs, and the task surfaces keep showing progress
  after it is dismissed.
- Mobile is JS-only here, so `runtimeVersion` stays as it is.
- Verify with `pnpm --dir apps/mobile test` and `pnpm exec tsc --noEmit`.

## Decisions

- Pairing calls the existing `bootstrap()` rather than a new pairing-specific
  load path, so there is exactly one way collections are read.
- The sheet holds its progress panel until the load finishes, so its dismissal
  means the machine is genuinely ready — but it stays dismissable, and the task
  surfaces keep showing "Loading tasks" for anyone who dismisses it early.
- When bootstrap stops early because the connection is not running, pairing
  still forces a desktop refresh: the machine that was just added has to appear
  in the Machines inventory even when its work cannot be read yet.
- The E2E journey pins the outcome (tasks arrive from the claim, no relaunch,
  inside a budget tighter than the generic screen timeout) and not the spinner,
  which is a race against harness speed; the panel is unit-tested instead.

## Acceptance

- After a successful claim, the controller marks task collections `loading` and
  runs the same bootstrap that a connected launch runs, so repos and tasks land
  without waiting for an unrelated tick.
- While the claim and load run, the pairing sheet shows an explicit progress
  panel (QR path included), and the task lists show "Loading tasks" rather than
  an empty or setup state.
- Existing pairing behavior — trust merge, device-secret retention, failure
  copy, sheet reset — is unchanged.
