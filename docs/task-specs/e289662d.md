# e289662d — A non-draft keystroke must not hold later mobile/manager input

## Goal

Stop the daemon's typed-byte draft ledger from arming on terminal bytes that
cannot put text at a provider's composer, so a phone or manager message is
delivered immediately instead of being answered `input_held_by_draft` and shown
as "queued" on mobile when no human draft exists.

## Why (owner report, 2026-09-05 ~18:05 UTC)

> "the queued input is causing problems. I got queued input banner on mobile
> app, when there was clearly no draft input in the terminal."

### Fate of the owner's 17:57 message

It was **not lost from the record and not silently dropped**: `task_input` id
152 holds its full text, and the daemon did write it to the PTY at 17:57:36.
What happened to it is two separate faults:

1. **It was held behind a draft that did not exist** (this task). The hold was
   armed by desktop keystrokes that put nothing at the composer, and released
   only when an unrelated idle-tick frame let attestation prove emptiness.
2. **Its terminating Enter did not submit it.** After the write the session
   settled `idle` with no agent turn, and the terminal frame stayed static and
   large for ~3 minutes until the owner cleared it by hand. The message text
   reached Claude's composer and stayed there. The likely cause is the
   150 ms `LOGICAL_INPUT_SUBMIT_DELAY_MS` fence between the message write and
   its `\r`: this message was 1227 bytes and the CLI took ~19 s of echo to
   drain it, so the `\r` arrived while the CLI was still consuming the burst
   and was taken as part of it rather than as a submission. The 927-byte
   re-send at 18:03 drained fast enough and submitted normally.

   **Fault 2 is out of this task's scope** and is reported for its own task —
   see "Deliberately out of scope" below. It is a different subsystem (the
   writer's submit fence), it is not what the owner reported, and fixing it
   here would widen this task into a second investigation.

## Scope — in

- `crates/daemon`: classify producer-declared draft bytes before they reach the
  typed-byte ledger. Only bytes that can put content at a composer count.
- Keep the safety property intact: a logical input is never written into a
  real, non-empty human draft.
- `apps/mobile`: make the held-input banner's wording true about how the hold
  ends.
- Document the new rule in `docs/kanna-server-boundary.md` and
  `crates/daemon/SPEC.md`.
- Tests: daemon unit tests for the classifier and the ledger, a real-PTY daemon
  E2E proving a navigation key no longer holds a following logical message,
  `kanna-server` route/snapshot tests for `queuedInputReason` across its cases,
  and a mobile banner test.

## Scope — deliberately out

- **The unsubmitted-Enter fault (fault 2 above).** Needs its own task: the
  submit fence between a logical message and its `\r` is a fixed 150 ms and is
  too short for a long message that a CLI drains slowly, and a logical message
  left parked at a composer is invisible to the typed-byte ledger, so a later
  delivery would concatenate onto it.
- No change to how *submission* is decided. Submission is still never inferred
  from PTY bytes.
- No new client surface, no new API field, no change to the `queuedInputReason`
  vocabulary (`input_held_by_draft` / `delivery_uncertain` / `sending`).
- No change to `LOGICAL_INPUT_SUBMIT_DELAY_MS`.

## The rule this task adds

The ledger's question is **"could an unsent line exist at this composer?"**, so
it counts only bytes that can *create* composer content. Bytes that move,
scroll, delete or abandon create nothing, and something that creates nothing
cannot create a draft.

- **Content** (counted, arms the hold): printable bytes, UTF-8 continuation
  bytes, TAB, CR and LF (a multiline composer's newline), anything between
  bracketed-paste markers, every C0 control not named inert below, and — this
  is the one that looks like navigation — **cursor up/down** (`ESC [ A` /
  `ESC [ B` / `ESC O A` / `ESC O B`), because in Claude Code and in every
  readline shell those recall history *into* the composer.
- **Inert** (not counted, does not declare a draft, treated exactly like an
  existing `Control` write): every other well-formed CSI (`ESC [ … final`) and
  SS3 (`ESC O x`) sequence — left/right arrows, Home/End, PageUp/PageDown,
  Delete, F-keys, SGR mouse reports, focus in/out — a bare `ESC`, an
  `ESC`+byte Alt chord, and the C0 controls that only move, delete or abandon
  (`NUL`, `Ctrl-A/B/C/D/E/F`, `BEL`, `BS`, `Ctrl-K`, `Ctrl-L`, `Ctrl-U`,
  `Ctrl-W`, `Ctrl-Z`, `FS`–`US`) plus `DEL`.
- Anything unrecognized defaults to **content**. The safe direction is to hold.

### Why not "Esc / Ctrl-C / Ctrl-U clear the ledger"

Considered and rejected. Counting them as *inert* fixes the reported bug
without asserting anything the daemon cannot prove. Making them *clearing*
would let them zero a ledger that already counted real typed content — and the
daemon has no provider-independent proof that a given CLI's Escape empties its
composer rather than dismissing a dialog or opening a transcript view. Getting
that wrong submits a delivered message into a human's half-typed line, which is
the exact harm this subsystem exists to prevent. Emptiness stays a claim about
a rendered frame: composer attestation already releases a hold the moment the
composer reads empty, and after a genuine clear it does read empty.

## Done when

- A desktop navigation/Escape/mouse keystroke no longer holds a following
  logical input; the daemon answers it `Ok` and writes it immediately.
- A real typed draft still holds it, and still releases at the producer's
  submission boundary or on an attested empty composer.
- The mobile banner's reason matches the real state and its copy is true about
  how the hold ends; the held message is still preserved and delivered later
  with no duplicate send.
- Tests above pass; both boundary documents describe the new rule.
