# Relayed owner authorization for revisions

## Goal and scope

Add a shared `kanna_request_revision` path through the tool catalog, kanna-cli,
kanna-mcp, and kanna-server that lets a manager relay a human-authorized
revision with specific attribution: who authorized it, when, and what they
authorized. Persist that attribution beside the revision verdict metadata and
make it readable afterward. Keep ordinary agent revisions subject to the
existing revision budget and exhausted/no-retry response, and preserve the
desktop's existing human revision action unchanged. Add server and shared
catalog/client-surface coverage, plus boundary E2E coverage or a dated gap note.
Do not deploy or change other human-gated actions.

Owner directive (2026-08-25, paraphrased from chat): "I'm much less excited
about the 'revise' button and its bs UI. kill it. human intervention is me
saying so not some silly ui." The implemented meaning is that human
intervention must not depend on the desktop revision button; it is the owner's
communicated decision, which a manager must be able to relay.
The existing button remains in scope only for compatibility, per the task's
explicit requirement not to change its behavior.

## Authorization and budget semantics

The relayed request will carry an explicit human-authorization record rather
than a generic bypass flag. It will reset `revision_rounds` exactly like the
desktop human action. Both routes represent the same owner capability, so
giving the relay weaker one-round semantics would make authorization depend on
which client conveyed it and could immediately park the task again without
restoring the intended agent revision budget. Agent-origin requests remain
unchanged and budgeted.

The shared request field is `human_authorization`, containing non-empty
`authorizedBy`, `authorizedAt`, and `authorizedAction`. The server stores it
beside the existing stage-run `metadata`, repeats it in the durable revision
event, and exposes the most recent attributed override as task detail's
`latestRevisionAuthorization` (including typed kanna-cli output).

Threat model: the server cannot prove that an agent actually received the
claimed authorization. As with caller-declared `kanna_send_task_input.source`,
the durable record is an audit trail, not proof. It must identify the human,
the time of authorization, and the exact authorized action closely enough for
a later reviewer to challenge a false or over-broad claim.

## Recommendation outside this task

Publish-shaped actions and uncertain close/restart decisions should eventually
use the same attributed, caller-declared authorization record where managers
need to relay an owner's decision. Each action should still keep its own policy
and validation; this task does not expose or implement those capabilities.

## Done when

Both shared tool surfaces can submit an attributed human authorization; the
server accepts it after budget exhaustion, resets the budget, records the
attribution durably in readable task history, and tests prove that ordinary
agent requests are still refused after exhaustion with the existing no-retry
guidance.

Real-E2E coverage remains blocked on the repository's missing live
`request_revision` driver; the dated gap and narrower cross-boundary coverage
are recorded in `docs/2026-08-25-relayed-revision-authorization-e2e-gap.md`.
