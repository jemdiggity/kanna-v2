# Task a2921434: mobile canonical identity at machine-local boundaries

## Goal

Make the mobile More tab load repository commands over signed-out direct LAN just as it does while signed in, without leaking canonical `git:<remote-url-hash>` or `cloud:<...>` display identities into machine-local API routes that require local ids.

## Scope and constraints

- Trace signed-in relay/cloud and signed-out LAN repo aggregation and command fetching, choose one existing architectural layer to own canonical-to-local translation, and document that decision here.
- Audit mobile task detail, logs, and files calls for the same canonical-id leak; fix reachable cases as a class and list any deliberate exclusions.
- Return a mobile-presentable error when an identity cannot be resolved instead of reducing the failure to a silent 404 / generic unavailable state.
- Add coverage for both signed-in and signed-out request paths, including the observed encoded `GET /v1/repos/git%3A<hash>/commands` shape or its prevention at the chosen boundary.
- Visually verify the affected More screen and render the new error copy in component coverage. Add cross-boundary E2E coverage or a dated gap note if the real wiring cannot be exercised here.
- `POST /v1/pairing/push-certificate` version skew is explicitly out of scope.

## Owner directive

On 2026-08-27, the owner added that commands work while cloud-signed-in and fail signed out, making anonymous direct-LAN parity a required first-class behavior (phase 4, task `6a98509d`) and requiring tests for both auth states.

## Identity decision and auth-state trace

Mobile owns canonical-to-local route translation. `repoIdentity.ts` defines `git:<remoteUrlHash>` as a machine-independent display id and says desktop-local ids are retained for routing; `cloudLanClient.ts` implements that contract with per-desktop repo-owner and task-route maps. Signed-in mode composes relay and trusted LAN through that router, so commands use the local repo id. Signed-out mode instead returned the raw trusted LAN client; `mobileController` still canonicalized the repo list for display, then sent that `git:` id to the machine-local route. The fix is to compose signed-out LAN through the same identity router with no cloud source.

This keeps `cloud:<desktop>:<repo>:<task>` translation client-owned too: that id identifies a specific owning machine and cannot be resolved safely by whichever machine-local server receives it. The server's explicit `repoRemoteUrlHash` event-feed parameter remains a deliberately separate alternate-key API rather than precedent for overloading every local-id route.

## Audit and exclusions

All mobile task-detail, terminal/log, directory, file-range, file-mention, and diff calls enter `cloudLanClient` through the same task route owner. A signed-out stale `cloud:` id is now rejected there with account-specific recovery copy and is never sent to a LAN server; ordinary local task ids continue directly to LAN. Repo command listing and execution share the repo route owner, so both translate `git:` to the selected desktop's local repo id. No server route accepts overloaded aliases.

The cloud-authenticated file download fallback remains relay-only by design, but it receives only a route validated by the same owner. The pairing push-certificate 404 is unchanged and out of scope, as directed.
