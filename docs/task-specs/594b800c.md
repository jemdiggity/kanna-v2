# Hide the mobile custom relay endpoint control

## Goal

Remove the user-visible custom relay endpoint surface from shipped mobile
builds without removing the feature's machinery. Owner decision relayed through
the task manager on 2026-09-03: "Tell Kanna TM to hide that feature for now.
We'll come back to it." The marketing claim "run your own relay" is untrue for
an App Store user, because the relay authenticates the phone's Firebase ID
token and the desktop's credential record against the *same* Firebase project;
a stock build cannot authenticate against a relay backed by an unrelated
project. Hiding the control is preferred to shipping one that cannot work.

## Scope

In scope:

- Gate the Account sheet "Relay connection" card so it is unreachable in
  staging and production builds and still reachable in dev builds.
- Make relay resolution ignore a persisted custom URL in a build where the
  control is hidden, falling back to the environment default.
- Keep dev push registration working (it only registers when a custom relay is
  set).
- Documentation: `docs/self-hosted-relay.md` says up front that the mobile
  control is hidden in shipped builds and that self-hosting requires building
  the clients against your own Firebase project; its "Point both clients at
  it" step no longer instructs a reader to use the (hidden) Account control.
  `docs/2026-09-03-mobile-custom-relay-e2e-gap.md` gets a dated note recording
  that the journey is hidden rather than pending.

Deliberately out of scope: desktop UI and `server.toml` `relay_url`, the relay
service, relay authentication or entitlement policy, the marketing site, and
any redesign of relay configuration. No native code, Expo config, or
`withKannaNativeIdentity.js` changes — this stays JS-only and
`runtimeVersion` stays `2.2.3` in `apps/mobile/src/mobileEnvironments.json`
so the change is OTA-deliverable.

## Constraints and decided behavior

- **Stored endpoints are preserved, not honored.** A device that already saved
  a custom relay URL keeps that value in AsyncStorage untouched — no migration,
  no clearing. In a build where the control is hidden, resolution ignores it
  and uses the environment default, so nobody is silently routed through an
  endpoint they cannot see or reset. Re-enabling the control restores the
  user's stored setting exactly as they left it.
- **The restore path is one switch.** `CUSTOM_RELAY_CONTROL_APP_ENVS` in
  `apps/mobile/src/relaySettings.ts` lists the `appEnv` values in which the
  control exists (currently `["dev"]`). Adding `"staging"` / `"prod"` — or
  making `isCustomRelayControlEnabled` return `true` — restores the feature;
  nothing else has to change. The gate fails closed: an unknown or missing
  `appEnv` hides the control.
- The machinery stays: `relaySettings.ts` precedence and validation, the
  sessionStore/persistence `customRelayUrl` fields, the five `accountRelay*`
  E2E ids, `services/relay`, and the existing unit tests.
- No `any`; `pnpm exec tsc --noEmit` passes.

## Done

`pnpm exec tsc --noEmit` passes, mobile unit tests pass, new coverage proves a
stored URL is ignored in a hidden build and honored in a build where the
control is shown, and the Account sheet was rendered in the iOS simulator with
the relay card absent in a staging build and present in a dev build.

### Simulator render: blocked on the host toolchain

**The required simulator render could not be produced on this machine, so the
UI change is not yet visually verified.** `./kd mobile run --simulator` booted
the iPhone 17 Pro simulator, completed Expo prebuild and CocoaPods, and then
failed in the native build:

```text
expo-modules-jsi/apple/Sources/ExpoModulesJSI-Cxx/include/RuntimeScheduler.h:61:26:
error: 'RuntimeScheduler' cannot be annotated with either
SWIFT_RETURNS_RETAINED or SWIFT_RETURNS_UNRETAINED because it is not returning
a SWIFT_SHARED_REFERENCE type
CommandError: Failed to build iOS project. "xcodebuild" exited with error code 65.
```

This is a pre-existing host-toolchain gap, not an effect of this branch (which
is JS-only): Expo SDK 57 requires Xcode 26.4 or newer per
`docs/2026-08-21-mobile-expo-native-abi-e2e-note.md`, and the installed
`/Applications/Xcode.app` reports 26.2. The identical failure is already
recorded for two other 2026-09-03 tasks in
`docs/2026-09-03-mobile-app-icon-simulator-e2e-gap.md` and
`docs/2026-09-03-mobile-dev-preview-webview-e2e-gap.md`.

**This machine is not merely missing a new-enough Xcode — it lost one it
already had.** `docs/task-specs/ac2b403e.md` records that on 2026-08-21 this
same `/Applications/Xcode.app` path reported Xcode 26.6, and that unpatched Dev
and Staging device builds were verified under it after the Xcode 26.2
compatibility patches were deliberately eliminated rather than carried. Today
that same path reports 26.2, so the application changed version in place at some
point since. The fix is therefore to restore the Xcode that was already here,
not to treat this as a new upgrade requirement — and the previously removed
source patches must stay removed (owner directive, 2026-08-21, recorded in
`ac2b403e.md`).

One hypothesis was raised and checked on 2026-09-04: that Xcode is still current
and only an iOS 26.2 *simulator runtime* made the build use a 26.2 SDK. The
evidence on this machine does not support it, so it is recorded here to save the
next reader from re-deriving it:

```text
$ xcodebuild -version
Xcode 26.2
Build version 17C52

$ /usr/libexec/PlistBuddy -c "Print :CFBundleShortVersionString" \
    /Applications/Xcode.app/Contents/version.plist
26.2

$ xcodebuild -showsdks
    iOS 26.2                  -sdk iphoneos26.2
    Simulator - iOS 26.2      -sdk iphonesimulator26.2
    Simulator - tvOS 26.2     -sdk appletvsimulator26.2
    Simulator - visionOS 26.2 -sdk xrsimulator26.2
    Simulator - watchOS 26.2  -sdk watchsimulator26.2

$ xcrun simctl list runtimes | grep -i iOS
iOS 18.4 (18.4 - 22E238)  - com.apple.CoreSimulator.SimRuntime.iOS-18-4
iOS 18.5 (18.5 - 22F77)   - com.apple.CoreSimulator.SimRuntime.iOS-18-5
iOS 26.2 (26.2 - 23C54)   - com.apple.CoreSimulator.SimRuntime.iOS-26-2
```

`xcodebuild -version` and the bundle's own `version.plist` describe the
application, not a runtime, and both read 26.2 (build 17C52). The tvOS, watchOS
and visionOS SDKs also read 26.2, and no iOS simulator runtime can affect those
— they ship inside Xcode. `mdfind` finds exactly one `com.apple.dt.Xcode`
bundle, at `/Applications/Xcode.app`, and `xcode-select -p` points at it, so no
second install is in play. Separately, the installed iOS runtime (26.2, build
23C54) is a distinct artifact from the Xcode build (17C52) that happens to carry
the same marketing number, and there is no 26.4+ runtime installed either — so
a runtime install alone would not be sufficient here even if Xcode were current.

Also note that the `iPhoneOS26.2.sdk` reference in `ac2b403e.md` describes the
*pre-upgrade* failure on that task, not its end state; that document's
conclusion is that the path "now reports Xcode 26.6".
