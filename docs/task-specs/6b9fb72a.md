# Task 6b9fb72a: reliable activity events

## Owner correction (2026-08-21)

This replaces the original sustained-idle-event design:

> "activity detection was made to show task status in the sidebar originally. only claude puts in a prompt placeholder. codex et al don't do that. if we need to debounce events, then we should debounce in the server. it's not reliable for the task manager to independently come up with its own monitoring method. it will be different for every task manager agent."

## Goal

Make `task.activity_changed` a provider-neutral, server-debounced settled-transition event so manager agents do not poll or invent provider-specific monitoring.

## Scope and constraints

- Do not add `task.idle_sustained`; retain `task.awaiting_input` unchanged.
- Debounce every activity transition in `kanna-server` for a configurable 15–30 second interval, emitting once only if the new value holds.
- Emit both directions for every provider without requiring `waitingPromptSnippet`.
- Include `activity`, `runtimeState`, and whether a settled idle latest run lacks a recorded stage completion (the parked-awaiting-advance signature), so managers need no follow-up polling.
- Append through the authoritative task-event DB path and preserve `ks1` aggregation with `machineId` attribution.

## Done when

Coverage proves sub-threshold flickers are suppressed, placeholder-free Codex transitions emit after settling, both directions emit, the parked signature is correct, and the event is visible through the aggregated feed; `cargo test -p kanna-server` and event-feed suites pass.
