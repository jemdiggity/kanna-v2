# Mobile App Store 1.0 provenance and versioning

## Goal

Determine which ref/commit produced the App Store 1.0 binary, whether its embedded runtime can receive current production OTAs, and make future production archive provenance durable and discoverable.

## Scope and constraints

- Inspect `kd` archive/publish records, local artifacts, repository/release history, App Store Connect metadata available through `kd`, and the production OTA channel without mutating production state.
- Document the independent mobile marketing-version policy and the rules for marketing version, build number, and `runtimeVersion` bumps.
- If `kd mobile archive` does not durably record ref, commit, runtime, version, and build number, add that record with focused `kd` tests and E2E coverage (or a dated gap note).
- If the store binary is proven older than runtime `2.2.2`, prepare a correctly versioned production archive from the appropriate ref, but do not upload or submit it.
- Do not publish a production OTA or change signing, certificates, entitlements, or App Store state.

## Done

The repository contains the versioning/provenance policy and tested archive-time provenance recording; the owner receives an evidence-based report of store-binary provenance, republish need, production OTA state/coherence, any signing re-authentication needed, and any unresolved question that is not durably answerable.
