# Shipping agent separation

## Goal

Make Kanna's own release/shipping agent an internal repository policy while preserving a full-fledged, user-configurable shipping-agent path for other repositories. Consult Kanna's internal architect before choosing and implementing the design.

## Scope

- Trace the bundled/repository agent-definition, task-template, API, and picker behavior that currently gives `ship` its meaning.
- Implement the architect-supported distinction between Kanna's private ship policy and the public shipping-agent capability available to users.
- Update focused tests and documentation for definition resolution and visibility/listing behavior.
- Do not perform a release, deploy, mobile publish, production operation, PR creation, or unrelated agent/workflow refactor.

## Done when

The internal Kanna shipping policy still resolves where Kanna explicitly binds it; users can create/configure their own shipping agent without inheriting Kanna-specific release policy; public listings and templates reflect that distinction; and relevant automated checks pass.

## Architecture decision

Architect consultation `c9e4656e` (2026-09-03) found the existing agent full-fledged but mis-scoped and recommended preserving the public `ship` / `custom:ship` identities. The bundled base will define a repository-agnostic authorization and completion contract; Kanna's `kd` runbook will move to repo-local `ship/EXTEND.md`, with the same separation applied to task-manager shipping guidance. An unconfigured repository must stop rather than guess a release procedure. No engine, schema, catalog-gating, or release-runtime change is included.
