# Mobile task-input queue visibility and integrity

## Goal

Diagnose the 2026-08-26 staging incident where mobile messages to task `227683ef` appeared not to send and later arrived concatenated, then make draft-held task input visible and preserve each queued message as a distinct delivery and `task_input` record.

## Scope and constraints

- Trace the mobile client, server input endpoint, daemon logical-input hold/flush behavior, staging logs, and durable input ledger; distinguish confirmed evidence from plausible explanations here.
- Surface queued/held status and the draft-hold reason to the mobile sender. Messages must not disappear silently; pending delivery must remain visible until delivered or an explicit error is shown.
- Preserve the existing protection for a human's unsent desktop terminal draft.
- Add mobile queue tests plus server/daemon boundary coverage proving held messages flush separately and are recorded as distinct `task_input` rows. Add an end-to-end test or a dated coverage-gap note where the real boundary cannot be exercised.
- Visually verify the mobile UI through the repository's `kd` workflow and save uncommitted screenshots under `docs/task-specs/08c44209-screenshots/`.
- Do not refactor unrelated terminal, relay, or task-input behavior.
- Revision round 2 (review feedback delivered 2026-08-27): bind durable queue rows, release events, and reconnect recovery to the exact daemon session incarnation. A missed release may be promoted only with evidence from the owning incarnation; replacement, exit, and crash-window `preparing` ambiguity must remain visible as `delivery_uncertain` without a false `task_input` record. Preserve FIFO promotion for proven releases and add SQLite/server-watcher/daemon lifecycle coverage for those cases.
- Revision round 3 (review feedback delivered 2026-08-28): cover the daemon's asynchronous writer path with a real-daemon/real-PTY integration test that holds two logical messages behind a desktop draft, releases them through `stream_output`, and proves three ordered, separate submissions plus one PID-bound release event per queued message.

## Done when

The incident mechanism is documented with evidence; mobile clearly shows pending draft-held messages and failures; queued messages flush one at a time with durable per-message records; relevant checks pass; and the changed mobile states have been visually inspected and documented.

For revision round 2, recovery must additionally prove that a same-incarnation missed release creates one distinct delivered row, while replacement/exit and an interrupted `preparing` reservation create no delivery record and surface uncertainty instead of remaining falsely `sending`.

## Investigation record

- Confirmed environment identity: the configured MCP connection is staging `http://127.0.0.1:48121`, environment `staging`, desktop `desktop-21b320e8-a5ad-4fae-9d87-1db14090f0a9` (checked 2026-08-26).
- Confirmed server evidence: the staging server log (`kanna-server_95225_2026-08-24_16-37-01.log`) records four mobile `POST /v1/tasks/227683ef/input` requests in the incident window returning `409 Conflict` with reason `input_held_by_draft`. Each response says the daemon accepted the message into its logical-input queue behind a human's unsent terminal line and warns the client not to resend it.
- Confirmed durable-record gap: `kanna_task_inputs` for `227683ef` ends at row 303 (`2026-08-26 04:47:12`, “I haven't received any notifications.”). The server records a `task_input` row only after an immediate daemon `Ok`; it treats `LogicalInputHeldByDraft` as an error even though the daemon has already retained the bytes, so held messages that later flush have no ledger rows.
- Confirmed mobile behavior: `TaskScreen` clears the draft synchronously after invoking `onSendInput`; `mobileController.sendTaskInput` turns `input_held_by_draft` into the shared top-level error string. It keeps no per-message pending state, does not reconcile later delivery, and therefore makes a queued message look discarded from the task composer.
- Confirmed boundary-loss mechanism: on a desktop submission boundary the daemon releases all held logical messages in FIFO order. Each message is written as text plus synthesized Enter, but the writer delays only between the text and its Enter, not after that Enter before starting the next queued message. The next message can therefore reach the CLI composer before the CLI consumes the prior submission, producing the observed concatenated blob despite the queue retaining separate byte vectors internally.
- Owner live reproduction (2026-08-27, running staging stack predating this branch): the owner left text in a desktop task terminal, sent “SGTM. Proceed.” and a second message from the physical mobile device, observed both sends remain silently held, then cleared the desktop draft and pressed Enter. Both messages released afterward, as two separate messages in this exercise. This confirms the old stack's invisible hold and release flow; the separate delivery in this instance does not remove the confirmed race above that allowed the 2026-08-26 concatenation.
- Plausible but not needed to establish the defect: the exact owner-authored text of the four held requests is not present in server logs or `task_input`, so the historical concatenated terminal blob cannot be split back into its original messages from durable evidence. The response sequence and code paths establish how it happened without guessing those boundaries.

## Delivered design

- `kanna-server` now reserves every task input in a durable FIFO before daemon submission. A draft hold returns `202 Accepted` with `status: queued`, the reason, and queue count; uncertain delivery remains durable and visibly marked rather than inviting a blind retry. Immediate delivery transactionally promotes the same row into `task_input`.
- The daemon retains the draft protection, adds the missing Enter-to-next-message processing fence, and emits one release event after each held message's synthesized Enter is written. The server consumes each event into one ordered `task_input` row and reconciles missed release events against the daemon's pending count after reconnect.
- Mobile LAN and relay transports understand the accepted-queue response without retrying. Task summaries/details expose `queuedInputCount` and `queuedInputReason`; the server publishes both fields through the cloud snapshot and relay/Firebase path as well as LAN, so the task composer shows a live held/sending/uncertain explanation until server state reports the queue cleared.
- This is a JS-only mobile change, so the native `runtimeVersion` is unchanged.

### Revision-round 2 correction

- Review identified that the first recovery design keyed durable rows only by task ID. Since stage/recovery replacement reuses that ID, a replacement session's zero pending count could falsely promote an old session's held row and clear the mobile warning. Conversely, a server interruption between inserting `preparing` and recording the daemon's held response could leave a row permanently shown as sending or let reconnect guess at delivery.
- The corrected contract binds each reservation to the live daemon session incarnation used by guarded submission. Release and reconnect evidence is accepted only for that incarnation. A `preparing` row observed during reconnect is inherently ambiguous, and a row whose owning session was replaced or exited has no proof of delivery; both become visibly `delivery_uncertain` and never synthesize a `task_input` record. An uncertain row remains a FIFO barrier because a later release edge may belong to that ambiguous slot; only held rows before any ambiguity with same-incarnation release evidence are promoted, in FIFO order.
