# 48a0da30 — Workspace forks must cut from the task's latest committed tip

## Goal

A stage transition or revision must never fork a workspace from a base that
predates a commit the task has already landed. When it does, every subsequent
reviewer sees code without the previous round's fix and re-raises the identical
finding, so the revision budget burns without converging.

## The observed defect

Task `7a38cc18` (2026-08-20/21, staging instance, repo `kanna-2`), reconstructed
from its `stage_run` rows, the Claude transcript `61fca65e-…` and the branch
reflogs:

| when (JST) | what |
|---|---|
| 00:35:39 | `in progress` commit post lands `b79ae0e2` on `task-7a38cc18` |
| 00:35:55 | review fork `task-7a38cc18-2` created **from `task-7a38cc18`** ✔ |
| 00:54 | review fails → revision **resumes** the implement run in `.kanna-worktrees/task-7a38cc18`, which moves `pipeline_item.branch` back to `task-7a38cc18` |
| 01:09:03 | round-1 commit `585bb5e2` lands on **`task-7a38cc18-2`** |
| 01:09:20 | review fork `task-7a38cc18-3` created **from `task-7a38cc18`** ✘ — `585bb5e2` dropped |
| 01:39:35 | round-2 commit `79fec020` lands on `task-7a38cc18-3` |
| 01:40:45 | review fork `task-7a38cc18-4` created **from `task-7a38cc18`** ✘ |
| 01:56:44 | round-3 commit `28abf0e2` cherry-picked onto `-4` by the agent, working around the loss |
| 02:06:17 | review fork `task-7a38cc18-5` created **from `task-7a38cc18`** ✘ |

Three rounds, three commits with identical content on three sibling branches,
three identical review findings.

The engine's fork base is `pipeline_item.branch`
(`prepare_stage_run_spawn`, `RunWorkspaceSpec::Fork`). That field records the
workspace the engine last *placed* the task in — which a resumed revision
rewinds to the resumed run's older branch — not the branch that actually holds
the newest commit. The two diverged here because the revision agent, whose PTY
cwd was `.kanna-worktrees/task-7a38cc18`, worked and committed in the reviewer's
`-2` worktree instead. The engine cannot see where an agent `cd`s, so the fix
cannot rely on run records: which branch holds the tip is a question for git.

## Scope

In:

- Resolve the task's **work tip** — the newest commit among every workspace
  branch the task is known to have used — and reconcile `pipeline_item.branch`
  (and the task's `worktree` row) onto the branch holding it before any stage
  transition, post dispatch, revision, or stage restart is prepared. Every
  workspace fork then cuts from that branch, i.e. from the latest committed tip.
- Candidate workspaces come from `pipeline_item.branch` plus the distinct
  `stage_run.cwd` values recorded for the task, each resolved to the branch
  actually checked out there.
- Coverage: an integration test driving review-fail → revision → commit →
  review-fork twice and asserting the second review fork contains the first
  revision's commit; a regression test for the resumed-revision + separate
  commit-workspace shape specifically. Both run against real git worktrees and
  the real preparation code; a dated note records why the live loop is not yet
  drivable in the real E2E tier.

Deliberately out:

- Changing where a resumed revision puts the agent, or stopping the documented
  branch rewind on resume. With the reconcile in place the rewind loses nothing:
  the resumed workspace and the abandoned fork are at the same commit at that
  moment, and any commit that later lands elsewhere is found by the tip
  resolution.
- New-task creation, task reopen, and merge-master worktrees. Those are not
  stage forks and keep their current start points.
- Teaching agents which worktree to work in, or any prompt change.
- Repairing the three sibling branches of `7a38cc18`; they are the reproduction
  and are left alone.

## Constraints

- Only committed work crosses a stage boundary — the tip is a committed tip;
  dirty state in any workspace is still left behind.
- The reconcile must be a no-op when the task's branch already holds the tip,
  including when several candidate branches sit on the same commit (the common
  case right after a fork). It must never move a task off its current branch
  onto an equal-tip sibling.
- A branch **rename inside the task's own workspace** is not a workspace move.
  The PR agent renames the branch checked out in the task's worktree and records
  the new name in `pipeline_item.pr_branch`, while `pipeline_item.branch` keeps
  naming the workspace; the fork start point already follows the rename through
  the worktree. Reconciliation must leave that alone.
- Genuinely diverged siblings (each holding work the other lacks — the state
  `7a38cc18` is in today) cannot be resolved by picking one without dropping the
  other. The engine keeps the task's current branch and logs an error naming the
  diverged tips rather than guessing or wedging the task.
- Repo conventions: `cargo fmt --all`, `cargo clippy` clean, no `unwrap()`
  outside tests.

## Done when

- After a revision whose commit lands on a workspace other than
  `pipeline_item.branch`, the next review fork's worktree contains that commit,
  and `pipeline_item.branch` names the branch that held it.
- A second revision round on top of the first still contains both rounds' work.
- Existing revision resume/fallback semantics are unchanged when no commit has
  moved.
- `cargo test -p kanna-server` and `./kd test rust` pass, plus `cargo fmt --all`
  and `cargo clippy` with no new warnings.
- Both regression tests fail on the pre-fix engine and pass after it.
