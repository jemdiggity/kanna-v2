# ec0286eb — Persist Codex sessions across stage transitions

## Goal

A Codex PTY implementer's conversation must survive an ordinary
implementation -> review stage transition, so that a later revision reopens
that conversation instead of forking a fresh one.

Codex is never given a session id: the daemon scrapes the rollout uuid off the
TUI footer and reports it on `DaemonEvent::Exit.resume_session_id`. A stage
transition is an orchestrated `Kill`, and `terminal_watcher` skipped every
replaced/killed `Exit` before it reached `persist_exit_resume_session_id`,
while `kill_session_replacing` only ever saw `DaemonEvent::Ok`. The
implementation `stage_run` therefore kept `provider_session_id` NULL,
`request_revision` logged `no stage run recorded a provider session; forking
fresh`, and every revision lost the prior conversation.

Historical evidence: closed tasks `cf1b5371` (terminal redraw) and `6a6eb58b`
(relay WebSocket bounds), each burning four distinct rollout uuids across one
implementation and three revisions.

## Scope

In:

- Carry the outgoing stage run's identity from the killer into the replacement
  bookkeeping, and record the discovered provider session id on **that exact
  run** when the killed `Exit` arrives.
- Regression coverage across the daemon-event/server/revision boundary.
- A dated E2E-gap note for the part that cannot be proven end to end.

Deliberately out:

- Any change to how the daemon discovers the uuid — that half already works and
  is already covered.
- Widening the mechanism to reruns, close, teardown, worktree shells, or stage
  posts. Those kills pass no outgoing run and keep their current semantics.
- Any release, deploy, OTA, device, notification, or production action.

## Constraints

- Must not misattribute the uuid to the newly inserted review run — the
  transition respawns the **same session id**, so "the task's latest run" names
  the replacement by the time the `Exit` is processed. Identity must be an
  explicit run id resolved by the killer, not `latest run`.
- Must not treat an intentional kill as task completion: no completion
  notification, no terminal-state finalization.
- Must not weaken replacement/ABA fencing. Entries stay consume-once; a
  delayed or repeated `Exit` must not overwrite a conversation a run already
  recorded; overlapping kills that disagree about the outgoing run attribute to
  no run at all.
- Natural exits, reruns, close, stage posts, daemon handoff, non-Codex
  providers, and failed/missing extraction keep their existing semantics.
- Repo conventions: `cargo fmt --all`, `cargo clippy` clean, no `unwrap()`
  outside tests.

## Done when

- An implementation session killed by an implementation -> review transition
  records its rollout uuid on the implementation `stage_run`.
- `request_revision` then resumes that exact conversation in that run's own
  worktree rather than forking, while an `Exit` that discovered nothing still
  forks and still records `no stage run recorded a provider session`.
- The review run never receives the implementation uuid, and neither does the
  stage's `commit` post run.
- A replaced/killed `Exit` still triggers neither completion notification nor
  terminal-state finalization.
- Focused server/daemon/revision tests plus proportionate `cargo fmt --all`,
  `cargo clippy`, and the configured test suite pass.
