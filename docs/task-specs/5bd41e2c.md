# External workspace build cleanup

## Goal and scope

Make the existing workspace teardown command, `./kd clean --all`, remove the current worktree's external per-workspace Cargo build directory without touching sibling workspaces or shared compiler caches. Keep the change in `kd`, its machine-local external-build setup contract, tests, and documentation; server, mobile, and agent definitions are out of scope.

## Confirmed mechanism

The machine-local `.kanna/setup.local.sh` makes each worktree's `.build` an absolute symlink to `/Volumes/VHS/kanna-builds/kanna-7/<worktree-directory>`. `kd clean` only offered `.build` itself to `rmSync`; removing a directory symlink does not traverse to its target, and its `existsSync` guard skipped a dangling symlink. The external directory therefore survived successful teardown. Staging daemon records confirm detached `td-task-*` teardown sessions spawned and exited with code 0 for affected workspaces (including `task-9e36a8c7-7` and `task-fa2e2ab2-{4,5,6,7}`), while their exact external directories remained. This is mechanism (a), not evidence that close teardown was bypassed or failed.

Machine-local setup computes the external path and now persists it in a gitignored workspace-local target record that survives an unavailable-volume `.build` fallback; Cargo consumes the matching `.build` symlink when external storage is available. Cleanup must read that record rather than repeat the machine-local root computation, with the symlink retained as a compatibility source for older workspaces. It may remove the target only when its normalized final component exactly equals the current worktree directory name; a mismatched target is a visible refusal. Shared kache/Cargo stores remain untouched.

## Done when

- `kd clean` removes the validated external target, local `.build` path, and durable record, including safe handling of unavailable storage and visible failures/refusals.
- Tests pin shared path resolution, exact-match refusal, and teardown of one workspace while a live sibling's external build remains.
- Cross-process E2E coverage exists or a dated gap note explains the remaining boundary.

## Follow-up decision

An orphan sweep is not part of this patch. A safe `kd clean --orphaned-builds` requires selecting and authenticating the intended Kanna server instance, enumerating every workspace generation encoded by directory names, and verifying closure without racing task creation/transition. That is a separate server-aware recovery feature; the lifecycle fix prevents new successful teardowns from leaking directories.

## Revision 1 clarification (review feedback, 2026-08-27)

Reviewer feedback identified that an unavailable recorded target was treated as absent: cleanup silently skipped it, removed the dangling `.build` link, and reported success. The contract is now explicit: an unresolved external target is a visible cleanup failure, the authoritative link is preserved for retry after the volume returns, and a workspace with no recorded `.build` remains normally idempotent. Focused tests distinguish those cases; the existing dated E2E gap remains the coverage record for the server/PTY teardown boundary.

## Revision 2 clarification (review feedback, 2026-08-27)

Reviewer feedback identified a second lifecycle hole: the documented unavailable-volume setup fallback replaced the authoritative `.build` symlink with a local directory, erasing the only record cleanup could use after remount. Setup and cleanup must retain a separate, gitignored workspace-local target record across that fallback. Cleanup reads and validates that recorded absolute target (falling back to the link only for legacy workspaces), fails visibly without deleting the record while storage is unavailable, and after remount removes only the exact departed workspace target plus its local fallback and record. A live sibling and shared caches remain untouched. The existing dated E2E gap remains accurate for the server-owned detached-teardown boundary; the setup-to-clean filesystem lifecycle is covered by the kd integration test requested in this revision.

## Revision 3 clarification (review feedback, 2026-08-27)

Reviewer feedback identified an upgrade hole for machines whose ignored primary-checkout `.kanna/setup.local.sh` predates the durable-record change: updating the tracked example does not update that installed hook. The tracked `kd env sync` setup step, which runs before the optional local hook, must automatically migrate a legacy external `.build` symlink into the durable record. Migration derives the target only from the existing link, applies the shared workspace-build safety contract, writes the record atomically, and visibly refuses a target whose final component does not exactly match the current workspace. This preserves cleanup knowledge even when the old hook subsequently replaces a dangling link with a local directory. Tests must exercise that real ordering, prove cleanup fails visibly while the target is unavailable, and after remount prove cleanup removes only the departed target while retaining a live sibling. The dated server/PTY E2E gap remains the coverage record for the detached-teardown boundary.

Task-manager directive (2026-08-27): close this defect class cheaply by documenting every path that can create, modify, replace, or destroy `.build` or `.kanna-external-build-target`, and give the next reviewer an explicit durable-record safety verdict; do not add commands or refactor paths already shown safe.

| Path | Mutation and ordering | Durable-record safety verdict |
|---|---|---|
| Tracked setup list (`.kanna/config.json`) | Runs `kd env sync`, then `rust-cache warm`, then the optional ignored hook, then `kd env sync` again. It does not directly mutate either path. | **Goes through the durable-record owner:** the pre-hook sync protects every existing legacy link; the post-hook sync captures a legacy hook's first-time link. |
| `kd env sync` (`env-sync.ts` → `workspace-build.ts`) | Reads only an existing `.build` symlink, applies cleanup's outside-workspace and exact-final-component validation, rejects an available symlink/non-directory target, and atomically publishes the record without replacing an existing record. It never computes the machine-local external root. | **Goes through the durable-record owner:** this is the tracked migration owner and a refusal fails setup visibly. |
| Current machine-local hook template (`.kanna/setup.local.sh.example`) | Establishes the external target from the operator's local configuration; it atomically creates/validates the record before creating, replacing, or repairing its `.build` link. On unavailable storage it records before replacing a dangling link with a local directory. | **Goes through the durable-record owner:** every destructive link operation requires the matching record first. |
| Pre-upgrade ignored local hook (`primary-checkout/.kanna/setup.local.sh`) | May create a first-time link without a record or replace a dangling link with a local directory. Kanna cannot rewrite this untracked deployed copy, so tracked sync runs on both sides of it. | **Cannot execute a destructive replacement before the record exists:** pre-sync migrates an existing link. A first-time link goes through the durable-record owner immediately afterward via post-sync, before later setup or teardown can erase its target knowledge. |
| `kd rust-cache warm` / `rust-cache.install` | Installs the pinned kache binary and creates only the deliberately shared repository cache store; it never creates, replaces, or removes `.build`, its symlink, or the record. | **Cannot execute before the record exists for such a mutation:** it has no mutation path to either workspace-owned location, and shared cache paths are deliberately outside cleanup scope. |
| `kd clean` (`clean.ts` → `workspace-build.ts`) | Resolves and validates the record (or a legacy link), removes the exact available external workspace directory first, then removes local `.build` and the record. An unavailable or mismatched target throws before any removal. | **Goes through the durable-record owner:** only the shared resolver authorizes destruction, and failure preserves cleanup knowledge for retry. |
| Kanna teardown (`.kanna/config.json`) | Stops the workspace dev processes, then invokes `./kd clean --all`; it has no independent filesystem cleanup implementation. | **Goes through the durable-record owner:** teardown delegates all `.build`/record destruction to `kd clean`, and command failures remain visible in the detached teardown log. |
