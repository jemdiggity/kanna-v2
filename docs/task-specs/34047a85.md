# Task 34047a85 — `kanna_notify_mobile` silently flips to `noRegisteredDevices`

## Goal

Find and close the path that removed the signed-in account's mobile push
registration on 2026-09-03 between 07:41 and 08:39 UTC (desktop-aa43ab36,
Kanna 0.3.0-staging.9), make a zero-device notify result explain itself, and
surface the missing registration to the desktop operator.

## Scope

In scope:

- Root cause with evidence from the staging relay VM log and staging Firestore.
- Relay: unregister carries a per-registration id the relay compares, so a late
  cleanup from an older app lifecycle can never delete a newer registration;
  retirement (explicit unregister, provider token rejection) leaves an
  attributable record instead of a bare delete; register/unregister/retire are
  logged (never tokens); zero-target deliveries return a `noDevicesReason`
  (`neverRegistered`, `unregistered`, `tokenRejected`, `unknown`); a `dryRun`
  publish resolves targets without sending or consuming rate-limit budget.
- Mobile: account push registration is a serialized, desired-state reconciler;
  a failed (re-)registration is retried with backoff instead of being treated
  as registered; unregister sends the registration id.
- Desktop server: every notify outcome is logged (status, counts, reason);
  `noDevicesReason` is passed through to callers; a new
  `GET /v1/mobile/notifications/registration` reports whether the signed-in
  account currently has a registered push device.
- Desktop UI: `MobileAccessPanel.vue` shows a warning row with the reason and
  the re-register instruction when no device is registered.
- Docs: `docs/kanna-server-boundary.md`, tool catalog description, task-manager
  agent guidance, dated E2E-gap note for the desktop warning.
- Tests: relay unit + integration (ordering, reasoned zero-device, dry run),
  mobile `mobilePush.test.ts` (race, retry), desktop component test, server
  unit tests.

Out of scope: production deploys or OTA; weakening invalid-token retirement;
anonymous-only (signed-out) delivery semantics beyond what the shared code
path changes; a live registration feed pushed to the UI (the first cut polls
when the preferences panel opens or the operator clicks "Check again").

## Constraints

- Staging cloud only. Record exactly what is deployed.
- Mobile changes are JS-only (OTA-deliverable, no `runtimeVersion` bump).
- Token values never appear in a response or a log line.

## Root cause (evidence)

Staging relay VM `kanna-relay-staging` container `kanna-relay-relay-1`
(image created 2026-09-01T23:42Z), UTC:

```
08:11:29.921 [ws] New connection ... Authenticated phone for user tDdBG…
08:11:30.271 [auth] Registered mobile push device mobile-mt2ryr1e-… for user tDdBG…
08:11:30.415 [auth] Registered mobile push device mobile-mt2ryr1e-… for user tDdBG…
08:11:30.976 [auth] Registered mobile push device mobile-mt2ryr1e-… for user tDdBG…
```

Staging Firestore at investigation time: `users/tDdBG…/pushDevices` is empty
(every user's is), while both `anonymousPushPairings` rows are active with
`updatedAtMs` 08:11:31.035 and 08:11:31.259 — the same burst. No relay log
line mentions a failed registration, an invalid token, or an account deletion
in the window, and no notification failure was logged at 07:32/07:41/08:39.

Three account registrations for the same device inside 700 ms is the
`startMobilePushNotifications` effect in `apps/mobile/src/App.tsx` re-running
as its dependencies settle after the app came to the foreground. Each cleanup
fired a fire-and-forget `POST /push/unregister` for the previous registration,
carrying the same FCM token the new run re-registered. The relay's unregister
guard compared tokens only, so the last cleanup to land deleted the freshly
written row. Unregister success was not logged, which is why the sequence left
no trace. The anonymous bindings survived because their coordinator is
serialized and never revokes on effect cleanup. Earlier bursts on 2026-09-02
(05:14:28/29, 18:51:10/26) happened to resolve with the register last, which is
why the loss was intermittent. This is drop path 2 from the task prompt; paths
1 (provider rejection) and 3 (sign-out / account deletion) are excluded by the
logs.

## Done when

The cause above is stated; the same-token cleanup race can no longer delete a
live registration (registration-id guard on the relay and a serialized
reconciler on the phone); a zero-device notify returns `noDevicesReason`;
the desktop logs every outcome and warns in Mobile Access; tests and
`./kd test all` pass; staging verification is recorded or its blocker named.
