# Task e4176cb8: stream live task-card snippets over KSP

## Goal and scope

Remove continuously changing agent-output snippets from the hot Firestore publication path. Add a per-desktop KSP task-summary subscription carrying task id, snippet, activity/runtime state, and revision; mobile subscribes only while the foregrounded home/tasks or activity view is visible, overlays live summaries on Firestore-backed resting snippets, and falls back silently to the resting value when KSP is unavailable. The relay remains a payload-opaque tunnel.

Firestore keeps a durable snippet only at meaningful boundaries: run finish, working-to-idle/unread activity transition, and task close. Terminal views continue using their existing terminal stream and must not keep the summary subscription open.

## Constraints and completion

- Debounce live summary frames by at least 250 ms per task and make revisions monotonic enough for mobile to reject stale frames.
- Add protocol coverage, mobile controller lifecycle coverage, and a real KSP-session integration test proving live snippets arrive without continuous-output Firestore writes.
- Verify kanna-server cargo tests, relay tests, mobile tests, TypeScript checking, Rust formatting, and clippy where practical.
- Do not add relay payload interpretation, loading indicators, or stale/offline marker UI.

## Firestore write measurement

The diff-aware publication harness confirms the cost hypothesis for one active task: 10 continuous-output snapshots whose only changing published field is `waitingPromptSnippet` produce 10 task-document writes before this change (one per snapshot). With the resting-snippet mapper, the same 10 working-output updates retain one fingerprint and produce 0 post-warm-up task writes; the subsequent working-to-idle boundary produces exactly 1 durable update. Snippet churn was therefore the dominant task-document churn in this scenario, so implementation proceeded.
