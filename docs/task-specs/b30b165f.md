# b30b165f — Composer text is not session content, and an attested-empty composer must not hold input

## Why

The Claude Code CLI paints a tab-to-accept placeholder suggestion on its idle
`❯` composer line. Kanna surfaced that line to agents as undifferentiated
session content, and the daemon's draft-hold treated it as a possible human
draft. It has confused the task manager twice (2026-08-07, and 2026-08-20 on
task `d846edb7`, where the suggestion "run it on my phone so i can see it" read
exactly like an owner directive and stalled the task a day).

Owner directive, 2026-08-20: "fetching from an agent task shouldn't return
input at the prompt"; the suggestive placeholder "is going to be confusing for
agents."

## Goal

Two coordinated fixes, both built on the daemon's own record of what was typed
into a session it spawned.

1. **Composer text stops being session content.** The derived agent-facing
   surfaces — `waitingPromptSnippet` / the activity snippet, and the
   `GET /v1/tasks/{id}/logs` tail — must not carry the composer input line as
   undifferentiated content. The composer becomes its own labeled field on task
   detail:

   ```
   composer: { text: string | null, attestation: "typed" | "not-typed" | "unknown" }
   ```

   - `typed` — the daemon watched keystrokes go into this composer since the
     last submission boundary: a real human draft.
   - `not-typed` — an attested session with zero typed bytes since the last
     boundary, so any rendered `❯`-line text is provably CLI chrome/suggestion.
   - `unknown` — a session inherited from before attestation; the daemon never
     saw what was typed.

2. **An attested-empty composer must not hold logical input.** When the daemon
   can prove zero bytes were typed, a delivered message goes to the PTY
   immediately instead of answering `409 input_held_by_draft`. The hold stays
   for `typed` and for `unknown`.

## Scope

In:

- Daemon: a typed-byte ledger per session, reset at every producer-declared
  submission boundary and by a successful composer attestation; a
  `ComposerAttestation` verdict derived from it; composer text read off the
  rendered idle frame; an edge-triggered `ComposerChanged` event and the same
  two fields on `SessionInfo`; the ledger carried across v3 handoff.
- Daemon: the waiting-prompt snippet never collects the composer line or
  anything rendered below it (chrome, hint bars, and the composer's own wrapped
  rows).
- Server: persist composer text + attestation on `pipeline_item`
  (migration `054_pipeline_item_composer`), report them as `composer` on task
  detail, and label the composer line in the task-logs tail instead of leaving
  it as content.
- Agent-facing documentation of the new field where agents actually read it:
  the `kanna_get_task` catalog description, `kanna-cli guide`'s event-supervision
  guidance, `AGENTS.md`, `docs/kanna-server-boundary.md`, and
  `crates/daemon/SPEC.md`.
- Tests as listed under Coverage.

Out, deliberately:

- **Draft save/clear/restore around an injection.** The owner raised the
  concurrency question directly. Conclusion recorded here: with one PTY there
  is one byte stream, so genuinely simultaneous human and agent input would need
  the daemon to save the human's draft, clear it, inject the message plus Enter,
  and retype the draft. Attestation knows the typed bytes, so it is
  *theoretically* possible — but paste, multiline composers, and IME
  composition all break the "retype what was typed" assumption, and a restore
  that gets it wrong corrupts a human's unsent line. The queue-until-submit
  contract from #1134 stays the safe default. No restore mechanism is built
  here.
- Rendering the new field in the desktop or mobile UI. This task exposes it on
  the API so those clients *can* render it; changing their views is its own
  task. `TaskSummary` (the list payload) is likewise unchanged — the composer
  belongs to detail.
- The cloud task snapshot. It carries `waitingPromptSnippet` and gains no
  composer field here.
- Raw PTY transcripts. `Snapshot` bytes and the terminal stream are unchanged —
  only derived surfaces are touched.

## Constraints

- The hold is only ever relaxed on positive proof. Zero typed bytes is proof;
  a quiet session or an unreadable frame is not. Anything the daemon cannot
  prove stays held, including every inherited pre-attestation session.
- Bytes are never interpreted. The ledger counts what a producer declared a
  draft; it does not decide from the byte values whether a keystroke "really"
  left text. A session that was typed into and then cleared by the human
  therefore still reads `typed` until a submission boundary or an
  empty-composer frame resolves it — the conservative side of the trade.
- The existing frame-freshness guards on `attest_empty_composer` (every
  declared write landed, at least one chunk mirrored since) are unchanged.

## What makes it done

- `GET /v1/tasks/{id}` reports `composer`, and `waitingPromptSnippet` does not
  contain composer-line text.
- The task-logs tail labels the composer line rather than presenting it as
  transcript.
- A logical input to an attested session with zero typed bytes is written to
  the PTY even while the CLI renders suggestion text on the `❯` line; a
  genuinely typed draft, and an inherited-unknown session, still hold.
- `cargo test -p kanna-daemon -p kanna-server` and `pnpm test` pass.

## Coverage

Per the repo's E2E expectation, cross-boundary behaviour gets a test:

- Daemon: the three attestation verdicts on the composer field.
- Daemon: the waiting-prompt snippet excludes the composer line and its wrapped
  rows.
- Server/API: `waitingPromptSnippet` carries no composer text while the labeled
  `composer` field does.
- Integration: logical input to an attested-empty composer with rendered
  suggestion text delivers instead of 409ing, and a genuinely typed draft still
  holds.

## Known limits, accepted

- The composer is published on the session's status tick, so `composer.text`
  can lag a fast typist by up to that interval. The same is already true of
  `waitingPromptSnippet`, and the attestation — the part a reader must not get
  wrong — moves with the ledger, not the frame.
- A session that never draws a readable composer publishes nothing, so
  `composer` stays absent on task detail for plain shells and for providers
  whose empty composer has never been measured (OpenCode, Antigravity,
  Copilot). Absent is deliberately not `unknown`.
- In the task-logs tail the composer row and everything below it is replaced by
  the single labelled line. Nothing below a composer is transcript, so this
  loses no session output, but it does drop the CLI's hint bar from the tail.

## Findings recorded during the work

- The 2026-08-20 `d846edb7` refusal is reproduced from this machine's staging
  logs. The daemon's 17:26 `HandoffReady` payload for that session records
  `raw_input_draft_active: false, raw_input_draft_state_known: true` with the
  composer already rendering `❯\u{a0}\x1b[2mcheck again in a minute` — the CLI
  placeholder, painted faint. So current `main` does deliver into an attested
  session that nobody has touched; what produced the 409 at ~20:36 was a later
  producer-declared draft write, after which the rendered suggestion made
  `composer_state` permanently `Unknown` and attestation could never clear the
  hold again. The hold's message ("a human has an unsent line") was false in
  substance, and the wedge was unrecoverable without a human pressing Enter.
  The typed-byte ledger fixes the never-typed case outright; the
  typed-then-cleared case stays held by the constraint above.
- The refusal is reproduced as a test, not just read from logs. With
  `draft_holds_input` reverted to the old `raw_input_draft_active`,
  `a_declared_draft_that_typed_nothing_delivers_through_a_rendered_suggestion`
  fails with the verbatim production message — "a human has an unsent line at
  that terminal" — against a composer nobody typed into.
- The suggestion is rendered with SGR 2 (faint) while a real draft is not.
  Reading cell attributes would let `composer_state` classify the placeholder
  positively, which would also fix the typed-then-cleared wedge. Not done here:
  it is a different mechanism from the attestation the directive names, and it
  belongs in its own task.
