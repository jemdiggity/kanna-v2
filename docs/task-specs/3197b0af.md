# Cancellable relay connection establishment

## Goal

Ensure the `kanna-server` desktop relay loop never waits indefinitely while establishing a relay connection and that a local reconnect request can interrupt establishment immediately.

## Scope and constraints

- Bound the complete desktop control connection attempt (TCP, TLS, WebSocket upgrade, and authentication), retrying a timeout through the existing reconnect backoff.
- Race in-flight establishment against the existing local reconnect/disconnect control boundary, without changing established-session behavior or its retry policy.
- Preserve the relay-unavailable reason surface from task `eef65d54` and distinguish `connect timed out` from `connect cancelled` in state/log diagnostics.
- Add server integration coverage with a real TCP fake relay that stalls the WebSocket handshake, proving timeout/retry, immediate reconnect cancellation, and an unaffected established session. Add a dated E2E gap note only if this boundary cannot be covered end to end in the server harness.
- Do not redesign the shared publication/routing WebSocket. Production or staging deployment is out of scope: this is a `kanna-server`-only fix, and task `eef65d54` already deployed the staging relay service.

## Done when

Focused integration tests and Rust checks pass; no connect phase can await forever; local reconnect cancels establishment; diagnostics identify timeout versus cancellation; established relay sessions retain their existing lifecycle.

## Implemented and verified

- The primary desktop relay connection now has one 15-second budget through WebSocket upgrade and `auth_ok`; a timeout drops the socket and follows the existing five-second retry backoff.
- The local reconnect notification races both the signed-in account probe and primary establishment. Cancellation drops the in-flight socket and records a distinct unavailable reason before retrying.
- The unavailable-reason state introduced by `eef65d54` is included here because that task was not yet in this branch; machine discovery and relay request failures preserve timeout, cancellation, close, send, publication, and keepalive reasons.
- Real-TCP fake-relay integration tests cover a stalled WebSocket handshake timing out and retrying after backoff, an upgraded socket stalling at `auth_ok`, immediate reconnect cancellation of a stalled socket, and an established authenticated session remaining usable after the connect budget elapses. The existing HTTP route test covers propagation of the retained reason through machine discovery, so no separate E2E coverage-gap note is needed.
- `cargo test -p kanna-server relay::tests`, the focused machine-list route test, `cargo check -p kanna-server`, and `cargo clippy -p kanna-server --all-targets` pass. Clippy reports only pre-existing warnings outside this task's changes.
