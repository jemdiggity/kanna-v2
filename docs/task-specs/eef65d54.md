# Same-account multi-desktop relay sessions

## Goal

Fix the staging relay failure that prevents two signed-in desktops on the same Kanna account from remaining connected and routing to each other without manual LAN pairing.

## Scope and constraints

- Confirm the failure chain using staging runtime logs and a local two-desktop relay reproduction, distinguishing confirmed findings from plausible hypotheses.
- Make concurrent desktop sessions first-class in the relay registry and routing, including visibility of every desktop on the account.
- Make capacity or flow refusal use an explicit WebSocket close code/reason, and preserve any reason known by `kanna-server` when relay routing is unavailable.
- Add integration/E2E coverage for two same-account desktops staying connected and routing to each other; if full E2E is not practical, add the required dated gap note.
- Deploy only the staging relay through `./kd cloud deploy`, then verify relay health and a stable MacBook Pro session while the Mac Studio is online. Production deployment, LAN-pairing changes, and unrelated relay refactors are out of scope.

## Done when

The cause is documented, focused tests and repository checks pass, staging is deployed, and staging evidence confirms both same-account desktops can remain concurrently connected with working machine discovery/routing or any external verification blocker is explicitly recorded.

## Confirmed investigation result

- The registry-collision hypothesis is false. Staging relay logs show concurrent, distinct control registrations for the account: MacBook Pro `desktop-21b320e8-a5ad-4fae-9d87-1db14090f0a9` and Mac Studio `desktop-aa43ab36-e634-4ae9-b629-e8c8a91f7bff`. The Studio remained registered while the MacBook connection churned.
- The flow-cap hypothesis is false for this outage. `/health` reported `capRejectCount: 0`; `maxBufferedBytes: 17627898` is a tunnel backpressure high-water observation, not a control-channel payload or capacity rejection.
- The confirmed cause is a publisher/relay Unicode contract mismatch amplified by the publisher's failure policy. Staging.8 truncates `promptSnippet` to 500 Rust Unicode scalar values, while deployed relay `d29433be6b7a` validated it with JavaScript UTF-16 `String.length`. A prompt containing supplementary characters was therefore rejected as longer than 500. The MacBook log records `tasks[2].promptSnippet` rejection three times followed by `Cloud task snapshot retries exhausted; reconnecting relay`; this cycle occurred 643 times in the inspected log. Reconnecting the shared socket removed otherwise healthy desktop discovery/routing.
- Bare code-1006 resets also occurred, but relay logs show no matching capacity refusal and they are not the repeated post-auth failure that drove the outage. Their transport origin remains unconfirmed and is not required to explain the observed unavailable state.
- Deployed-relay skew mattered: `d29433be6b7a` contains the UTF-16 validator. The current branch already had a per-user map keyed by desktop ID and explicit tunnel flow close codes, so deploying registry replacement logic is neither necessary nor correct.

## Implemented contract

- Relay publication validation counts `promptSnippet` in Unicode characters, matching the Rust publisher.
- An explicit negative publication acknowledgement suppresses only that unchanged snapshot; it no longer retries it and disconnects the shared routing socket. Missing acknowledgements still use bounded retries and reconnect recovery.
- Pre-upgrade load-shedding completes an HTTP refusal body containing the reason instead of `write()` followed by `destroy()`, which could appear as a bare reset. Established tunnel flow limits continue to use WebSocket close code 1013 with a reason.
- `kanna-server` retains known connection, close-code, keepalive, and send-failure reasons and returns the current reason from the machine-list API while relay routing is unavailable.
- Relay integration coverage proves two desktop-secret principals on one account remain open, appear together in presence, and route an invoke/response between each other.
