# Singleton reclaim after close

Goal: after all Merge Masters close, the next merge handoff atomically claims
and creates a replacement. Closing releases ownership with the authoritative
close write; a missing owner or a provably closed owner is reclaimable, while
an unreachable potentially live owner remains a specific 503. Concurrent
requesters must use the existing reservation and creator/publication fencing.

Scope: server singleton discovery/creation and close publication, relay claim
transactions, deliberate manager/operator recovery, and boundary documentation.
Use the existing signal-merge-handoff find-or-create entry point for recovery:
creation must pass account-wide ownership arbitration, so merely registering a
workflow that ordinary task creation could duplicate is not sufficient.
No UI, release, or unrelated cleanup. Do not publish or advance this task.

Done: server and relay regression tests cover close/recreate, concurrent reclaim,
atomic release, and unreachable-owner refusal; extend relevant relay/multi-machine
E2E coverage or document the gap alongside narrower tests. Run cargo fmt --all,
clippy on touched crates, TypeScript checks if applicable, and ./kd test all.

Implementation rule: the local owner is derived from open task/stage-run rows,
so SQLite close already releases it atomically. The account directory is a
Firestore projection, not that SQLite DB. Publish the task removal and matching
claim deletion atomically there, and await a current snapshot acknowledgement
before local or reachable-sibling singleton discovery. Never claim global
SQLite/Firestore atomicity. Reclaim absent/unowned claims and owned claims
whose owner's complete directory proves the task absent; preserve reservations
and their existing creator-process fences. Re-read directory and claim inside
the claim transaction so concurrent publication cannot resurrect stale owners.
The protocol calls the claim owner `machineId`, the published task owner
`ownerDesktopId`, and the desktop document identity `desktopId`; the quoted
incident error is not a literal emitted by this checkout.

Recovery choice: retain synthetic internal workflows; document and test explicit
re-seeding through `kanna_signal_merge_handoff` (or `kanna_signal_agent` for any
singleton agent). Registering a workflow alone would permit duplicate creation
outside the fenced claim, so that alternative is deliberately not implemented.
The relay E2E task-actions test extends existing creation coverage through
close then handoff/recreation; the two-desktop race also has server router and
Firestore-emulator transaction coverage.

The real account E2E exposed close-before-first-publication: a claim can still
be reserved when its task closes, so there is no previous cloud task to remove.
Close now releases that reservation using the existing creator-fenced command;
a subsequent handoff also repairs a failed release on this desktop or a reachable
sibling after the owning desktop proves the reserved task closed. This is a positive committed-close proof, not absence or
a timeout used as permission to revoke a creator. E2E authenticates with a
real desktop secret in the emulator, assigns a shared repo hash, and checks the
replacement machine/task claim and its release after close.
