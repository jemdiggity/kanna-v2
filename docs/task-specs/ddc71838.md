# Task ddc71838: deterministic Rust timing tests

## Goal

Make the four named Rust tests and the observed cross-version daemon handoff test deterministic under default full-lane parallel load. Preserve the product behavior each test is intended to prove.

## Scope and constraints

- Trace each test's invariant and replace load-sensitive wall-clock assumptions with event-driven or controllable synchronization, or a justified eventual-progress guard.
- Rust only. Do not change daemon/server protocols unless investigation finds a real product race.
- Do not ignore tests, serialize the lane, or merely multiply timeouts without relating the guard to the tested invariant.
- Keep `cargo fmt --all` and `cargo clippy` clean.

## Done when

- The five named tests pass in the default-parallel `./kd test all` lane on a loaded machine.
- `./kd test rust` passes three consecutive times while a concurrent heavy build runs, followed by one `./kd test all` pass.
- This spec records full-lane and isolated reproduction, each root cause, daemon handoff findings, and final verification.

### Root causes

1. **Task-transfer finalization:** the 250 ms ordinary peer timeout was installed when both runtimes were created, so it also bounded pairing, preflight, and commit setup. Under load the test could fail before reaching the finalization request it purported to exercise. The setup now uses the normal request budget, then both runtimes restart from their durable trust and reservation state with the 250 ms budget. Only the finalization operation is exposed to the deliberately narrow ordinary window; its simulated 2.5-second agent wrap-up still proves the first request uses the separate finalization budget.
2. **Advance-stage route:** the setup script already supplied the correct causal gate, but the test asked the HTTP response to beat a one-second wall-clock timeout before first proving setup had reached that gate. Executor, sidecar, and filesystem load therefore counted as a product failure. The request now runs concurrently, the test waits until setup is observably blocked, and then requires the HTTP future to complete while the gate remains closed. A 30-second deadline only contains hangs; passing depends on ordering, not elapsed response time.
3. **Inherited aggregate event leg:** a 1.1-second sleep guessed that a one-second inherited relay poll had completed, a delayed writer guessed that its replacement had started, and a two-second outer deadline counted scheduler delay as failure. The relay harness now reports each invoke's start and completion. The test waits for invoke 1 to finish, resumes the same cursor, waits for invoke 2 (the rearmed leg), and only then writes the peer event. The endpoint's own long-poll completion and event contents prove the wake-up.
4. **Signal-agent route:** a fake daemon slept for five seconds while the route was required to answer within two, conflating detachment with machine speed. The fake daemon now signals when it has received `Spawn` and blocks on an explicit release channel. The test proves the route responds while that acknowledgement gate remains closed; 30-second deadlines serve only as hang containment.
5. **Cross-version daemon handoff:** the fixture communicates through real Unix sockets, and every connection imposed a fixed five-second read timeout. Those blocking reads are already the causal synchronization: responses still must arrive in protocol order and the test still proves both the PTY and agent survive adoption. The five-second value is not a handoff latency contract, so scheduler and process-start pressure could fail an otherwise-correct exchange. This scenario now uses a 30-second read guard solely to contain a wedged fixture; the default five-second guard remains unchanged for other handoff tests.

No product race or protocol defect was found; all five failures were in test setup or timing assertions.
