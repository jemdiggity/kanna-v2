### Attribution

The evidence supports a daemon-originated false status-event flood that forces desktop reactivity/JSON work while Claude is painting. It refutes machine starvation, terminal-buffer scale, renderer fallback, the Claude process itself, and network routing:

- Machine load was not the limiting resource. Although the three load averages began at `9.63, 19.72, 19.07`, the three CPU samples were 88.39%, 53.04%, and 78.38% idle. The 64 GB machine had 13 GB unused, memory pressure reported 92% free, pages throttled were zero, and swapins/swapouts were zero.
- Staging process attribution was: desktop PID 32540, its WebContent PID 33213, GPU PID 33208, daemon PID 37964, and server PID 5163. At capture they used about 0.8%, 4.5%, 1.2%, 2.6%, and 2.3% CPU respectively. The desktop main-process sample was idle in 4064/4067 main-thread samples. The Claude PID 35710 sample was in `kevent64` for 8255/8430 main-thread samples (about 98% idle), so Claude was not consuming the CPU needed to echo typing.
- During the owner's Claude-output reproduction, WebContent was idle in only 7657/8459 main-thread samples (about 90.5%, versus about 94.5% in the earlier sample). Its active timer/microtask branch repeatedly contained `JSC::ProxyObject::getOwnPropertySlotCommon`, `JSC::ProxyObject::performGetOwnPropertyNames`, and JSON `LiteralParser` frames. This is the shape of Vue reactive object replacement, not a hot xterm render loop.
- The matching staging frontend log had 420 `[store] refreshed snapshot after KSP state change` messages in the captured hour. It recorded 34 reloads from 12:20:40.397 through 12:20:59.809 at the original report, and 25 reloads from 12:39:47.353 through 12:39:55.842 while the reproduction sample was running. Each full `/v1/snapshot` response was 132,297 bytes; three direct requests took 9.65–11.05 ms, showing that repeated reactive replacement in WebContent, rather than server response latency, was the costly part.
- The Claude task was local PTY session `f572a73d`, not `CloudTerminalView`; no LAN/relay path was involved. Four xterms were mounted (one task terminal and three shells), scrollback was the configured bounded 10,000 lines, and the current recovery snapshot was only about 10 KB (`serializedLength` 6,742). The WebContent sample contains `WebGLRenderingContextBase` and canvas display frames, with no context-loss/fallback log. There were no xterm backlog events, event-bridge reconnect storm, oversized-frame warnings, or server/daemon outbound-queue stalls.
- The daemon did record short secondary `attached_writer` stalls for `f572a73d` during dense output (670/1156 ms at 12:16:52, 698/927 ms at 12:17:44, 547 ms at 12:31:33, and 627/868 ms at 12:32:02). PTY gap records otherwise name `pty_source_silence`. These stalls explain individual pauses but not the regular half-second reactivity work; they coincide with the excess state traffic rather than a daemon CPU/read-loop bottleneck.

The deciding code path was Claude-specific. Claude does not bracket repaints with DEC synchronized output, so an intermediate clear briefly exposes its parked `❯` composer before the next `Forming… / esc to interrupt` footer arrives. The 500 ms status sampler treated that intermediate grid as a real Busy→Idle edge. Every edge reached the server and caused the desktop `StateChanged` handler to fetch and replace the entire snapshot. Codex brackets its repaint, which is why the owner's Codex control did not reproduce the issue. The quiet-status path also checked PTY `last_active_at`, but that timestamp tracks operator input rather than terminal output and therefore could not prove the repaint was settled.

### Fix and before/after measurement

`crates/daemon/src/session.rs` now records the last mirrored output time. Claude output-triggered classification still publishes positive Busy and Waiting evidence immediately, but cannot publish or infer Idle from an unbracketed partial frame. Claude instead converges to Idle through the existing quiet-status pass after the existing 500 ms output-quiet boundary. Other providers retain their prior immediate-idle behavior, including Codex's synchronized-frame path. No polling, retry, or new throttle was added.

Before the fix, the deterministic Claude repaint used by the regression contains two intermediate parked-composer frames, each eligible to produce a false Idle edge on the old cadence. After the fix, both the unit replay and the real daemon socket→PTY→parser→status timer→fanout test measure **0 false Idle events across 2 partial repaints**, followed by exactly the expected settled Idle transition after 500 ms without output. The live before rate was 25 full 132 KB snapshot replacements in 8.49 seconds during sampling; removing those false transitions removes their corresponding full-store replacements while preserving terminal output and final state convergence.

Verification: focused daemon unit and real-daemon E2E tests pass, the existing Codex idle-status server regression remains green, `cargo clippy -p kanna-daemon --lib -- -D warnings` passes, and `RUST_TEST_THREADS=1 ./kd test all` passes in full. Two default-concurrency full-gate attempts reached an unrelated pre-existing 250 ms task-transfer timing failure in `a_finalization_slower_than_the_peer_request_window_answers_the_first_request`; that exact test passed three consecutive isolated runs and passed in the serialized full gate. This task deliberately does not alter that unrelated test or transfer implementation.
