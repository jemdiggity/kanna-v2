# Task 483f3563: task-event cursor progress and historical fidelity

## Goal

Make `GET /v1/task-events` / `kanna_wait_events` resumable without duplicate pages and make replayed events describe event-time state rather than being overwritten by the task's current state.

## Scope

- Fix and test the `kanna-server` task-event feed and the shared CLI (`ks1`) / MCP (`km1`) aggregate cursor surfaces.
- Accept deployed per-machine cursor forms as needed, but emit one canonical wire form.
- Preserve event-time stage and the run an event describes; keep optional current-state enrichment structurally separate.
- Do not change append-site lifecycle semantics or add event types.
- Add client/server boundary coverage, including mid-settled-scan progress, historical replay after a stage change, and CLI/MCP aggregate cursor round trips.

## Constraints and done criteria

The starting point is current `origin/main` including task `703f1b0c`; behavior it already fixed receives regression coverage rather than a duplicate fix. Every returned cursor must advance or represent a drained tail, repeated continuation calls must not return a sequence twice, both clients must remain in parity, relevant Rust formatting/clippy/tests must pass, and any untestable boundary must be documented in a dated E2E-gap note.

## Baseline decision

The required A/B on `origin/main` (`555f8563`, including `703f1b0c`) showed that a mid-settled aggregate cursor already drains 125+ retained events without repeating a sequence, so that path receives regression coverage only. The same baseline failed the historical replay assertion by replacing the old run's `in progress` stage with the task's current `pr` stage; that enrichment defect and mixed embedded cursor formats are the implementation changes in scope.
