# Task 533d9aac — relay status dashboard and a usable `/stats` credential

## Goal

Give the operator a relay status view that does not require
`gcloud compute ssh` + `docker logs`. Owner request, 2026-08-21: *"do we have a
relay status dashboard I can use? I'm streaming this console rn"*.

Two things block that today:

1. There is no status page at all — `/health` reports a commit, a connection
   count and the tunnel-flow counters, and nothing else.
2. `GET /stats` (the byte odometer, landed by the odometer task) is gated on a
   **Firebase ID token**, which is a credential no operator has to hand — the
   desktop's own task-events token gets a 401 because it is not a phone ID
   token. The route is effectively unreachable.

## Scope

In:

- **`GET /dashboard`** — a single self-contained HTML page served by the relay
  process itself (same VM, no new infra, no external asset), polling `/stats`
  every few seconds and rendering: the live connection list (uid, desktopId,
  role, tunnel service, duration, per-class byte counters), process aggregates
  since start (bytes by class, connection totals, refused upgrades,
  compression negotiation counts), tunnel buffer pressure (the existing
  `tunnelFlow` counters), and the last N close-time rollups.
- **`KANNA_RELAY_STATS_TOKEN`** — an operator credential for `/stats` and
  `/dashboard`, read from the environment, compared in constant time, accepted
  from `Authorization: Bearer` **or** a `?token=` query parameter. Both routes
  answer `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.
- The counters the dashboard needs that do not exist yet: refused upgrades
  (per status), per-connection compression negotiation, a bounded ring of
  close-time rollups, and a live per-connection reader.
- **Deploy plumbing** — the variable is declared in
  `services/relay/deploy/docker-compose.yml` and written into
  `/opt/kanna-relay/.env` by `kd cloud deploy --relay` from the
  `kanna-relay-stats-token` Secret Manager secret. A missing secret writes no
  line and never fails the deploy; the dashboard is simply disabled.
- **`kd relay stats --staging|--production [--open] [--dry-run]`** — reads the
  token (env override first, else the Secret Manager secret via `gcloud`) and
  either prints the `/stats` JSON or prints/opens the dashboard URL with the
  token in the query string. No `--json` flag: printing the JSON *is* the
  default, so a flag for it would name the absence of `--open`. `--dry-run`
  prints the resolved plan (URLs, token source, the secret-read command) without
  reading the secret — the level the kd test asserts at.
- `docs/relay-vm-operations.md` updated: where the token comes from, how to
  provision it, what the dashboard shows, and the privacy boundary.
- Tests: relay tests for the auth gate (401 without a token, 200 with),
  the dashboard route serving, and the `/stats` payload shape; a kd test for
  the helper's env plumbing at dry-run level.

Out (deliberately):

- Exposing `relay stats` as a `kd-mcp` tool. The MCP registry is a curated list
  of high-value tools, and this one hands back a credential in its `--open`
  output; an operator types it.
- A real-browser test of the page. There is no browser tier the relay's suite
  can reach, so the gap is recorded in
  `docs/2026-08-21-relay-status-dashboard-e2e-gap.md` with the narrower tests
  that stand in for it: a spawned-relay route/auth test and a `node:vm` render
  test of the page's own script against a real `/stats` payload.
- Any new infrastructure — no separate metrics service, no Cloud Monitoring
  export, no dependency added to the relay.
- Persisting counters across a relay restart. `/stats` is still in-memory and
  still resets on redeploy.
- Changing `/health`, which stays unauthenticated and unchanged.
- Deploying. This rides the next staging relay deploy.

## Constraints

- **Never expose per-user data unauthenticated**, and not to an arbitrary
  authenticated account either. The pre-existing Firebase-ID-token credential
  keeps working and keeps seeing exactly what it saw before — process
  aggregates with no uid, desktop id, or per-connection row. The per-connection
  rows and close rollups the dashboard needs *are* per-user data, so they are
  served only to a caller presenting `KANNA_RELAY_STATS_TOKEN`. Two credentials,
  two visibilities, one route.
- Dependency-free and small: the relay runs on a 1 GB e2-micro, and its
  Dockerfile copies only `services/relay/src/`, so the page ships as a TypeScript
  module, not as a static asset.
- The token in a query string is accepted deliberately (single-operator tool,
  no-store, no-referrer, scoped to stats only) so `--open` can hand the browser
  a working URL.

## Done when

- `/dashboard` renders live in a browser given a valid token and auto-refreshes.
- `/stats` returns 401 with no credential and 200 with the operator token, with
  per-connection rows present only for the operator token.
- `kd relay stats --staging` prints the JSON, `--open` opens the dashboard.
- `docs/relay-vm-operations.md` documents the token's provenance.
- The relay suite, the kd suite, and repo-wide `pnpm test` pass.
