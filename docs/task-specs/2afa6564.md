# Task 2afa6564 — relay byte odometer

## Goal

Owner request 2026-08-20: measure real per-user relay traffic ahead of
subscription pricing (`docs/specs/accounts-and-billing.md`, fast-follow item
16, "per-user bandwidth metering/quotas"). Today `services/relay` measures
message sizes only for backpressure — nothing cumulative — so nobody knows
which class of traffic dominates or what an account actually costs.

This task lands the measurement, not the enforcement: counters plus a way to
read them. No quotas, no billing, no storage.

## Scope

In:

- Cumulative sent/received byte counters per WebSocket connection, accumulated
  at the relay's **existing** measurement points (the `rawDataByteLength`
  already computed for backpressure), attributed to the authenticated Firebase
  uid and desktop id.
- A message-class split, at least: tunnel/terminal bytes, task-transfer tunnel
  bytes, and control/metadata.
- Emission: a structured log line on connection close (uid, desktopId,
  duration, per-class totals); a periodic rollup log line per active connection
  so long-lived tunnels are visible before they close; and an authenticated
  read-only endpoint exposing the process's aggregate counters.
- Counters are in-memory per process. No new storage system, no Firestore
  writes, no new deploy secret.
- Coverage: unit tests for attribution and the class split, and an integration
  test driving the real relay with a mobile+desktop pair over both tunnel and
  control traffic, asserting the close-time rollup's per-class totals.

Out (real, deliberately not done here):

- Quotas, throttling, entitlement gating, or any billing surface.
- Durable/aggregated usage records that survive a relay restart. A relay
  restart resets every counter; that is acceptable for a measurement pass and
  is stated in the ops runbook.
- Per-uid breakdown over HTTP. The endpoint reports process aggregates only
  (see Constraints).
- The unauthenticated `/ota/*` bandwidth surface — HTTP, not WebSocket, and its
  own item in the billing spec.

## Constraints

- Negligible hot-path overhead: integer adds only, no per-message logging, no
  second measurement of a payload the relay already measured.
- No per-user data reachable by an unauthenticated caller. `GET /stats`
  requires a Firebase ID token and returns **process aggregates only** — no
  uid, no desktop id, no per-connection rows. Per-user attribution exists only
  in the relay's own logs, which are not served over HTTP.
- `/health` keeps its existing shape and unauthenticated posture; the odometer
  does not change it.
- Repo TypeScript conventions: no `any`, `pnpm exec tsc --noEmit` clean.

## Decisions taken while implementing

- **Four classes, not three.** The task named three (`tunnel`, `taskTransfer`,
  `control`); the split shipped adds `terminalEvent`. The task's premise was
  that raw terminal bytes ride the tunnel (`router.ts` `forwardTunnelData`),
  but the mobile app's remote transport
  (`apps/mobile/src/lib/transports/relayClient.ts`) streams terminal output as
  control-plane `{"type":"event", payload:{session_id, type:"terminal_output"}}`
  messages routed to session observers — not through a tunnel. Folding those
  into `control` would have hidden exactly the traffic the odometer exists to
  measure. The task's wording ("at least into") allows the extra class.
- **`GET /stats` authenticates with a Firebase ID token**
  (`Authorization: Bearer <idToken>`), the credential the relay already
  verifies for `/register` and `/push/register`. An ops-only shared secret was
  rejected: `kd cloud deploy` rewrites `/opt/kanna-relay/.env` on every deploy,
  so a new token would have needed a Secret Manager entry, an IAM grant, and a
  `kd` change — infrastructure scope this task does not own. Because the
  response carries no per-user data, any authenticated account reading it
  leaks nothing about another account.
- **Classification happens once, at the ingress boundary**, and the same class
  is applied to the forwarded egress bytes. The relay never parses tunnel
  frames (by design), so a tunnel's class comes from its service, not its
  content.
