# Task spec — terminal history across full-screen TUIs and stage transitions

## Goal

Stop losing earlier terminal content to full-screen agent TUIs:

1. **Startup (setup) script output** disappears from the user's view as soon
   as Claude's TUI takes over the screen, and stays invisible after a restore.
2. **Stage transitions** (implement → review → …) discard the previous
   stage's terminal content entirely; the user cannot scroll back past the new
   agent's screen to see what the earlier session printed.

The task owner explicitly allowed dropping any part of this that turns out
complicated or weird.

## Findings that shape the design (verified in code + empirically)

- Claude Code (measured: 2.1.239) runs its main TUI in the **alternate
  screen** (`ESC[?1049h`, then `2J`). Setup output therefore lives safely in
  the **primary** screen/scrollback; the daemon's Ghostty-based snapshot
  serializer already preserves it (`<primary+scrollback>` + `?1049h` +
  `<alt frame>`). Nothing overwrites it — it is only **unreachable**, because
  xterm.js cannot scroll into the normal buffer while the alternate buffer is
  active.
- Stage transitions kill the daemon session and respawn the same session id
  with a **fresh** headless terminal; the old emulator (and all scrollback) is
  dropped. Only the printed `━━ Stage advanced ━━` marker survives, and only
  into the new session.

## Scope

**In:**

1. **Server-side stage-transition terminal continuity**: when a stage
   transition (including a revision's fresh-fork fallback) replaces a task's
   PTY session, snapshot the outgoing session's terminal, flatten it into a
   primary-screen history seed (drop the transient alt-screen TUI frame, reset
   modes/styles), and seed the replacement session's headless terminal with it
   via the existing `SeedSnapshot` mechanism. The existing stage marker
   prelude separates the segments. Best-effort: any failure to snapshot or
   seed must never block the stage transition.
2. **Desktop access to pre-TUI output**: while the live terminal is in the
   alternate screen, surface a small affordance ("Earlier output" chip →
   read-only overlay) that lets the user view the normal-buffer content (setup
   output, prior-stage history) that the TUI is hiding.
3. **Stage-swap snapshot reset on the client** (required for #1 to be
   correct): a `session_created` rebind or a cleared stale-exit latch marks
   the next snapshot as replacing the xterm buffer for *every* provider.
   Codex's reconnect path deliberately skips `reset()`; without this, the
   carried history in the fresh snapshot would be appended below the dead
   incarnation's content and read twice.

**Out (deliberately):**

- Flattening the alt-screen TUI's final frame into scrollback text at stage
  boundaries — the frame is transient chrome; carrying it forward as text adds
  noise and would need new daemon surface. The primary-screen scrollback (what
  the agent actually printed outside its TUI, plus setup output) is what
  carries over.
- Raw-byte replay or changes to the snapshot serializer.
- Rerun continuity (`kanna_rerun_stage`): a rerun is "try again"; carrying the
  failed attempt's noise forward was not asked for.
- Mobile UI changes (mobile already has a server-side scrollback protocol).

## Constraints

- No daemon protocol changes: `Command::Snapshot` and `Command::SeedSnapshot`
  already exist.
- Continuity is cosmetic; every added step in the stage-transition path is
  best-effort and logged, never fatal.
- Seeded history must not leak terminal modes (alt screen, mouse reporting,
  bracketed paste, kitty keyboard) into the replacement session.

## Done when

- Advancing a task's stage seeds the new session's terminal with the previous
  session's primary-screen history, separated by the stage marker; scrolling
  up in the new session (when its agent is not in the alt screen) shows the
  previous stage's content.
- With Claude's TUI active, the desktop offers a way to read the setup output
  / earlier history without disturbing the live session.
- Tests cover the seed-VT flattening and the transition ordering
  (snapshot → kill → seed → spawn); an E2E gap note records anything not yet
  E2E-testable.
