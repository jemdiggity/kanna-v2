# Stop the canonical gate failing for reasons unrelated to the change under test

## Goal

Agents kept reporting the same two failures as "pre-existing, unrelated to my
change", each after spending time confirming that themselves. Both are real and
neither is a flake in the agent's work:

1. **Absolute wall-clock deadlines.** This box routinely runs four to six
   worktrees' suites and cargo builds at once (load average ~20). Tests whose
   pass condition was a short absolute deadline failed nondeterministically
   there and passed in isolation.
2. **Fresh-worktree sidecar builds.** `cargo check --workspace` and
   `cargo clippy --all-targets` failed in any fresh worktree because
   kanna-desktop's Tauri build script hard-requires
   `binaries/kanna-daemon-aarch64-apple-darwin`, which only exists after
   `./kd build sidecars`.

## Scope

In:

- The timing mechanics of tests that guard the canonical gate (`./kd test all`),
  plus an audit for other sub-second absolute deadlines beyond the named
  offenders.
- The Tauri build script's behaviour when sidecars are absent, and docs so
  agents stop rediscovering it.

Out:

- Any change to what a test asserts. Only timing and provisioning mechanics
  move; no correctness assertion is weakened.
- Suites outside the canonical gate (desktop E2E mock/real, live agent-CLI
  contracts, remote E2E). They are excluded from `./kd test all` and were left
  alone.
- The product behaviour any of these tests exercise.

## Constraints

- Fix the assertions, not the numbers: prefer relative behaviour, a mocked
  clock, or an order-of-magnitude ceiling *stated as such in a comment*, over
  inflating a budget until it passes today.
- Port collisions get OS-assigned ports (bind `0`), following the existing
  harness.
- Sidecar rule from AGENTS.md: final sidecar binaries used for staging,
  packaging, or daemon launch must come from a build-private `.build/` path — a
  check-only stub must never be usable as a real artifact.

## Decisions

- **Class 2: the build script degrades; worktree setup does not provision.**
  The deciding evidence is that the Bazel release path already resolved it the
  same way — `desktop_build_script` in `apps/desktop/src-tauri/BUILD.bazel`
  hands the build script
  `TAURI_CONFIG={"bundle":{"externalBin":[],"resources":[]}}` and assembles the
  shipped sidecars from Bazel targets, so a release bundle never reads
  `binaries/` at all. Provisioning would have meant six extra crate builds in
  every fresh worktree purely to lint, and the only cheap form of it is a stub,
  which is exactly the artifact the repo rule forbids. Nothing is stubbed here:
  the `externalBin` entry is *removed* for check-only builds, so a relaxed
  build cannot produce something that stands in for a real sidecar.
- **Bundling is opt-in-to-strict, by env var.** `KANNA_REQUIRE_SIDECARS=1`
  marks an invocation that produces a runnable app; every in-repo path that
  drives the Tauri CLI sets it. The CLI's own `TAURI_CLI_VERBOSITY` is a
  best-effort second signal, not the contract.
- **Class 1 technique, in order of preference used:** happens-before over
  duration (read the parked state directly instead of inferring it from elapsed
  time); relative over absolute (compare against what the regression would
  actually cost); order-of-magnitude ceiling with the regression and its cost
  named in a comment. Liveness waits — where the thing either arrives or never
  does — are deliberately generous, because the assertion after them is what
  proves the behaviour.
- **The runner's own defaults were the largest single lever.** `vitest.shared.ts`
  now owns the workspace's test and hook ceilings, and `vitest.setup.ts` raises
  `vi.waitFor`/`vi.waitUntil`'s 1s default, which vitest hard-codes with no
  config knob and which was an implicit sub-second deadline on ~200 call sites.

## Acceptance

- `./kd test all` runs to completion and is green at least twice while the box
  carries real load from other worktrees.
- `cargo clippy --all-targets` in a fresh, sidecar-less worktree passes or skips
  cleanly per the Class 2 design.
- No correctness assertion weakened.

## Notes on the named offenders

Two entries in the task prompt are worth recording, because leaving them
untouched otherwise reads as an omission:

- `apps/desktop/tests/e2e/helpers/fixture-repo.test.ts`, named as carrying a
  100ms worker perf budget, has no timing assertion in it at all — its only
  numeric literals are array indices and length comparisons, and it is not
  collected by the gate in any case (`apps/desktop/vitest.config.ts` excludes
  `tests/e2e/mock/**` and `tests/e2e/real/**`, and this file asserts nothing
  about time). The 100ms budget was in
  `apps/desktop/src/services/desktopStreamFrameDecoder.realWorker.test.ts`,
  which is fixed: the synchronous call is now asserted as a fraction of the
  total decode rather than against a wall clock.
- Of the two older flakes named for verification, one was already fixed and one
  was not:
  - `crates/kanna-mcp/tests/stdio_http.rs` already binds `127.0.0.1:0`
    throughout, so its port collisions were genuinely gone. Left untouched.
  - `startup_artifact_cleanup_yields_the_async_runtime_worker`
    (`crates/task-transfer/src/runtime/tests.rs`) was **not** load-immune, and
    an earlier round of this task wrongly cleared it on the grounds that it
    asserts a yield rather than a duration. It does — but the probe parked on
    `yield_now`, so it needed *two* executor turns, and the spawn only yields
    when `spawn_blocking(..).await` is still pending. With one stale file the
    cleanup often finished first, the await returned `Ready` without giving the
    executor a turn, and a correct implementation failed. Reproduced at 2/12
    under load. Fixed by seeding enough stale artifacts that the cleanup is
    real work (so the await reliably pends) and by having the probe store on
    its first poll instead of parking. Now 20/20 under load, and still fails
    when the cleanup is made inline — verified by temporarily replacing the
    `spawn_blocking` with a direct call.

Two of the reported offenders turned out **not to be deadline bugs**, and the
real causes are fixed instead of the symptom:

- `tools/kd/tests/rust-cache.integration.test.ts` raced cargo's metadata
  pipelining — the stand-in cache poisons `defaults` only after rustc exits, so
  the consumer could compile against the fresh `.rmeta` and fail later with
  E0460 instead of the E0432 the negative control asserts.
- `crates/task-transfer/tests/runtime.rs`'s pre-auth-permit test lost two of
  sixteen permits to a 10s peer-request timeout that expired while the test
  drained their events.

## Beyond the literal task, and deliberately left alone

Done, but outside the literal task, so recorded rather than folded in silently:

- `crates/daemon/src/pty.rs` had nine unbounded `while session.try_wait().is_none()`
  reap loops. A zsh child that wedged mid-exit made one spin for fifteen
  minutes with no output, hanging the whole gate on a single line. They are now
  bounded, so a wedge reports itself. This is the *opposite* of a deadline
  problem, which is why it is called out here.

Left alone on purpose:

- `kanna_info_retains_adapter_and_endpoint_when_status_is_unreachable`
  (`crates/kanna-mcp/tests/stdio_http.rs`) uses the standard
  reserve-port-0-then-drop pattern, which carries a microsecond TOCTOU window.
  There is no clean std-only alternative and it was not among the observed
  failures, so it is left as is.
- The `drain_output(fixed window)` idiom elsewhere in the daemon tests is a
  fixed flush window rather than an assertion deadline. It was not among the
  observed failures and rewriting it would be a project, not a fix.

- Four more Class 1 offenders surfaced while running the round's own acceptance
  bar, each of which failed a `./kd test all` on this tree. They are the same
  failure class the task exists to remove and each blocked acceptance, so they
  are fixed rather than deferred:
  - `ClientConn::recv` (`crates/daemon/tests/reconnect.rs`) had a 5s socket read
    timeout whose expiry panics `"read timed out"`; it failed
    `natural_exit_finalization_precedes_same_id_replacement_creation`. Now a
    named, commented liveness ceiling.
  - The `callLatencyMs < totalDecodeMs / 4` ratio this task introduced in
    `desktopStreamFrameDecoder.realWorker.test.ts` was itself a bad relative
    baseline — worker startup dominates the synchronous side and does not scale
    with the async decode, so under load the numerator grew while the
    denominator did not (failed at 66ms vs 55ms). Replaced with an
    order-of-magnitude backstop; `ticks` remains the direct, load-immune
    statement of "the main thread stayed schedulable".
  - Three `sleep(500ms)` "give the daemon a moment to observe EOF" waits in
    `crates/daemon/tests/agent_sessions.rs` were wall-clock guesses at a state
    transition; when the guess was short the next input never took the respawn
    path the test asserts on. They now poll for `SessionState::Exited`, which is
    the transition itself.
  - `crates/task-transfer/tests/sidecar_control.rs` had 1s/2s/3s waits on an
    out-of-process sidecar; folded onto the file's existing
    `CONTROL_RESPONSE_WAIT` liveness constant.
