## Open questions / contradictions found (recorded, not fixed — outside scope)

1. **Portal ↔ billing-backend checkout contract mismatch** (verified in code,
   unresolvable by docs): the portal calls `createCheckoutSession` with
   `{successUrl, cancelUrl}` and no `plan`
   (`apps/web-portal/src/types.ts:12-15`), but the backend requires
   `plan: "monthly"|"annual"` (`services/firebase-functions/src/billing/checkout.ts:36-41`),
   ignores the client URLs, and builds return paths `/billing/success` /
   `/billing/canceled` — routes the portal does not register (it has
   `/checkout/success` and `/checkout/cancelled`). Each side's tests pin its
   own spelling, so nothing fails today; a live call would. Also, the backend
   may return `url: null`, which the portal types as `string`.
2. `.kanna/workflows/schema.json` still describes `revision_limit` as
   "defaults to 3"; the code default is 5
   (`crates/kanna-server/src/task_creator/definitions.rs:210`). Live
   code-asset bug, not a docs/dev file.
3. `docs/relay-vm-operations.md` glosses `/stats`' `connections` as "paired
   desktop/phone connections"; it is the number of userIds with an active
   connection pair (`services/relay/src/router.ts:844-846`).
4. `apps/web-portal/README.md:13` still says "Until the billing backend
   lands…" — it has landed; the test stub remains but the framing is stale.
5. `docs/kanna-server-boundary.md` CLI section (~line 1125) still describes
   pre-#1134 send-input semantics (retained-behind-draft prints ok) and omits
   `kanna-cli task inputs` and `--source`; its own earlier "Terminal Input
   Boundaries" section states the corrected contract.
6. Dead relay-era leftovers: `services/relay/deploy/compose.yaml` (nothing
   consumes it) and the `KANNA_CLOUD_RUN_REGION` variable name in
   `services/relay/deploy/provision.sh:7`.
