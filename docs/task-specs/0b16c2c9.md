# Task 0b16c2c9 — a revision must never start with empty reviewer feedback

## Goal

Fix the platform defect observed on staging 2026-08-20 (desktop-21b320e8, task
33d3d96a): a failed review recorded a non-empty verdict, but the revision it
triggered was composed with an empty `Reviewer feedback:` section. The revision
agent had nothing to act on, spent revision round 2 of 5 confirming that, and
the reviewer's findings were lost.

## Scope

In:

- Trace review-failure → `request_revision` → revision-prompt composition in
  `kanna-server`, and identify where feedback can legally be empty while the
  terminating run's verdict is not.
- Refuse an **agent-origin** `request_revision` whose `prompt` (the reviewer's
  findings) is empty or whitespace, with an actionable error, **without**
  spending a revision round and without closing the review run — so the
  reviewer can retry with the findings.
- When composing a revision, fall back to the terminating run's `feedback`,
  then its result `summary`, if the request carried no feedback; refuse the
  revision outright if no verdict exists anywhere, rather than starting an
  agent with an empty feedback section.
- Tests: a review failure with feedback reaches the revision prompt; an
  empty-feedback agent request is refused and `revision_rounds` is unchanged;
  a blank-feedback human request still runs, on the fallback text.

Out (real but separate):

- The `summary`/`prompt` field split itself, and the tool-catalog schema (an
  empty string satisfies `required`). Not widened here.
- Any change to reviewer agent definitions; they already instruct putting the
  findings in `prompt`.

## Constraints

- Human-origin revisions are never refused (desktop review action, budget
  hand-back) — a short human prompt stays valid; only empty falls back.
- The round-claim/refuse ordering must keep the existing exhausted-budget
  parking behavior intact.
- Rust conventions: no `unwrap()` in production code, `cargo fmt`, clippy clean.

## Done when

- `cargo test -p kanna-server` (revision/workflow suites included) passes, with
  new coverage for the three cases above.

## Mid-task data point (owner, 2026-08-20, during implementation)

The owner reported a second occurrence on the same task 33d3d96a: review run
`run-33d3d96a-1787219353754974000` (failed 09:49:21 UTC, non-empty feedback
column) → revision run `run-33d3d96a-1787219588008345000` (started 09:53:16)
again spawned with an empty `Reviewer feedback:` section **and an empty
`feedback` column**. Rounds 1 and 3 carried full findings; rounds 2 and 4 lost
them. The owner asked whether two distinct code paths exist — an explicit
`kanna_request_revision` versus a `kanna_complete_stage` failure
auto-triggering a revision.

Traced and answered: there is only one. `complete_stage` with
`status: "failure"` returns without preparing anything
(`crates/kanna-server/src/http_api/task_actions.rs`, `should_auto_advance`
guard), and `prepare_revision_task_for_api` has exactly one non-test caller —
the `request_revision` handler. A revision run's `feedback` column is written
verbatim from the request's `prompt`, so an empty column proves the caller
sent `prompt: ""`; the alternation is caller-side, not two engine paths.

This does not change the terms: the fix is the same either way, and both
halves of it now cover this occurrence — the agent-origin request is refused
before a round is spent, and any request that still arrives without feedback
runs on the terminating review run's recorded verdict instead of nothing.
