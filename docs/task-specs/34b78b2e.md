# Review against a committed task spec, not a reconstructed prompt

## Goal

A task's effective instructions are the original prompt plus every mid-task
directive. Reviewers reconstruct that from the stage prompt and the
delivered-input ledger, and the reconstruction diverges as directives
accumulate — twice this week (the pin-button incident, and task 00e8169f round
4). Make the implementer commit a spec stating the task's terms, and make
reviewers judge the branch against that spec.

## Scope

In:

- A spec artifact written by `implement`, committed by `commit`, judged against
  by `review` and `qa-dispatcher` (and by the specialty panel the dispatcher
  briefs).
- A decision, with reasoning, on where the file lives and whether it survives
  into the merged PR.
- A proportionality rule so the spec is not busywork on trivial tasks.
- Docs for the convention; content tests pinning it.

Out:

- Engine, server, daemon, and workflow-JSON changes. Anything the engine would
  have to know is named as a follow-up instead.
- Editing the seven specialty `review-*` definitions: they receive the spec
  through the dispatcher's child prompt.
- The `pr` agent and its flavors — see the lifecycle decision below.
- The delivered-input ledger itself (task 973bc808, already landed): this
  builds on it and does not change it.

## Constraints

- Zero engine behavior change: agent definitions, docs, and content tests only.
- The convention must read for any project, not Kanna specifically (the
  architect de-branding precedent).
- Respect internal/public agent visibility rules; `commit` stays internal.
- The `Revision round N of M` preamble and revision-budget semantics are
  untouched.
- Verify with `pnpm test` and `cargo test -p kanna-server task_creator::`.

## Decisions

- **Path:** `docs/task-specs/<task-id>.md`, keyed by `$KANNA_TASK_ID` (stable
  across stage forks; branches and worktrees are not). Flat, not sharded by
  date: a revision weeks later must update the same file, and a shard computed
  from "today" would create a second one.
- **Lifecycle:** committed on the task branch and **kept** through the merged
  PR. `.kanna/task-specs/` was rejected on a mechanism — the definition
  snapshot reads `.kanna` recursively and batch-reads every blob it names at
  every resolution. A `pr`-stage drop was rejected because it puts a mandatory
  `git rm` plus commit into the most fragile agent in the system, ahead of its
  rebase and duplicate-PR logic, repeated across flavors, one of which opens no
  PR. Cost stated honestly in the spec doc: ~242 merges/30 days here, so the
  directory grows by roughly 3000 small files a year, contained in its own
  directory and prunable in bulk.
- **Proportionality:** existence, honesty, and currency are required; length is
  never a finding. A three-line spec is a correct spec.

## Acceptance

- `implement` seeds the spec early and updates it in the same commit whenever a
  directive, reviewer feedback, or a declined finding changes the terms.
- `commit` commits it and never invents one.
- `review` and `qa-dispatcher` judge against the spec, use `kanna_task_inputs`
  as the audit trail, treat a spec/ledger disagreement as a finding rather than
  a licence to substitute their own reading, and treat a missing or stale spec
  as a blocking finding.
- Content tests in `packages/core/src/workflow/qa-assets.test.ts` pin all of
  the above; `pnpm test` and `cargo test -p kanna-server task_creator::` pass.
