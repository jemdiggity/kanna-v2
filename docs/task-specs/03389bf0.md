# Task 03389bf0 — Slice-1 relay entitlement enforcement (flag-off) + comp seeding

Source of terms: `docs/specs/accounts-and-billing.md` — Decision 5
(enforcement), Decision 3 (the `comp` source), Decision 7 Slice 1, Decision 8
(coverage). Owner approved starting Slice 1 on 2026-08-20.

Blocked-on work that landed first: `058e51d5` (relay desktop-credential TTL
cache — the pattern this reuses) and `344057c3` (entitlement record + reducer —
what this enforces against).

## Goal

Teach the relay to read `users/{uid}/entitlements/cloud_access` after identity
verification and refuse the paid surfaces when it is not honoured — with the
whole check behind a config flag that is **off** everywhere until Slice 3 — and
land the operator script that grants complimentary (`comp`) access to the
owner-designated existing accounts.

## Scope — in

1. **Entitlement resolution** in the relay, after identity verification, for
   both session kinds (phone Firebase ID token, desktop `desktopCredentials`),
   behind an in-memory TTL cache (~60 s) modelled on the credential cache from
   `058e51d5`.
2. **Refusal semantics**, exactly the set Decision 5 enumerates:
   - the session still completes auth (`auth_ok`);
   - an unentitled session is advertised **no** `tunnelServices`, and no
     `taskSnapshotPublication` / `mobileNotifications` capability;
   - `tunnel_request`, `task_snapshot_publish` and
     `mobile_notification_publish` are refused with the distinct code
     **4402 / `entitlement required`** so a client can render "subscription
     required" instead of a generic failure, and a tunnel socket that reaches
     the relay anyway is closed with the same code.
   - The relay never closes an ordinary session over an entitlement: that would
     produce exactly the generic connection error Decision 5 exists to avoid,
     and it would stop the client reading its own state.
3. **The config flag** `KANNA_RELAY_ENTITLEMENT_ENFORCEMENT`, default off.
   Off means byte-identical behaviour to today: no entitlement read, no new
   `auth_ok` field, no refusal. Passed through `deploy/docker-compose.yml` with
   an `off` default so Slice 3 can flip it from the VM `.env`; the deploy
   writes no value for it, and nothing in this task enables it anywhere.
4. **Comp seeding script** — writes `users/{uid}/billing/comp` for
   owner-designated accounts and invokes `recomputeEntitlement` explicitly, so
   the reducer derives the entitlement. Runs against the emulator by default;
   a real project requires an explicit typed confirmation (human-only, same
   rule as production deploys).
5. Tests per Decision 8's relay row, against the emulator.

## Scope — out (deliberate)

- **Flipping the flag.** Slice 3.
- **Gating phone→desktop `invoke` routing** (the `remote_task_control`
  capability). Decision 5 enumerates the refusal set as tunnels, publication
  and push, and this task's brief repeats that set; mobile has no
  subscribe/inactive surface to route to until Slice 2/3, so refusing remote
  control today would produce exactly the generic dead end Decision 5 is trying
  to avoid. **This is a real gap in what flag-day would enforce** — an
  unentitled phone could still drive tasks on its desktop — and it must be
  settled before Slice 3 flips the flag. Flagged here and in the run summary
  rather than fixed, because widening enforcement past the spec's enumerated
  set is a scope decision for the owner, not for this task.
- **Firestore-rule entitlement gating** — Decision 5 says rules stay as they
  are; the task index merely goes stale.
- **LAN.** Untouched, and free forever. Nothing in this change reaches a LAN
  path.
- **A shared TTL-cache primitive.** The entitlement cache duplicates roughly
  thirty lines of shape from `auth.ts`'s credential cache. Extracting a common
  primitive would mean rewriting freshly-landed code from `058e51d5`, and the
  two caches differ where it matters (the credential cache re-checks the
  presented secret's hash on every hit and has an explicit invalidation hook;
  the entitlement cache is a plain keyed value). Declined as a refactor this
  task does not require.

## Constraints and edge cases carried in

From the billing-backend review (PR #1150, recorded on task `344057c3`),
relayed by the manager on 2026-08-21:

1. `invoice.payment_failed` maps to `grace` unconditionally in
   `stripeEvents.ts`. Unreachable through the Checkout funnel, but a
   dashboard-created subscription whose first invoice fails would be granted
   entitlement it never paid for. Reducer-side; not fixed here.
2. **A `grace` source stays entitled past `graceEndsAt`** until Stripe sends
   another event. The enforcement-side read therefore treats a `grace`
   entitlement whose `graceEndsAt` has passed as **unentitled**, and a test
   pins it. Deliberately *not* symmetric: an `active` record past
   `currentPeriodEndsAt` stays entitled, because renewal legitimately advances
   that field a moment after the period ends and denying the gap would lock out
   paying subscribers.
3. **A manual admin-SDK write to `billing/comp` does not trigger
   `recomputeEntitlement`** — there is no Firestore trigger. The seeding script
   invokes the recompute explicitly, and `docs/comp-access-runbook.md` states
   the procedure for an operator who writes the doc by hand.
4. `duplicateSources` is suppressed whenever comp is active. Out of scope to
   fix; enforcement never reads that flag.

Other terms:

- The reducer as landed has no `grandfathered` **writer** — Decision 3 folds
  manual grants into the single `comp` source with a `reason` field. So
  grandfathering is seeded as `billing/comp` with `reason: "grandfathered"`,
  and the derived entitlement reads `source: "comp"`, not Decision 5's literal
  `source: grandfathered`. Recorded here because it is a visible deviation from
  Decision 5's wording, resolved in favour of Decision 3's mechanism rather
  than by adding a fourth source writer.
- Phone sessions with `email_verified: false` are unentitled regardless of the
  entitlement doc (Decision 1; Decision 8's relay row names the case). Desktop
  credential sessions carry no token and so no such claim.
- A Firestore failure while reading the entitlement **fails open** (the session
  keeps working, the error is logged) and is never cached; only an
  authoritative answer — the document is absent, or says not entitled — refuses.
  An outage must not disconnect every paying subscriber, and it is the same
  posture the credential cache already takes.

## Done when

- Enforcement off: the relay behaves exactly as before, and the existing relay
  suite proves it.
- Enforcement on, against the emulator: an entitled session advertises tunnel
  services and publishes; an unentitled one authenticates, advertises none, and
  gets 4402 on tunnel request, snapshot publication and push; a comp-seeded
  account passes; a revocation is honoured within the TTL bound; a `grace`
  record past `graceEndsAt` is refused.
- The comp script grants and revokes against the emulator, with the reducer
  deriving the entitlement, covered by a test.
- `pnpm test` and the relay suite pass; `pnpm exec tsc --noEmit` is clean.
- The boundary this task cannot cross end to end — no Stripe credentials, no
  client surface that renders 4402, flag off — is recorded in
  `docs/2026-08-21-relay-entitlement-e2e-gap.md`, per the repo's E2E
  expectation.
