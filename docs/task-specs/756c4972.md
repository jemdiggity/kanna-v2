# MCP completion of reused-session posts

Goal: let an existing MCP adapter complete a commit post without restarting, with the server resolving an omitted run id to the task's sole running run. Explicit ids must match; ambiguous requests must name the running ids. Preserve CLI completion and retry behavior, and apply the same resolution to other run-scoped MCP actions that depend on session environment.

Scope: trace server completion, MCP/CLI binding, and post injection; implement shared resolution as needed, route and adapter regressions, real post E2E coverage (or a dated gap note with route tests), and update the server boundary documentation. No agent-prompt workaround, publishing, or stage advancement.

Done: post completion transitions the workflow using the existing adapter; stale/ambiguous ids are rejected with actionable ids; CLI remains compatible; touched Rust crates pass clippy, cargo fmt --all runs, and ./kd test all passes. Mechanism and verification findings will be recorded below.

Mechanism traced (2026-09-05): `complete_stage` used `latest_stage_run` and rejected omitted ids when `stage_run.completion_bound` was true. Both fresh spawns and injected post runs set that bit. MCP `bind_request_to_spawned_run` and CLI `bind_completion_request` already read `KANNA_COMPLETION_CONTEXT` on every call, preferring its current run/attempt mapping over `KANNA_STAGE_RUN_ID`. Their process environments cannot change. `dispatch_prepared_post_for_api` injects semantic input into the existing daemon session, finishes the main run, inserts a bound post run, and atomically advances the inherited process's server-owned context file; it does not export a new environment into the live process. Legacy unlocked contexts cause a fresh post spawn instead. Thus the reported missing-id failure is the server's compatibility gate for adapters without run context, not a missing per-call file read in current MCP. Explicit stale environments still fail deliberately. Completion attempt mappings continue to protect retries of already-recorded main verdicts.

`request_revision` is the only other MCP binding that reads this environment/context; it now shares resolution and records against the selected running main run. `signal_merge_handoff` carries branch, target, PR and summary only, and records a task-level signal, so there is no run dependency to change. CLI and tool schemas remain unchanged.

Verification so far: server HTTP regressions passed, including post completion/transition, stale/ambiguous ids, explicit selection, and existing recovery/retry coverage. All 15 revision route tests passed after correcting their fixture to cancel its original review run before seeding a replacement. The MCP stdio lost-response/post test passed. Desktop `tsc --noEmit` passed (the root has no tsconfig; the required root invocation prints compiler help). `cargo fmt --all` and `git diff --check` passed. No dependencies or tool schemas changed.

The real post E2E was extended and run, but timed out before the agent created its first marker, so it did not reach MCP completion. See `docs/2026-09-05-mcp-post-completion-e2e-gap.md`; the harness cleaned up its instance. Standard Clippy completed for kanna-server, kanna-mcp, and kanna-cli, but strict `-D warnings` is blocked by pre-existing server warnings (dead code, argument counts, existing async test locks, and other lints outside the changed behavior). No lint suppressions or unrelated cleanup were added. A fully clean Clippy gate and live E2E success remain unclaimed.

Final canonical gate: `./kd test all` passed, including all workspace JS/TS tests, full Rust workspace tests (server, CLI, MCP and desktop), and serialized daemon tests. The two remaining verification limits are the live E2E marker timeout above and pre-existing warnings preventing a strict warning-free Clippy run. Changes remain in this manual implementation workspace for the workflow's commit/review steps; no branch was published and no stage was advanced.
