# Canonical desktop updater repository

## Goal and scope

Point the production and staging desktop updater endpoints at the canonical
`tampopogk/kanna` GitHub release repository, and pin that relationship in tests.
Keep the production `releases/latest/download/latest.json` feed and staging
`releases/download/desktop-staging/latest-staging.json` feed distinct. Do not
change signing keys, public keys, manifest shape, release/promotion state, or UI.

## End-to-end trace

- Production builds read `plugins.updater.endpoints` from
  `apps/desktop/src-tauri/tauri.conf.json`. The Bazel
  `tauri_updater_bazel_config` copies that config and only injects
  `KANNA_UPDATER_PUBKEY` when present.
- Staging Bazel builds instead use `tauri_staging_bazel_config`, which preserves
  the same updater configuration and key injection but overrides the app identity
  and endpoint to the `desktop-staging` channel. The generated configs flow
  through the matching ACL/context targets into the production and staging
  desktop binaries and bundles.
- `apps/desktop/src-tauri/src/lib.rs` registers the official updater plugin.
  `App.vue` starts `useAppUpdate`, whose scheduled and manual checks call the
  plugin's `check()`; an available update is rendered by `AppUpdatePrompt.vue`,
  and installation calls the returned handle's `downloadAndInstall()` before a
  user-triggered relaunch.
- `./kd release ship` in `tools/kd/src/runtime/release.ts` derives the repository
  with `releaseRepoSlug(origin)`, asks Bazel for both architecture-specific DMGs
  and updater bundles, signs the updater bundles, and writes the unchanged Tauri
  static manifest shape (`version`, `notes`, `pub_date`, and per-platform `url`
  and `signature`). Production uploads signed archives plus `latest.json` to the
  immutable `vX.Y.Z` release; staging uploads the signed artifacts plus
  `latest-staging.json` to an immutable prerelease, then clobbers only
  `latest-staging.json` on the `desktop-staging` pointer release. This matches
  `docs/dev/release.md` and `docs/specs/release-candidates.md`.
- Live verification on 2026-09-03: `gh release view --repo tampopogk/kanna`
  resolved the latest production release to `v0.2.0`; its `latest.json` is served
  from `tampopogk/kanna` and names only `tampopogk/kanna` artifact URLs. The
  `desktop-staging` release carries `latest-staging.json`, currently serving
  `0.3.0-staging.9`, whose artifact URLs also name only `tampopogk/kanna`.

## Compatibility

Apps built before this change keep polling the old `jemdiggity/kanna` endpoint.
GitHub currently responds to both old production and staging manifest URLs with
HTTP 301 redirects to the corresponding `tampopogk/kanna` URL. The locked
Tauri updater 2.10.1 constructs a default reqwest client for manifest checks and
artifact downloads without replacing its redirect policy ([manifest request
code](https://docs.rs/tauri-plugin-updater/2.10.1/src/tauri_plugin_updater/updater.rs.html#451-479),
[artifact request code](https://docs.rs/tauri-plugin-updater/2.10.1/src/tauri_plugin_updater/updater.rs.html#663-687));
the locked reqwest 0.13.2 default policy follows up to ten redirects
([source](https://docs.rs/reqwest/0.13.2/src/reqwest/redirect.rs.html#158-165)).
Following the old URLs live reached the release assets successfully (HTTP 200),
so existing installs remain compatible while new builds stop depending on the
repository-transfer redirect.

## Done when

No updater config or build stamp references `jemdiggity`; production and staging
endpoints name `tampopogk/kanna`; tests derive the canonical release repository
from `origin` via `releaseRepoSlug`; updater/release tests and `./kd test all`
pass; and no release or promotion is performed.
