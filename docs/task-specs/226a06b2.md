# Task 226a06b2 — bound the remote `term_snapshot`, lazy scrollback, delta resubscribe

## Goal

Stop the mobile terminal view from paying for the *whole* PTY scrollback every
time it opens or reconnects. Owner-observed on staging over one-bar 4G
(2026-08-21): opening or reconnecting a remote terminal ships the full
serialized terminal — screen **plus 10,000 rows of scrollback** — as one
`term_snapshot`, and a flaky link re-ships it on every reconnect. A ksp tunnel
moved ~4.9 MB during ~5 minutes of viewing, dominated by snapshot re-sends.

`7a38cc18`'s frame inventory measured the same class as **producer-unbounded**:
1.71 MiB base64 for a plain-ASCII 10,000-row scrollback, and 114.8 MiB
worst-case truecolor at 240×60 — above the relay's own `maxPayload`. That task
deliberately deferred the producer-side bound to this one
(`docs/task-specs/7a38cc18.md`, "The two unbounded classes").

## Scope

In:

1. A **bounded initial `term_snapshot`** for remote viewers: the visible screen
   plus a bounded window of recent scrollback, capped by both a line count and
   a byte ceiling.
2. **Lazy scrollback**: new ksp request/response frames so a viewer scrolled
   near the top of its loaded buffer pulls the next older chunk over the
   existing ksp session, chunked and bounded per request.
3. **Delta resubscribe**: on re-attach the client presents its last-seen
   `(stream_id, offset)`; the server replays only the bytes it missed, and
   falls back to a *bounded* fresh snapshot when the gap is unreplayable.
   Never the full history unconditionally.
4. The before/after measurement method, recorded below so the win is
   verifiable on staging.

Out (deliberately):

- **The agent journal** (`agent_snapshot`), the other producer-unbounded class
  in `7a38cc18`'s inventory. Same shape of problem, different subsystem, its
  own task.
- Changing the daemon's 10,000-row retention or the Ghostty serializer. The
  bound is applied where the frame is produced (`crates/kanna-server/src/ksp.rs`),
  which is what the task asks for and what keeps the daemon's own fidelity
  contract (`crates/daemon/SPEC.md`) untouched.
- Any relay change. `maxPayload` stays where `7a38cc18` set it; this task only
  makes the frames that travel under it smaller.
- Desktop UI work. The desktop is a localhost client and keeps today's
  behaviour exactly (see "LAN and desktop behaviour").

## Constraints

- **Opt-in by capability.** Everything new is gated on the client advertising
  `term_scrollback_window` in its `auth` frame. A client that does not
  advertise it gets byte-identical behaviour to today — same frames, same
  full snapshot, same per-attachment daemon connection.
- The daemon contract is unchanged: kanna-server still attaches with
  `AttachSnapshot { emulate_terminal: true }` and forwards `Output` verbatim.
- Repo conventions: no `any` in TypeScript, `pnpm exec tsc --noEmit` clean,
  `cargo clippy` clean, no `unwrap()` in production Rust.

## LAN and desktop behaviour

The cap is **not** applied by transport, it is applied by capability, and the
mobile app advertises it on *both* of its transports (LAN and relay). Reasons:

- The desktop (localhost) never advertises it, so the desktop terminal — the
  fidelity-sensitive surface with full scrollback expectations — is untouched,
  including its per-attachment daemon connection.
- A phone on LAN is still a phone: same xterm buffer, same cold-open latency,
  same battery. Bounding it there is harmless and keeps one code path for the
  mobile client instead of two.

## What was built

### 1. Bounded snapshot (`crates/kanna-server/src/terminal_window.rs`)

The daemon's serialized VT is split into lines at `\r\n` row separators (the
serializer's own row separator; wrap continuations carry none, so a "line" is a
logical line). The **window** is the last `rows + 400` lines
(`TERMINAL_WINDOW_SCROLLBACK_LINES`), further trimmed until it fits 256 KiB
(`TERMINAL_WINDOW_MAX_BYTES`) — but never below the visible screen, which is the
one thing that cannot be dropped and still be correct. Everything older is
**retained server-side** as that attachment's scrollback history, bounded by
1 MiB (`TERMINAL_HISTORY_RETENTION_BYTES`).

A window or chunk that starts mid-buffer is prefixed with an SGR reset: the
serializer emits style *diffs*, so a fragment would otherwise inherit the style
of content it no longer carries.

An alternate-screen serialization (`\x1b[?1049h`) is never cut through: the
alt-screen segment is kept whole and only the primary-screen prefix in front of
it is windowed, so a TUI session cannot be re-hydrated with its alt-screen
content painted onto the primary screen.

### 2. Lazy scrollback

`term_scrollback_request { task_id, request_id, history_id, before_line,
max_lines }` → `term_scrollback_chunk { task_id, request_id, history_id,
start_line, end_line, data_b64, remaining_lines }`. Chunks are served from the
retained history newest-first, bounded per request at 64 KiB / 500 lines
server-side (the mobile viewer asks for 200). A single line larger than the byte
budget is still delivered whole, or a client could never walk past it. The
`history_id` fences a stale request against a history that has since been
replaced by a fresh daemon snapshot: the server answers with its *current*
`history_id` and an empty chunk, and the client re-anchors instead of splicing
stale rows above its buffer.

The mobile viewer requests a chunk when the reader scrolls within 40 rows of the
top of what is loaded, debounced to one request per 250 ms in the page and
gated on "something is retained and nothing is in flight" natively. xterm has no
API to insert above its scrollback, so a chunk is applied by rewriting the
buffer with the older rows in front and putting the reader back on the same
content, which has simply moved down.

### 3. Delta resubscribe (the session tap)

Capability clients attach through a **session-scoped terminal tap**: one daemon
connection per session, shared by its subscribers, which records live output
into a 512 KiB ring (`TERMINAL_RING_MAX_BYTES`) with a monotonic byte offset and
survives the last subscriber leaving by 120 s (`TERMINAL_TAP_IDLE_GRACE`). That
grace window is what makes a flaky-link reconnect cost O(delta):

- `attach` with `term_resume { stream_id, offset }` inside the ring → the
  server sends `term_resumed` (no snapshot) followed by exactly the missed
  bytes as ordinary `term_output` frames. The client keeps its xterm buffer.
- Unknown `stream_id`, or an offset the ring can no longer replay → a bounded
  fresh snapshot: the "bounded fresh tail" of the requirement.

The client tracks its own offset by adding each `term_output` frame's decoded
byte length, so no per-frame protocol overhead was added.

## Measurement method (odometer rollups)

The relay's byte odometer (`services/relay/src/byteAccounting.ts`) already
attributes bytes per connection and per class; `tunnel` is the ksp class that
carries `term_snapshot`. To reproduce the before/after on staging:

1. `GET /stats` on the staging relay for the process aggregate, or read the
   per-connection `connection_rollup` / `connection_close` log lines, which
   carry `received`/`sent` split by class for the phone's tunnel connection.
2. Open a task's terminal on the phone against a session with a long
   scrollback, view for a fixed interval, force a few reconnects (airplane mode
   toggle), close the view.
3. Compare the tunnel-class `sent` delta for that connection before and after
   this change. The expected shape: initial attach drops from
   O(full scrollback) to ≤ `TERMINAL_WINDOW_MAX_BYTES`, and each reconnect
   inside the grace window drops from a full re-ship to the bytes the session
   actually produced while the link was down.

The same accounting is what the automated integration test asserts in-process:
a reconnect after N appended lines transfers O(delta), not O(buffer).

## Coverage

- `crates/kanna-server/src/terminal_window.rs` — 11 unit tests: windowing (line
  and byte bounds, the visible screen never trimmed away, alt-screen segment
  kept whole, window + history rebuilds the original byte for byte), history
  chunking (bounded, always makes progress, runs out), ring replay (delta only,
  eviction, re-anchoring).
- `crates/kanna-server/src/ksp.rs` — six tests through a real ksp session
  against a fake daemon socket: bounded snapshot plus a full scrollback walk
  that reconstructs the terminal; the stale-`history_id` re-anchor; the
  unchanged full snapshot without the capability; a reconnect that transfers
  O(delta) and no snapshot; an unreplayable resume falling back to a *bounded*
  snapshot; two viewers sharing one daemon stream; and a new viewer restarting a
  tap whose ring outran its snapshot.
- `packages/stream-client` — resume-position tracking across a reconnect, no
  resume position for an unwindowed snapshot, scrollback request/response
  plumbing, and never asking a peer that did not negotiate the capability.
- `apps/mobile` — store splice/stale-chunk/resume behaviour, the mutation
  planner's prepend, the WebView's scroll message and prepend injection, the
  page's near-the-top debounced request and viewport-preserving prepend, and the
  controller's one-chunk-per-scroll fetch plus the reconnect-delta path leaving
  the buffer intact.
- `tests/remote-e2e/src/lan-layer.e2e.test.ts` — the cross-boundary one, per the
  repo's E2E expectation: the **mobile LAN transport** against a real
  `kanna-server`, a real daemon and a scripted agent that prints ~10,000 history
  lines. It asserts the phone's snapshot is a small tail of an ~800 KB terminal
  (under 300 KB, holding the newest line and not one 5,000 lines back), that the
  desktop reports thousands of retained lines, and that a scrollback request
  returns the rows immediately below the window with the remainder shrinking.

Run: `cargo test --workspace`, `pnpm --filter @kanna/stream-client test`,
`pnpm --filter @kanna/mobile test`, `pnpm --filter @kanna/desktop test`, the
relay suite (`services/relay`, doc comment only), and
`tests/remote-e2e/src/lan-layer.e2e.test.ts`. All pass; the one workspace
failure seen (`kanna-daemon` `recovery::tests::failed_replay_is_single_flight…`)
reproduces on this machine without these changes and is a load-sensitive timing
test, not a regression.

## Found outside this task, left alone

The remote-e2e harness could not start its Firebase emulators here: the repo's
`firebase.json` declares a `hosting` entry with `target: "account"`, and
`.firebaserc` maps that target for `kanna-staging` and `kanna-build` but not for
`kanna-local`, the project the emulators run as. `firebase emulators:start`
therefore exits with *"Deploy target account not configured for project
kanna-local"*, taking the whole harness down — and `kd emulators up` builds its
config the same way (`tools/kd/src/runtime/firebase.ts`), so it is not specific
to remote-e2e. The LAN E2E above was executed by adding the missing
`kanna-local` hosting target to `.firebaserc` locally and reverting it; the fix
is not part of this task.
