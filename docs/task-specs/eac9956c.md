# Task eac9956c: remote terminal rendering and image-drop parity

## Goal

Make a remote-machine task's full-screen terminal render like its local terminal over both LAN and relay, and make an image dropped on the remote view either reach the owning machine as a usable file or fail with a clear message rather than typing a viewer-local dead path.

## Scope and constraints

- Reproduce and characterize the rendering failure across the real desktop/server/daemon remote path, including dimensions, redraws, attributes, cursor, scrollback, and reconnect snapshot/stream ordering.
- Trace local image drop and preserve local behavior. For remote tasks, transfer image bytes under the existing trust model and inject the owner-local path, or visibly refuse the drop; never type a viewer-local path.
- Confirm single-line, multiline, and bracketed text-paste parity with local behavior; change it only if broken.
- Fix the responsible KSP/server/desktop layer without client polling or retry loops. Cover the cross-instance LAN and relay wiring with E2E tests (or document a precise dated E2E gap).
- Run real-app visual verification for any rendered UI change and keep screenshots in the gitignored `docs/task-specs/eac9956c-screenshots/` directory.
- Do not broaden into unrelated terminal, transfer, or UI work.

## Done

The remote full-screen TUI is faithful over LAN and relay, remote image drop produces a usable owner-machine image path (or an explicit visible refusal), text paste parity is demonstrated, focused tests and `./kd test all` pass, and reproduction/visual verification results are recorded here.

## Reproduction and resolution

The scoped Kanna Staging server log on desktop `desktop-aa43ab36-e634-4ae9-b629-e8c8a91f7bff` showed that the reported Studio-to-MBP view was using a cloud/relay KSP tunnel. The same faults were reproducible with the real two-instance harness over relay and paired LAN:

- Remote clients discarded snapshot dimensions, replayed serialized VT state into unrelated viewer dimensions, and appended reconnect snapshots to stale xterm state. This displaced cursor-addressed alternate-screen content and retained stale cells.
- Output was decoded one transport frame at a time, corrupting a UTF-8 character whose bytes crossed frames.
- The remote xterm enabled `convertEol` and did not install the local terminal's WebGL/Image renderer stack. In real WKWebView this produced correct buffer cells without visible painted rows.
- The initial fit could run before xterm had measured a character cell, leaving the owner PTY at its seed dimensions instead of propagating the viewer dimensions.

Remote snapshots are now carried as bytes with their source dimensions, reset and restore the authoritative grid before live output, and defer the post-snapshot fit by one bounded layout frame before resizing the owner. Live bytes remain bytes until xterm's streaming decoder. Remote xterm options and render addons now match local behavior.

Local image drop resolves paths on the local machine and types them into the local PTY. A viewer path cannot identify the same file on the owning machine, and the existing remote protocol has no bounded file-upload surface. This task therefore takes the explicitly permitted refusal path: remote terminals register the same native/container drop bridge, show a localized error telling the user to transfer the file and paste its owner-local path, and never inject the viewer-local path.

Text input needed no product change. Real single-line and multiline paste events over paired LAN use xterm's bracketed-paste mode; multiline input arrives as one bracketed frame with LF normalized to CR, matching the local path.
