# Task 33d3d96a: deterministic cleanup of spawned processes

## Goal

Prevent long-lived processes started by `kd` and Kanna E2E harnesses from surviving their owning run, workspace teardown, task close, or a prior crash.

## Current terms

- `kd` records every long-lived process and exact tmux socket it starts in per-worktree durable inventory. `kd dev down` / `kd clean` terminate only recorded resources.
- Inventory mutation is inter-process locked. Process records include a stable spawn identity, which must still match before TERM or KILL is sent; cleanup waits for exit, escalates after a bounded grace period, and retains an entry when exit cannot be confirmed.
- Tmux session shutdown retains the exact server record for inventory cleanup, and tmux pane processes plus the server's concrete socket path are inventoried at spawn. Down/clean consume those exact records without discovery.
- E2E harnesses under `tools/kd/tests`, `tests/e2e`, `tests/remote-e2e`, and mobile E2E clean their own Tauri dev, Firebase emulator, Appium, tmux, daemon, and related children in `finally`/`afterAll`, while registering them in the same inventory for crash recovery.
- Agent/task-environment instructions add one line requiring agents to stop background processes before recording stage completion, with content tests updated.
- Detached best-effort teardown failures become visible through server logging and a task event. Teardown cleanup uses only recorded inventory.
- No process enumeration, cwd-based ownership inference, process-name matching, argv matching, periodic process sweeper, or inferred process killing may ship.

## Owner directive replacing the original design

On 2026-08-20 the owner replaced the initial cwd-reaper direction: "i don't think cwd based killing spree is a good idea. the agent, test process etc should know to clean up after themselves so I'm not buying it." The discarded design would also have killed an operator shell merely cd'd into a closing worktree. The motivating one-time manual sweep is history, not precedent.

## Done when

Inventory round-trip tests prove spawn → record → exact cleanup (and no unrelated cleanup), a crashed-run test proves the next `kd dev down` consumes surviving inventory, named harness spawn sites have deterministic in-band cleanup plus inventory registration, teardown failures are observable, docs and agent contracts are updated, and relevant Rust and `pnpm test` checks pass or unrelated failures are reported.

## Revision 1

Reviewer feedback delivered 2026-08-20 requires deterministic TERM→KILL cleanup, concurrent-safe inventory with spawn-identity validation, real tmux/dev-down lifecycle coverage, and persistent task-event-feed assertions for teardown start failure and hard timeout. These requirements refine the recorded-inventory design without restoring the rejected cwd/process discovery design.

## Revision 3

Reviewer feedback delivered 2026-08-20 requires daemon pidfile cleanup to use the inventory's spawn identity and verified TERM→KILL exit path, retaining unconfirmed records. Inventory locking must recover after a writer crashes, and cleanup may remove only the exact identity it cleaned so a concurrent same-PID replacement remains owned and unsignaled. Focused process-lifecycle tests cover these cases; no UI E2E is required.

## Revision 4

Manager-relayed reviewer feedback delivered 2026-08-20 requires the production desktop daemon spawn path to record each per-worktree daemon's pid and spawn identity in the shared inventory. The daemon pidfile is only a legacy lookup fallback and may authorize cleanup only when matched to that identity. Coverage must prove a daemon launched through the production spawn path is subsequently cleaned by `kd dev down`; no other surface changes are in scope.
