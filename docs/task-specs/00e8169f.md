## Goal

> "We probably need a way to add photos to agent input box from mobile kanna."
> — owner, 2026-08-19

Let the user attach a photo — from the photo library, and from the camera if it
falls out naturally — to the agent input composer on mobile, and have it reach
the agent as something the agent can actually see.

## Scope

In scope, as the prompt set it:

1. **Mobile UI** — an attach affordance on the task input composer: pick a
   photo, show a thumbnail with a remove control before sending, then send it
   together with the text.
2. **Transport** — the image travels over **both** mobile paths, direct LAN and
   the relay, like every other mobile capability. Encoding is the
   implementer's call, mindful of the relay's message-size characteristics, with
   a sane size cap and client-side downscaling to JPEG/PNG inside a documented
   budget before upload.
3. **Server** — receive and store the image durably for the task, somewhere it
   survives long enough for the agent to read it and is cleaned up with the
   task's lifecycle owner rather than leaking forever.
4. **Delivery to the agent** — write the image to a file the agent can access
   and compose the injected input as the user's text plus a clear reference to
   that path, delivered through the existing `POST /v1/tasks/{id}/input`
   mechanics so submission boundaries and the input-persistence record from
   PR #1123 apply.

Explicitly out of scope:

- Photos only. One attachment per message is acceptable for v1. No video, no
  arbitrary file types, no drawing or annotation.
- Same-machine delivery only — the task's own desktop. No cross-machine
  attachment routing.
- No daemon protocol change. The file-path-reference approach exists precisely
  to avoid needing PTY-level image support.
- No new input security model: an attachment arrives from the authenticated
  paired or signed-in phone like any other input.

## Constraints and decisions

**Encoding — base64 in the JSON body, on both paths.** The relay tunnels a
desktop invocation as JSON and the LAN client posts the same JSON to the same
route, so one encoding means one server handler, one durable record, and one
thing to test. Multipart would have existed on one path only.

**Budget.** The phone resizes to a 1568px longest edge and re-encodes as JPEG
before upload, and refuses anything still over 3 MiB. The server enforces the
same 3 MiB cap (`MAX_TASK_INPUT_ATTACHMENT_BYTES`) and raises the task-input
route's body limit to 8 MiB so a legitimate at-the-cap attachment is refused by
the attachment error that can explain itself rather than by the transport.
Accepted media types: `image/jpeg`, `image/png`, `image/webp`, `image/heic`.

**Storage — beside the database, not in the worktree.** Files live under
`<db-dir>/<db-stem>-task-attachments/<task_id>/`. A worktree is a git checkout
whose dirty state is snapshotted into a WIP commit at close, so a photo dropped
there would be committed onto the task's branch and appear in every diff. The
root is named after the database file so parallel instances do not share a
directory. Attachments are removed when the task closes, beside the other
per-task on-disk artifacts.

**Injected message.** `<text> [Attached image: <absolute path>]`, joined with a
space and **never a newline**: the daemon writes a logical message and then a
carriage return, so an inserted newline would split one submission in two and
put the words in front of the agent before the picture.

**Durable record.** No new column. The `task_input` row holds the exact
delivered text, which names the path; a second representation of the same fact
could only drift from it.

## Native dependency and ship path

**This is the new-native-dependency case.** The app bundled no image-picker
module at runtimeVersion 2.1.4 — `expo-camera` was present for QR pairing only,
and cannot open the photo library. The feature therefore adds
**`expo-image-picker`** (library and camera) and **`expo-image-manipulator`**
(the resize; `expo-image-picker` cannot resize at all, so the required
downscaling is not implementable without it).

Consequences, which govern how this ships:

- `runtimeVersion` moves **2.1.4 → 2.2.0 in every environment** (dev, staging,
  prod) per the repo contract.
- **It is NOT OTA-deliverable. It ships only with a new binary.** An OTA
  published against 2.1.4 would push JS calling native modules the installed
  binary does not contain.

Two plugin settings are load-bearing rather than cosmetic: `expo-image-picker`
adds `RECORD_AUDIO` and a microphone usage string unless configured with
`microphonePermission: false`, and both plugins write
`NSCameraUsageDescription`, so they are given one shared camera string.

## Review-driven corrections

Four defects were found in review and corrected on this branch. They are terms
now, not history — each is a property the feature must keep.

1. **A denied photo permission must be told to the user** (`3c4377c0f`). A
   denial was collapsed to `granted` and returned as the same `null` a
   cancellation returns, so the composer showed nothing and — because neither
   iOS nor Android re-prompts once denied — the control looked permanently
   broken. Denial now throws with a `permission-denied` reason, and the message
   splits on `canAskAgain`: still-askable says retry, permanently denied points
   at Settings.

2. **Desktop capability must be advertised and honoured** (`d493c836e`). A
   desktop built before attachments deserializes the `attachment` field,
   ignores it, delivers the text alone and answers the same `204` — so a 2.2.0
   phone paired with an un-updated Mac, the ordinary state on release day,
   would have silently lost the photo. `/v1/status` now carries
   `taskInputAttachmentVersion` (currently `1`), following the
   `kspStreamVersion` convention where **absence means an older desktop**, and
   the composer hides the attach control when it is absent.

3. **The capability must be read from the desktop that receives the input**
   (`b72dd11a1`). Reading it from the connection's status was wrong in
   principle: with cloud tasks wired, `remoteTransport.getStatus()` returns a
   synthetic "Kanna Cloud" record describing no desktop at all, and a phone can
   see tasks owned by several machines at different versions. The question is
   resolved per task, routed exactly the way the input is routed.

4. **The capability read must be answered once per task, and its claim owned by
   its issuer** (`9fb30356e`, `cb2de6afd`). `startTaskView` is a reconciler
   re-entered by every live cloud publication, so an unguarded read cleared the
   flag and re-probed on each entry — flickering the control, and starving it
   entirely when publications outpaced the round trip. The read is memoized per
   `(taskId, routeIdentity)` behind an in-flight claim, and that claim is tagged
   with the generation that installed it so only the installer may release it:
   two reads for the same task share an identity, so an identity-keyed release
   let an earlier read free a later one's claim and reopened the flicker on an
   ordinary A → B → A task switch.
