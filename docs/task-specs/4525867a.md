# Task 4525867a: concurrent Bonjour discovery and stable QR failures

## Owner report (2026-08-21)

On Gu's MacBook Pro, pairing a physical iPhone with either the Dev desktop or the installed Staging desktop fails while the pairing sheet rapidly alternates between scanning/adding and "No matching machine was found."

Observed authoritative instances:

- Dev: `desktop-4095c29f-368f-4795-9f51-876d79aca506`, environment `development`, LAN port `48154`.
- Staging: `desktop-21b320e8-a5ad-4fae-9d87-1db14090f0a9`, environment `staging`, LAN port `48121`.
- Production: `desktop-0722feec-a5a5-4729-842d-28ecd4c28508`, environment `production`, LAN port `48120`.
- Another active worktree server used port `22663`.

Dev and Staging logged successful `_kanna-mobile._tcp` configuration/refreshed publication on `172.16.0.54` (and IPv6 for Dev), but a Mac-side `dns-sd` browse/zone dump exposed only two records, both on port `48120`: current Production `desktop-0722...` and stale `desktop-4d98b183-4414-4bbe-b263-2f659b7f688b`. Dev, Staging, and the worktree were absent. Mobile discovery requires the TXT `desktopId` to match the QR payload, so those payloads failed before HTTP.

Separately, `MachinePairingSheet` locked before submitting a QR but cleared the lock immediately after every failure. A continuously visible QR was therefore resubmitted automatically, causing the visible progress/error flicker.

## Goal and scope

- Trace and correct the full `kanna-server` Bonjour lifecycle, including `mdns_sd` multi-process behavior, interface refresh/re-registration, server startup/shutdown, externally observable publication health, and stale-record cleanup/replacement.
- Make simultaneous Development-like, Staging-like, Production-like, and additional worktree servers publish distinct, correct desktop identities and ports on the same Mac.
- Make failed camera QR submissions latch/deduplicate until a deliberate retry, meaningful scan change, or explicit UX transition, without degrading manual code entry.
- Keep read-only diagnostics unambiguous about instance identity, environment, and port.
- Do not redesign environment modeling, the pairing protocol, or cloud/release flows.

## Done criteria

- Server tests and a real multi-process E2E prove at least three distinct servers are simultaneously discoverable with correct IDs/ports, and that records disappear or update after shutdown/restart.
- Mobile tests prove a continuously visible failing QR makes one claim attempt and retains a stable error; explicit recovery can retry successfully; manual code entry still works.
- Cross-boundary discovery/pairing is exercised against a real server where practical. If physical-device automation is not stable, add the required dated E2E gap note and document manual verification steps for the attached iPhone 15.
- Run `cargo test -p kanna-server`, mobile tests/typecheck, relevant pnpm/`kd` suites, `cargo fmt --all`, `cargo clippy`, and applicable repository checks.
