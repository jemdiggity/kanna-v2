# Task 51b2b041: safe process termination guidance

## Goal

Prevent agents from terminating sibling Kanna sessions when restarting tests or other commands whose text may also appear in task prompts.

## Scope

- Add concise guidance to `AGENTS.md` and every built-in agent definition (all 21 under `.kanna/agents/`, since every one of them runs `git`, `gh`, or shell commands, or inspects the repo): never use `pkill -f` or `killall` with a substring; stop only a process the agent started by recorded PID/process group, or by a unique command-line token it created. The `qa-assets` test enumerates the directory rather than a hardcoded subset, so a new built-in agent cannot omit the rule.
- Audit existing agent and developer-document examples and replace any unsafe process-matching pattern.
- Assess whether `kd test all` can gain a small, scoped way to stop only a run owned by the current workspace; implement it with `tools/kd/tests` coverage only if the design stays small and identity-safe.
- Trace PTY provider spawning and record whether Claude, Codex, Copilot, OpenCode, and Antigravity have a documented non-argv initial-prompt mechanism that preserves Kanna's interactive TUI behavior. Change spawning only when equivalence is established.

No UI changes or speculative provider-spawn changes are in scope.

## Constraints and completion

Process termination must be scoped to recorded process identity and must not depend on arbitrary command substrings. Preserve existing interactive/resume behavior. The work is done when guidance and audited examples are safe, the `kd` decision and per-provider assessment are recorded here, relevant tests pass, and `./kd test all` passes.

## Findings

### `kd test all` scoped-stop assessment

No scoped stop command was added. `tools/kd/src/runtime/test-all.ts` runs
`pnpm test` and then a nested `./kd test rust` through the shared
`CommandRunner`. That runner neither creates a dedicated process group nor
returns a durable ownership handle, and the running `kd` process does not
forward termination to its active child tree. A pidfile containing only the
parent PID would therefore make `kd test stop` look safe while leaving test
descendants running.

A correct follow-up is larger than a small command addition. It must:

1. create an isolated process group for the whole `test all` run (or for every
   lane with an owning coordinator);
2. durably record PID plus kernel start identity, handle concurrent/stale runs,
   and atomically clear only its own record;
3. forward TERM/INT, wait, revalidate identity before escalation, and signal
   the owned group rather than only its leader; and
4. cover normal completion, interruption, a TERM-resistant descendant, PID
   reuse, and nested `./kd test rust` behavior.

The resolver launcher already isolates and cleans up its short-lived resolver
process group, and the dev-process inventory has identity-safe single-process
cleanup, but neither owns the later `kd test all` tree. Reusing either
partially would not satisfy this contract. Until that follow-up lands, agents
must retain the PID/process-group handle for a background test they start and
terminate that exact handle.

### Provider argv assessment (2026-09-03)

The interactive PTY command is built in
`crates/kanna-server/src/task_creator/commands.rs`; the desktop recovery path
mirrors it in `apps/desktop/src/stores/agentCommand.ts`. The resulting shell
command goes through the daemon's ordinary PTY spawn path. Each provider's
opening task text is therefore in argv today. The daemon's separate SDK-mode
`SpawnAgent` path supports Claude, Codex, and OpenCode only; it is not the TUI
path this task is assessing.

| Provider | Documented alternatives and Kanna compatibility | Decision |
|---|---|---|
| Claude | The [Claude Code CLI reference](https://docs.anthropic.com/en/docs/claude-code/cli-usage) documents a positional prompt for an interactive REPL. Piped/stdin input and `--input-format` are print/SDK mode. Kanna's SDK adapter already sends Claude's first stream-JSON message on stdin, but that mode has no interactive TUI. | No TUI-equivalent non-argv initial-prompt path is documented; keep PTY spawning unchanged. |
| Codex | The interactive CLI accepts a positional prompt. [`codex exec` accepts stdin](https://github.com/openai/codex/blob/main/codex-rs/README.md), but it is explicitly non-interactive, while the [TUI requires terminal stdin and stdout](https://github.com/openai/codex/blob/main/codex-rs/tui/src/tui.rs). No prompt-file or stdin channel for the interactive TUI is documented. | Keep PTY spawning unchanged. SDK mode could separately move `codex exec` prompts to stdin, but that would not harden PTY sessions and is outside this incident's behavioral contract. |
| Copilot | The [Copilot CLI reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference) documents `-i/--interactive <prompt>` for an initial interactive turn. [Piped input is documented under programmatic use](https://docs.github.com/en/copilot/how-tos/copilot-cli/automate-copilot-cli/run-cli-programmatically), where non-TTY operation is distinct from the interactive interface. No prompt-file or stdin-fed interactive initial turn is documented. | Keep PTY spawning unchanged. |
| OpenCode | The [OpenCode CLI reference](https://dev.opencode.ai/docs/cli/) documents `--prompt` on the TUI and positional text on the one-shot `opencode run`. The [server API](https://dev.opencode.ai/docs/server/) can drive an already-running TUI, but adopting it would require a known endpoint, readiness/authentication lifecycle, and a second control channel; it is not an equivalent spawn flag or stdin/file input. | Keep PTY spawning unchanged; a server-control redesign is a separate feature, not an incident fix. |
| Antigravity | The interactive CLI uses `--prompt-interactive`; its documented stdin stream is [headless mode](https://www.antigravity.google/docs/cli/headless/), which explicitly has no interactive prompt UI. No prompt-file or stdin-fed interactive initial turn is documented. | Keep PTY spawning unchanged. |

Accordingly, this task changes guidance only at the provider layer. Moving any
PTY prompt out of argv would currently trade away the composer, interactive
permission UI, live steering, or established resume behavior, so no spawn
behavior changed speculatively.
