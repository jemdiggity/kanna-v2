# Task bbe96646: relay anonymous push path

## Goal

Implement phase 3 of the owner-approved anonymous push design so a LAN-paired,
signed-out phone can bind its own FCM token with a desktop-signed certificate,
and the paired signed-out desktop can publish notifications through the relay.

## Scope

- Add certificate-verified `POST`/`DELETE /push/pairings`, token rotation,
  desktop-initiated signed revocation, Firestore `anonymousPushPairings`
  storage, binding caps, stale-binding GC, and registration/publish limits.
- Add replay-safe challenge/response WebSocket authentication for an
  `anonymousDesktop` principal that may only publish mobile notifications;
  refuse invoke, tunnel, snapshot, and ordinary desktop routing.
- Wire phone-authoritative registration/refresh/revocation into the mobile
  pairing lifecycle and add the kanna-server's lazy signed-out relay session.
- Cover binding lifecycle, delivery, forbidden capabilities, unpaired
  registration, rate-limit refusal, and the signed-out server publish path.
  Record the true-device-push CI limitation in a dated coverage-gap note.
- Deploy the completed change to staging with `./kd cloud deploy`.

Phase 4 dual-identity/account-token union delivery, entitlement-policy changes,
and production deployment are deliberately out of scope. The owner-approved
push-only amendment excludes any LAN notification banner work.

## Revision 1 lifecycle requirements (review, 2026-08-25)

- Desktop trusted-device removal must durably remove local trust and enqueue a
  signed `anonymous_push_revoke`; the anonymous relay loop deletes that outbox
  entry only after the relay acknowledges it, so offline removals drain after
  reconnect.
- Mobile notification subscription/effect teardown only detaches listeners.
  Phone-authoritative revocation happens only when `removeManualMachine`
  removes that pairing, and all anonymous binding POST/DELETE work is
  serialized and reconciled so certificate refresh or effect replacement
  cannot let an obsolete DELETE remove the current binding.
- Integration coverage must exercise the server persistence/WebSocket/relay
  revocation path and deferred mobile HTTP ordering across add, removal,
  certificate refresh, and effect replacement.

## Revision 2 hardening requirements (review, 2026-08-25)

- Phone unpair always attempts certificate-only relay revocation, including
  before FCM token initialization, and retains local pairing trust until the
  relay acknowledges deletion so failures remain retriable.
- Bound both pairing POST and DELETE certificate work per IP, and consume the
  anonymous desktop publish limit before querying bindings, including
  no-binding attempts.
- Retire revocation outbox entries from obsolete anonymous identity namespaces
  locally after key rotation, while retaining current-identity entries until
  relay acknowledgement.
- Add integration coverage for those lifecycle/limit behaviors and for binding
  caps, slot-neutral refresh/rotation, and stale-binding garbage collection
  survival/removal rules.

## Constraints and completion

The phone remains authoritative for its FCM token; the relay must validate the
desktop signature, certificate expiry, and binding namespace. Anonymous access
is display-only notification publication, with bounded payloads and abuse
limits. Existing signed-in registration, authentication, and push behavior must
remain compatible. Work is done when focused TypeScript/Rust checks and the
required integration tests pass, the coverage-gap note is present, and staging
deployment succeeds without touching production.
