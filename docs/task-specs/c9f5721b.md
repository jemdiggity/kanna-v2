# LAN authorization boundary

Close security finding #1 from owner review f1c3ca89 (2026-09-05): unpaired LAN callers must not access task, repository, settings, or file HTTP data. Audit all listener routes and enforce pairing by default at the router, preserving direct loopback and authenticated relay behavior and the existing 401 text refusal. Pairing/discovery bootstrap stays available; KSP's in-band authentication must remain compatible.

Scope: kanna-server Rust, authorization tests, boundary documentation, and mobile only if pre-pairing calls require correction. No local credential/CORS redesign, unrelated review findings, protocol bump, or staging mutations. Read the owner's review worktree only.

Done: exhaustive route audit and router regression coverage, paired/unpaired route tests, mobile pairing-flow verification, real second-host LAN probes or a dated E2E gap note with route tests, cargo fmt/clippy and ./kd test all. The table below enumerates all 114 registered path patterns, including debug-only routes.

## Mobile and compatibility

Reviewed `machinePairing.ts` (claim before storing the issued secret),
`appModel.ts` (trusted endpoint resolution and credential-bound clients),
`trustedBonjour.ts` (status-only discovery), `lanTransport.ts` (device headers
on HTTP and credential in KSP Auth), and `cloudLanClient.ts` (requires running
status before repository/task reads). Account-known but unpaired endpoints
report `pairing_required` and retain cloud fallback; no mobile change is needed.
Old trust records without secrets need re-pairing to use LAN data.

The audit found legacy `/v1/stream` empty-auth reads would bypass the requested
no-data boundary. Both LAN upgrade handlers now require pairing before task data. Unverified
upgrades select existing strict in-band paired KSP authentication. Legacy v1
readers already verified via headers/cookie keep their existing read-only
empty-Auth behavior; direct loopback stays empty-auth compatible. No frame,
paired-client refusal, or version changes. The audit also found the KSP
state-change forwarder subscribed at connection startup, before Auth. It now
subscribes around the authentication handshake and starts forwarding only
after success, so an idle unauthenticated upgrade cannot receive task-state
notifications. A paused-clock regression test proves pre-auth silence and
post-auth delivery. Local browser/CORS trust redesign
from the broader review is deliberately outside this assignment.

Second-host verification gap: `docs/2026-09-05-lan-auth-e2e-gap.md`.

## Verification coverage

The route-enumeration test reads the actual router registrations, requires each
path in this audit, and sends every HTTP method with missing and invalid LAN
credentials through the production router. It includes HEAD, OPTIONS, legacy
aliases, debug routes, and methods unsupported by handlers. Adding nested or
service mounts requires extending the enumeration rather than silently skipping
them. Refusals assert the exact existing 401 body (HEAD has no body).

Two paired route matrices exercise the newly guarded settings, snapshot, backup,
workspace, event, task-read, analytics, repository, definitions, command, and
checkout surfaces with valid fixture data. The settings/data matrix also proves
direct loopback and authenticated invokes still succeed while unauthenticated
invokes fail. Repository tests use local git fixtures and wait for checkout to
finish. A real ephemeral listener verifies unpaired settings/repo refusal,
loopback-created/LAN-claimed pairing, successful paired reads, and missing,
invalid, and valid KSP credentials on both v1 and v2 upgrades, plus the
legacy paired header/cookie read-only compatibility path. Existing task,
file, pairing/bootstrap, and status tests cover the retained stricter contracts.
