# Task 231ad8fc — Rethink the in-app PR review experience

## Goal

Produce a **design assessment only**: a bounded design and implementation plan
for a Kanna review experience that lets an operator meaningfully review a PR
without opening GitHub.

## Origin

Owner directive delivered into task `f1c3ca89` on 2026-09-05 (speech-to-text,
`kanna_task_inputs` id 148), verbatim in the relevant part:

> "…the problem is our PR approval feature sucks so I would suggest that we
> remove it and launch another task to rethink it. The idea is to let the user
> actually review PRs so they don't actually have to go to GitHub to review
> them. That's the idea — to devalue GitHub."

The same directive said mobile advance-stage should behave the way desktop's
does, and confirmed that moving a PR-stage task with a post action to enqueue it
for the merge master "is OK". Removal of the current UI is being clarified in
`f1c3ca89` and is **out of scope here**.

## Redirect — owner directive, 2026-09-05 (this task's session)

After the first design was delivered, the owner redirected the approach by
dictation from the mobile app. Verbatim, in the load-bearing part:

> "…what I wanna do for a PR review is basically use the building blocks we
> already have, which is structured workflows and agent definitions. Let's
> define a PR review manager agent that helps the user determine which PR they
> want to review and which order they should be reviewed in. Then that agent
> will create a bunch of child tasks of PR review agents, each one of those
> agents reviews one single PR, and their workspace worktree is based on the
> branch of the PR. The user can use the diff tool to look at what changed. It
> would be nice if the base branch were set so that the diff tool on first open
> shows the branch diff from the base branch to the tip. The PR review agent
> should also help the user identify risky areas of code change — maybe those
> parts of their system that are more critical than others — and more or less
> make the reviewing task easier for the human."

What this changed:

- **Withdrawn**: the first design's bespoke three-pane review surface, its
  approval-attestation schema (two `pipeline_item` columns plus a
  `task.review_recorded` event), the `reviewContext` repo command and PR tab,
  and the mobile review screen. The earlier open question about accepting the
  attestation columns is moot.
- **Replaces it**: a dispatched PR review task tree composed from existing
  primitives — a `pr-review` workflow and manager agent that triages and orders
  open PRs, fanning out one child task per PR on an internal
  `pr-review-item` workflow whose worktree is forked from the PR head; the
  human reviews in the existing diff tool.
- **Kept from the first design**: the diagnosis of the diff tool's gaps, now
  carried as an explicitly deferred list rather than as work this design does.
- The design document was renamed `docs/specs/pr-review-surface.md` →
  `docs/specs/pr-review-dispatch.md` and rewritten. The old title named the
  withdrawn approach.

## Scope

In:

- Inspect the current desktop and mobile diff/PR review flows and state, in
  code, and name what actually blocks review-without-GitHub.
- Propose a concrete review experience, built from Kanna's existing
  primitives (workflows, agent definitions, child-task fan-out, the diff
  tool), covering: which PRs to review and in what order, the per-PR
  workspace and its diff, and what the agent contributes to the human's read.
- Phased implementation plan with tradeoffs, non-goals, and testable
  acceptance criteria per phase.
- Write the design to a spec document in `docs/specs/`.

Out, deliberately:

- Any implementation of the proposed design.
- Removing or altering the existing verdict bar, comment overlay, or ⌘D diff
  modal — `f1c3ca89` owns that decision.
- Changing workflow stage-advancement semantics. The `pr` stage's `approve`
  post and its merge-master handoff are untouched by the design; a PR review
  session is a separate activity that never touches a task's own workflow.
- Building shared/forge-free review state. `docs/specs/forge-independence.md`
  is parked behind a decision gate and this task does not open it.
- Mobile advance-stage parity (owned by `f1c3ca89`), and a mobile equivalent
  of this flow, which the redirected design names as deferred.

## Constraints

- Engine stays forge-neutral: no `review_thread`/`review_comment` tables, no
  forge data model in SQLite, no `/v1` review-thread endpoints. Forge behavior
  lives in user-space `.kanna/` agents and config
  (`docs/specs/native-review.md`, `docs/specs/merge-master.md`).
- Compose Kanna's existing primitives — workflows, agent definitions,
  child-task fan-out, the diff tool — rather than adding review UI or a review
  data model.
- Design must be bounded and phased so each phase is shippable and testable on
  its own.

## Decisions taken while writing the design

- The design document is a **new** spec, `docs/specs/pr-review-dispatch.md`,
  rather than a rewrite of `docs/specs/native-review.md`. Native-review's
  phase 1 is implemented and shipped, and this design does not replace it —
  the two cover different activities. A `Related:` pointer says so in
  `native-review.md`.
- The design requires exactly two engine changes and no schema change:
  exposing the already-internal fork-point/diff-base split as `diff_base_ref`
  on task creation, and defaulting the diff tool's first-open scope to
  `branch` when the worktree is clean. A third (recorded base outranking
  branch upstream) is proposed as hardening, not a prerequisite, because
  forking the child from a local ref avoids the trap.
- Both mechanics were verified empirically against real git rather than
  reasoned about: a worktree forked from `origin/<head>` inherits that
  upstream and diffs to nothing, while one forked from a local ref has no
  upstream and uses the task's recorded base.
