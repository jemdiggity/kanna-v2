# macOS release deployment target regression

## Goal

Prevent a selected Xcode/SDK update from silently raising the minimum macOS version of Kanna desktop releases. The first `0.3.0-staging.5` artifacts built on 2026-08-22 carried Mach-O `minos 26.5` and were rolled back after macOS 26.2 refused them.

## Scope and constraints

- Set macOS 15.0 as Kanna desktop's deliberate supported floor for every Bazel release binary, including host-built release tooling where relevant. Owner directive delivered 2026-08-22: 15.0 covers Apple's security-support window (current 26.x plus the previous major), fits the developer audience's update behavior, and is directly buildable/testable with the build machine's 15.4 and 26.2 SDKs; this replaces the initial 13.0 implementation choice.
- Keep the authoritative floor in the committed Bazel configuration; generate `LSMinimumSystemVersion` from it and document the policy by reference so plist metadata and linked binaries cannot drift independently.
- Gate `kd release ship` after app assembly and before artifact publication by checking every Mach-O slice with Apple tooling and requiring its `minos` to equal the floor. Cover the rejection of a higher-minos binary with a unit test.
- Bazel and release tooling only. No desktop or mobile application behavior changes, publishing, staging rollback changes, or production operations.

## Done when

Focused tests and TypeScript checks pass, the higher-minos checker test fails for the intended reason, and `./kd release ship --staging --dry-run` builds app binaries at macOS 15.0 on the selected Xcode 26.6 toolchain and passes the new gate. After merge, a Ship task must re-ship staging.5 to replace the rolled-back bad build.
