# Task 7923562e: manager-grade MCP task events

## Goal

Make the advertised Kanna MCP task/event surface sufficient for a fresh long-running task manager to discover, watch, and shepherd tasks across reachable machines without polling or private scripts.

## Scope

- Emit a first-class `task.awaiting_advance` event when a manual-stage main agent session ends without recording stage completion, and enrich task events with actionable current task/run/machine context.
- Make task lookup explain remote-machine matches; add cross-machine search/recent-list modes and `include_closed` support.
- Document `kanna_wait_events` as the lossless fan-out primitive and update the task-manager runbook to act on `task.awaiting_advance` without polling.
- Audit advance, close, revision, and input mutation responses. Fix scoped cases where an error can be returned after a durable mutation; record larger independent findings as follow-up work instead of expanding this task without bound.
- Add real daemon/server coverage for a manual-stage session ending without completion and focused API/catalog tests for the new contracts.

## Constraints and done criteria

Events must be appended at the authoritative server/DB state-change boundary and retain the cursor/no-missed-event contract, including aggregate multi-machine cursors. Cross-machine rows identify their machine. Error mutation responses must not falsely imply that no write landed; uncertain or partial outcomes must state what happened and the resulting task state. Update server boundary docs, tool descriptions, and `.kanna/agents/task-manager/AGENT.md`; run focused Rust tests, formatting, and clippy for touched crates.

## Owner directive (2026-08-23, dictated)

The owner clarified that manager coordination is based on daemon runtime activity, never the sidebar's human `read`/`unread` inbox state: `busy` means actively working, `idle` means stopped awaiting another prompt, and `waiting` remains the existing specific-input state without redesign in this task. The essential primitive is level-triggered: waiting on activity must report a task already `idle`/`waiting` immediately, as well as report the natural daemon-detected busy→idle transition without agent cooperation or stage completion. This supersedes an edge-only `task.awaiting_advance` design; that terminal event may remain useful, but cannot be the sole primitive. For remote lookup, the acceptance bar is a non-bare-404 local-then-remote explanation plus clear manager notes; mechanism is deliberately not prescribed.

Owner follow-up (2026-08-23): the new runtime signal must be a separate, unconditional server-side busy→idle signal with a fixed approximately 10-second debounce. A busy→idle→busy blip inside the window emits nothing; a task already idle long enough returns immediately in level-triggered mode. Keep existing `task.awaiting_input` and `task.activity_changed` meanings compatible. Explicitly reject adaptive thresholds, provider heuristics, and worktree-mtime checks: the intended design is the boring fixed debounce that replaces manager-side multi-minute quiet polling.

Owner composer directive (2026-08-23): agent-facing task detail and log responses must omit non-user-typed composer placeholder/suggestion text; a genuinely typed draft may remain only when clearly labeled as a draft. Preserve the human UI's ability to render provider placeholders through its ordinary API view. Trace and rely on the daemon's authoritative keystroke attestation, ensure `waitingPromptSnippet` never derives from composer suggestions, and add an idle-session regression test proving a suggestion appears nowhere in agent-facing detail or logs. Event logic remains independent of snippet presence.

Owner scope boundary (2026-08-23): do not redesign, demote, or remove `waitingPromptSnippet`; issue #1213 owns that question. This task only guarantees that event logic does not gate on it and non-user-typed composer placeholders do not leak into agent-facing surfaces. Existing snippet semantics otherwise remain unchanged.

Owner-provided sidebar audit finding (2026-08-23, from merged PR #1214 / `docs/2026-08-23-sidebar-activity-source-audit.md`): the server already owns the provider-neutral activity debounce through `update_open_pipeline_item_activity`, `activity_event_pending_at`, `activity_event_debounce_loop`, and `flush_debounced_activity_events`. Extend that authoritative loop for the fixed 10-second busy→non-busy manager signal; do not create a parallel debounce loop or snippet-dependent mechanism. The audit is source-trace context, not permission to alter the parked `waitingPromptSnippet` semantics above.
