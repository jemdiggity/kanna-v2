# Explicit kd environment profiles

Source: owner directive delivered 2026-08-21.

Revision source: reviewer feedback delivered 2026-08-21 (revision round 1).

## Goal

Model kd development launches with three explicit axes: client build identity (`dev`, `staging`, `production`), desktop owner (`worktree`, installed `staging`, installed `production`), and cloud target (`emulators`, `staging`, `production`). Resolve supported profiles centrally, report the resolved axes, and reject unsafe or incoherent combinations before starting processes or installing apps.

## Scope and constraints

- Support normal dev; dev mobile on a physical iPhone against the installed staging owner and staging cloud; dev desktop plus its worktree owner against staging cloud; full staging; and guarded production behavior.
- Add explicit kd vocabulary (`--build`, `--owner`, `--cloud`) while preserving existing default commands and compatibility aliases including `mobile run --device --staging`.
- Cover parsing, resolution, process/environment plans, physical-device identity/install/launch selection, help, diagnostics, and operator documentation.
- Do not deploy cloud services, launch production, split server from daemon ownership, redesign their lifecycle, or depend on task `a92d87ab`.
- Avoid native/config changes and a mobile `runtimeVersion` bump unless genuinely required and explained.
- Reconcile profile-managed tmux launches: changing the resolved profile must replace the old process plan before reporting success, while repeating an unchanged profile remains idempotent. In particular, switching worktree desktop cloud targets must restart its coupled desktop/server/daemon environment, and an installed-owner mobile launch must replace an old worktree/emulator Metro plan.

## Done

Supported profiles resolve deterministically; invalid profiles fail before mutation; mobile `--build dev --owner staging` launches the dev bundle through Metro without starting the worktree desktop/server and targets the authoritative installed staging owner/cloud; `dev up --cloud staging` retains the worktree server/daemon; aliases and production safeguards remain intact; diagnostics/help show axes and endpoints; focused tests and relevant checks pass. Because attached-iPhone automation is hardware-dependent, add the required dated E2E gap note if stable E2E coverage is impractical and document narrower coverage.

Profile changes are also complete only when an existing same-named tmux session has been reconciled to the new plan and environment; unchanged-profile repeats must leave the live windows/processes intact. Integration coverage must exercise both transitions against the task/runtime boundary and real tmux.
