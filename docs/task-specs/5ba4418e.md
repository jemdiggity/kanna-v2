# Task 5ba4418e: bound mobile terminal attach scrollback

## Terms

- Owner bug report (2026-08-28, verbatim): "When the agent terminal connects on mobile, we still get a bunch of scrollback sent rapidly, instead of just a couple pagefuls."
- Goal: make mobile terminal attachment deliver the rendered screen plus only a bounded recent tail, while subsequent live output continues normally and older retained history remains available on demand.
- Scope: trace and fix the mobile LAN and relay attach surfaces, the server/daemon snapshot boundary they use, and mobile handling/tests needed to prove the bounded and paged behavior. Preserve desktop attach behavior, raw PTY transcripts, composer/content derivation, and attestation semantics.
- Constraints: do not truncate raw VT bytes at an unsafe offset; use the daemon's rendered snapshot and a VT-safe server-side window. Keep the initial payload to approximately a couple of pagefuls. Add boundary tests, mobile tests, measurement evidence, visual verification, and E2E coverage (or a dated gap note where real wiring cannot yet be exercised).

## Done when

Both mobile transport routes negotiate and receive a bounded ANSI-correct initial terminal view, older scrollback can be fetched in bounded pages, live output after attach is unaffected, and tests plus before/after payload measurements demonstrate the behavior on a long session.

### Trace and diagnosis

- Both mobile routes already opt into `term_scrollback_window`: LAN creates a capability-enabled `StreamClient` in `apps/mobile/src/lib/transports/lanTransport.ts`; relay does the same in `relayClient.ts`. KSP routes those attaches through the session-scoped `TerminalTap` in `crates/kanna-server/src/ksp.rs`.
- The daemon does not retain/replay raw PTY history. `AttachSnapshot` atomically supplies the Ghostty headless terminal's ANSI-safe serialized rendered state, followed by live `Output`; raw transcripts are separate and unchanged.
- Prior task `226a06b2` (commit `1bd450811`) added the capability, server-side windowing, paged `term_scrollback_request`, and delta resume. It did not fully cover this report for two reasons: its fixed 400-row initial tail is about 16.7 pages at the common 24-row attach geometry, and a fresh consumer of an existing tap receives up to the tap's 512 KiB raw replay ring immediately behind that snapshot. The latter presents exactly as scrollback streamed rapidly.

### Implemented outcome

- A fresh window now contains the rendered screen plus two screen-heights of recent scrollback (72 total rows at 24-row attach geometry), still subject to the existing 256 KiB ceiling and alternate-screen/SGR-safe splitting.
- A consumer with no valid resume cursor receives the complete post-snapshot delta only when it is at most 16 KiB. A larger accumulated delta forces a current daemon headless-terminal snapshot instead of replaying stale raw output. The server never slices a suffix at an arbitrary ANSI or UTF-8 boundary: it sends the exact delta from its snapshot base or replaces that base with a new rendered snapshot.
- A reconnect carrying a valid `(stream_id, offset)` still receives its exact missed delta from the 512 KiB ring; live output after attach is unchanged. Older snapshot history remains available in 200-row mobile requests (64 KiB/500-row server ceilings) when the reader nears the top.
- Desktop clients do not negotiate this capability and retain their prior full-snapshot behavior. PTY transcripts and composer/content/attestation derivation are untouched.

### Measurement

Using the real LAN E2E long-session corpus shape (10,050 `MOBILE_PTY_HISTORY_%05d_` rows with its 54-character body), excluding the small serializer mode suffix and sentinel:

| Payload | Raw bytes | Base64 characters |
|---|---:|---:|
| Full retained history (legacy reference) | 814,129 | 1,085,508 |

The previous fresh-attach path could additionally stream up to 512 KiB from the tap ring. The new fresh replay ceiling is 16 KiB; larger gaps re-anchor from a bounded rendered snapshot.
