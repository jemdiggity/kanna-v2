# Slice 1 web account portal

## Goal

Build `apps/web-portal/` as the Slice-1 Firebase account and billing funnel described by `docs/specs/accounts-and-billing.md`: registration, email verification, sign-in, Stripe Checkout handoff, return pages, and a basic entitlement account view.

## Scope

- Add clean, minimal Vue pages and guarded routing for signed-out, unverified, verified-unsubscribed, subscribed, and checkout-cancelled states.
- Use Firebase email/password Auth, callable `createCheckoutSession`, and the owner-readable `users/{uid}/entitlements/cloud_access` document.
- Supply Firebase/browser billing configuration through typed environment plumbing with no secrets committed.
- Add Firebase Hosting configuration and `kd cloud deploy` build/deploy wiring for staging and production projects.
- Cover routing/components, the auth-to-callable flow against Firebase emulators with the redirect boundary mocked, and the `kd` deploy plan.

## Deliberately out of scope

Slice-2 lifecycle work (Customer Portal, deletion, password reset, App Store-specific and duplicate-source UX), marketing/legal pages, Stripe backend implementation, relay enforcement, and any production deployment.

## Constraints and assumptions

- `createCheckoutSession` is being implemented concurrently by task `344057c3`; this portal follows the architecture spec and assumes the callable accepts `{ successUrl, cancelUrl }` and returns `{ url }`. Checkout pricing display is public environment configuration because the spec does not define a price-catalogue function in Slice 1.
- Firebase web config and the Stripe publishable key are public client identifiers, but are still injected per environment and are never treated as server secrets. The Stripe key is configuration-only in this slice because hosted Checkout redirects by URL.
- The existing mobile Firebase project identities are reused; browser-specific app IDs/API keys are supplied by deployment environment rather than borrowing iOS app IDs.
- Revision round 1 is limited to the manager-relayed reviewer finding delivered on 2026-08-20: make the emulator integration harness use Kanna's reserved per-worktree Firebase ports, with sensible defaults when those variables are unset.
- Revision round 2 is limited to the manager-relayed reviewer finding delivered on 2026-08-20: keep the emulator integration self-contained while backend task `344057c3` is still parallel by serving a clearly test-only callable stub on the emulator Functions port. The stub pins the portal's Slice-1 contract (authentication and verified email required; `{ url }` returned) and must be replaced by the real emulated function once that backend lands.

## Done when

The portal builds and typechecks strictly, its requested state and emulator integration tests pass, and `kd cloud deploy` is tested to build and include Firebase Hosting alongside the existing cloud services.
