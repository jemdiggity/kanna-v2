# Task 0528d738: scoped desktop KSP state updates

## Goal

Make the desktop resilient to bursts of per-task KSP `StateChanged` events by carrying the changed task state in the frame and applying it in place instead of fetching and replacing the full snapshot.

## Scope and constraints

- Trace and change only the KSP `StateChanged` payload/server emitters and the desktop store path. Do not change the daemon classifier, terminal renderer, mobile app, or investigate the separate daemon `attached_writer` stalls.
- Preserve old/new peer compatibility: current scope-only frames still trigger the desktop's full-reload fallback, and unknown optional fields remain safe for older clients.
- Use full snapshot reloads for scope-wide or structurally significant changes and whenever a scoped task update cannot be applied consistently; no polling or debounce workaround.
- Prove activity/runtime/read-state scoped emission and desktop in-place behavior with tests, add real desktop E2E coverage if the harness can drive the burst (otherwise document the gap), verify unchanged live sidebar badges/order in `./kd dev up`, and pass `./kd test all`.

## Baseline and done criteria

The 2026-09-03 Studio incident measured 25 full snapshot replacements in 8.49 seconds (about 2.9/s) while the owner typed. Each `/v1/snapshot` response was 132,297 bytes for roughly 500 tasks, direct server fetches took 9.65–11.05 ms, and WebContent showed roughly 750 ms event-loop stalls dominated by proxy enumeration and JSON parsing. This task will add its own busy-instance `[perf:items]` capture and a before/after burst measurement.

Done means a burst of about 20 scoped per-task status changes performs zero snapshot fetches, updates the live item consistently in place, retains full-reload correctness fallback and peer compatibility, documents the protocol, records E2E/live verification, and passes the full test gate.

## Trace and design

- Activity/runtime writes originate in the desktop runtime-status routes and
  the server's detached terminal watcher. `AppState` broadcasts a
  `ServerFrame::StateChanged`; `ksp.rs` forwards that frame on each KSP
  connection and the shared TypeScript stream client dispatches it to the
  desktop store.
- Previously `init.ts` sent every frame through its trailing async coordinator
  to `queries.reloadSnapshot()`. That fetched `/v1/snapshot`, replaced the base
  snapshot and flattened item array, reconciled task UI slots, and re-ran the
  sidebar's ordering/selection projections. Task detail reads the selected
  item and terminal tabs retain terminal components by task slot/id with
  `KeepAlive`, so collection replacement did substantially more work than the
  changed fields required.
- A tasks frame can now carry a version-1 complete summary of one existing
  task's non-structural state: activity and revision/timestamps, runtime state,
  derived read state, and output preview. The store coalesces a synchronous
  same-task burst by revision and mutates the existing base/visible task
  object. It preserves item arrays, slot arrays, object identities, sidebar
  order, selected detail, and mounted terminal tabs. A scoped update that
  arrives during a snapshot request is overlaid on that response before it can
  replace newer state.
- Scope-only frames from older servers, unknown payload versions, malformed or
  unknown tasks, closed/created/reordered tasks, repo/blocker/settings changes,
  reconnect gaps, and a lagged per-connection broadcast subscriber retain the
  authoritative snapshot path. On lag the server forwards a coarse `tasks`
  frame so dropped scoped updates cannot leave a client stale. The optional
  JSON field is ignored by older TypeScript clients; mobile registers no
  `StateChanged` listener.

## Measurements and verification

The real WKWebView E2E seeded 500 load tasks (505 visible tasks including the
suite fixtures) on a busy development instance. Its `[perf:items]` baseline
logged full-refresh totals from 249 ms to 611 ms. In the final same-window
comparison, 20 explicit old-handler reloads caused 26 snapshot fetches and 26
heartbeat-observed gaps over 50 ms (maximum 380 ms). After resetting the
counters, 20 server runtime-status flips for one task caused **0 snapshot
fetches**, preserved the exact sidebar row order and badge transition, and
recorded 4 heartbeat gaps (maximum 495 ms). WKWebView did not expose the Long
Task PerformanceObserver, so those gap counts are the harness's 10 ms
event-loop proxy and include host scheduling contention; the measured scoped
window contained no `[perf:items]` snapshot refresh.

The worktree app was also started through `./kd dev up`; `kanna-cli info`
confirmed the assigned `127.0.0.1:48123` development server, desktop
`desktop-597bea41-61f5-4af2-bdb6-9d85b3a29379`, and healthy write path. The
real E2E exercised the rendered unselected sidebar's working/unread styles and
ordering in the Tauri WKWebView. The dev process and daemon were stopped with
`./kd dev down --kill-daemon` afterward.

No additional E2E covers lag recovery because the condition is a
server-internal broadcast overflow that the real desktop harness cannot
provoke deterministically. A server unit test uses a small-capacity broadcast
channel to prove the coarse fallback, while the desktop reaction from a
scope-only frame to a full reload is already covered by `init.test.ts`'s
“coalesces KSP state change bursts into one active and one trailing refresh”
test.

Targeted protocol, server, watcher, desktop-store, stream-client, typecheck,
format, and clippy checks passed. The real Tauri E2E passed 4/4. Revision round
1 added deterministic lag-overflow coverage: the focused test and all 109
`ksp::` tests passed, as did `cargo fmt --all`, workspace-wide `cargo clippy`,
and a clean `./kd test all` run. The reviewer-noted
`worker_exits_promptly_when_daemon_control_channel_reaches_eof` timing test
passed in the workspace lane; no unrelated flake recurred.
