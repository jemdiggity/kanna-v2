# Desktop feedback for draft-held stage posts

## Goal

When a desktop stage advance queues its post behind a typed terminal draft, immediately tell the operator that the advance is waiting on that task's terminal and keep that queued state visible until the draft is submitted and the post is released.

## Scope and constraints

- Preserve the daemon's composer-attestation, draft hold, and automatic queued-delivery semantics; do not change the input queue or weaken draft protection.
- Use the existing held-delivery result and task composer/queue information rather than creating a second source of truth.
- Audit desktop actions that inject logical input. In scope: stage advance, whose configured post is injected into the live session. Ordinary terminal input is the human draft itself, not an injected logical action. Revision requests resume or spawn a revision session with its prompt rather than injecting through the logical-input helper, so they cannot hit this hold. Rerun, merge-agent start, close, and task metadata actions likewise do not use the held logical-input path. The server's `signal-agent` and `/input` routes can be held, but they are not separate desktop task actions; `/input` already returns and persists `input_held_by_draft` queue state (the mobile visibility counterpart shipped separately).
- Add focused desktop tests and client/server boundary coverage, or a dated E2E gap note if the real held transition cannot be automated yet.
- Visually verify the rendered desktop state through `./kd dev up`, including a real typed draft, and save an inspected screenshot under the task's gitignored screenshot directory.

## Done

The advance action surfaces specific queued-draft guidance immediately, the selected task visibly retains that pending state while its typed composer blocks delivery, the state clears truthfully after release, tests/checks pass, and desktop visual verification is recorded.

## Verification record
