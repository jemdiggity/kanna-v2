# Task 38814a09 — reject untrusted browser callers on the local HTTP/WS boundary

## Goal

Close the browser/loopback exposure found in product review f1c3ca89 and
requested by the owner on 2026-09-05 as its own task: `kanna-server`'s HTTP
router applies `CorsLayer::permissive()` and grants privileged authority from
the *peer address alone* (`ip().is_loopback()`), so any web page a user opens
can reach `http://127.0.0.1:<lan_port>` and drive task, file, and control
routes with the desktop's own authority. The same address-only rule promotes a
browser WebSocket upgrade of `/v1/stream` / `/v2/stream` to
`AuthMode::AllowEmpty`, which CORS never constrains at all, and a DNS-rebinding
page reaches loopback as *same-origin*, so it carries no `Origin` header to
inspect.

The LAN pairing fix already on `main` in d32dc0d8 (task c9f5721b) is preserved,
not re-litigated.

## Scope

In:

- A local-client authority policy on the real LAN listener that distinguishes
  browser-originated requests from local process clients, and requires a
  source-appropriate credential from the former.
- `Host`/`:authority` validation for loopback peers, so a DNS-rebound page
  cannot launder itself into the "local process" class.
- The same policy on the KSP WebSocket upgrades, authenticated in-band because
  a browser cannot attach headers to a handshake.
- Replacing permissive CORS with an explicit layer, documented as *not* an
  authorization mechanism.
- Teaching the one legitimate browser client — the Tauri desktop webview — to
  present the local control credential on its `fetch` calls and its KSP
  stream.
- Real HTTP and WebSocket boundary tests against a launched `kanna-server`
  process in an isolated temp fixture: hostile `Origin`, rebinding `Host`,
  missing/invalid credential, allowed callers, and preflight.
- Documenting the policy and its residual limitations in
  `docs/kanna-server-boundary.md`.

Out (real, deliberately not widened into this task):

- Any other finding from product review f1c3ca89.
- The task preview proxy (`http_api/preview.rs`), which is a separate listener
  with its own enter-secret/cookie boundary.
- Requiring a credential from non-browser local processes (CLI, MCP, sidecars,
  agents). See Constraints — that would be a migration, not a fix, and a local
  process already holds the user's authority.
- Renaming the existing `task-events.token` credential file or its
  `KANNA_TASK_EVENTS_TOKEN_PATH` environment variable; running agents hold
  those paths.

## Constraints

- Must not break: packaged and dev desktop, `kanna-cli` / `kanna-mcp`, the
  `task-transfer` sidecar, paired mobile over LAN or relay, authenticated
  relay dispatch, or the debug-only E2E routes.
- CORS response headers may not carry authorization weight, and arbitrary
  localhost origins may not be trusted — a task's own preview/dev server runs
  on loopback and is exactly the untrusted browser this fixes.
- No probing or mutating other running Kanna instances; tests launch their own
  server process in a temp root on an ephemeral port.

## Done when

- A browser-shaped request (an `Origin` or any `Sec-Fetch-*` header) without
  the local control credential is refused on every route, including the
  WebSocket upgrades.
- A loopback request whose `Host` is a DNS name is refused.
- The desktop webview, CLI/MCP, sidecars, paired mobile, and relay dispatch
  all still work.
- Boundary tests cover hostile `Origin`, rebinding `Host`, missing and invalid
  credentials, allowed callers, and preflight.
- `cargo clippy`, `cargo fmt --all`, `pnpm exec tsc --noEmit`, and the touched
  test suites pass.

## Decisions taken while implementing

These changed or sharpened the terms above; they are recorded here because a
later reviewer reads this file, not this session.

- **A paired device secret satisfies the browser requirement too.** Pairing —
  not an address, and not the absence of an `Origin` — is what a hostile page
  cannot obtain, so a request that verified a device secret keeps that device's
  authority whatever client shape it arrives in. Without this, an existing test
  (`task_diff_route_allows_paired_lan_device_with_valid_secret`) that pairs a
  device and sends an `Origin` would have been refused for no security gain.
- **A browser now gets *no* task-event feed, where it previously got the
  local-only one.** `AccountWideTaskEventAccess` used to downgrade a
  browser-metadata loopback caller to this desktop's own feed rather than the
  account-wide one. That local feed is still this desktop's task activity, and
  a page the user opened has no business reading it, so the boundary refuses
  the request outright.
  `unauthenticated_loopback_waits_get_the_local_feed_and_browsers_get_nothing`
  now pins both halves: a local process client keeps the local feed, a browser
  gets 403.
- **A request that omits `Host` entirely is not refused.** Hyper serves such an
  HTTP/1.1 request rather than rejecting it, so the `Host` check could in
  principle be skipped — but no browser can omit `Host`, so skipping it leaves
  only a local process in the class it was already in. Pinned by
  `omitting_the_host_header_does_not_launder_a_browser_past_the_boundary`.
- **CORS mirrors the request origin rather than allowlisting one.** The
  webview's origin is a moving target (`tauri://localhost` packaged, the Vite
  origin under `kd dev up`, whatever a future WebKit serializes it to), and an
  allowlist there could only ever break the app. Authority comes from the
  credential; a mirrored origin grants nothing a rejected request could use.
  The layer stays *inside* the authorization middlewares, where it already was.
  Moving it outside would have made refusals readable by the webview, which is
  better for diagnosing the app's own misconfiguration — but `tower_http`
  short-circuits every `OPTIONS` request as a preflight, so an outer CORS layer
  answers `OPTIONS` on every route with no authorization, breaking the
  deny-by-default-for-every-method contract that
  `every_registered_http_route_denies_unpaired_lan_by_default` pins from task
  c9f5721b. That contract wins; the server logs each refusal at `warn` and the
  client logs a credential it could not read.
- **Non-browser local processes were not asked for a credential.** The CLI, the
  MCP server, the sidecars and every running agent keep their loopback
  authority. A process running as the user already holds it — it can read the
  credential file, the database and every worktree — so requiring a token there
  is a migration, not a boundary. This is the compatibility reasoning the task
  asked for, and it is what keeps the change free of client migration.

## Verification

- `crates/kanna-server/tests/local_client_boundary_http.rs` — nine cases
  against a launched `kanna-server` process on an ephemeral loopback port in a
  temp root: local process callers, hostile `Origin`, `Sec-Fetch-*`-only,
  loopback-origin pages, invalid/empty/guessed credentials, the webview's real
  shape, rebinding `Host`, addressable hosts, hostless requests, preflight, and
  real WebSocket handshakes on both `/v1/stream` and `/v2/stream`.
- `http_api::lan_trust::tests` — host parsing (ports, case, trailing dot, IPv6
  brackets), the addressable-host rule, and browser detection.
- The full `kanna-server` suite (1251 unit + integration), `kanna-cli`,
  `kanna-mcp`, `cargo clippy --workspace --all-targets`, `cargo fmt --all`.
- Desktop: `pnpm exec tsc --noEmit` and the full `vitest` suite (1780 tests).
  The client tests now assert the credential header on every `kanna-server`
  request, so a regression that stops sending it fails there.
- **Real app.** `./kd dev up` in this worktree, desktop app running against the
  changed server on its assigned port 48123: the snapshot fetch, the backup
  POST and the KSP stream all succeed, and
  `/tmp/kanna-webview-task-38814a09.log` shows "refreshed snapshot after KSP
  state change" — the browser stream authenticated in band. Probing that same
  instance (this worktree's own, never another): a local-process
  `GET /v1/repos` is 200, the same request with
  `Origin: http://attacker.example` is 403, with `Sec-Fetch-Site` alone is 403,
  with `Host: attacker.example` is 403, and the webview's shape with the
  credential is 200 with `access-control-allow-origin: tauri://localhost` and a
  preflight answered 200 with `access-control-allow-headers: authorization`.
  The app was run twice, once under each candidate CORS ordering, and worked
  under both; the shipped ordering is the one the first run exercised. The dev
  session was torn down with `./kd dev down`.

## E2E coverage

The boundary tests above drive a real socket and a real WebSocket handshake
against a launched server process, which is where this behaviour lives. The
webview half is covered transitively rather than by a new webdriver test: every
desktop E2E test drives the app against a real `kanna-server`, so a webview
that stopped presenting the credential would fail all of them rather than none.
No new E2E gap note is warranted.
