## Future push watcher decision (design only)

Reject generalizing `TASK <id> DONE ...` into an event stream written to the manager PTY. PTY delivery conflates the control plane with a human terminal and agent context, repeats the composer-suggestion and palette-chrome class of failure, inherits draft holds, consumes context on every fire, interleaves with output, and cannot cross a stage fork. Completion notification works because it is rare and terminal; a wake stream is neither.

Prefer the MCP control plane. MCP already permits server-initiated traffic and `kanna-mcp` emits `notifications/tools/list_changed`; the missing piece is a portable client signal that starts a user-facing agent turn. Arbitrary MCP notifications may not wake every client, while `sampling/createMessage` returns generated content to the server rather than injecting a turn. The future design is therefore two-layered: a server-initiated wake where the client supports it, with the long-poll as the portable fallback. The prompt's last-call invariant remains load-bearing across providers.

The notification must wake the manager to drain the durable feed rather than carry event payloads. A lost wake then costs latency instead of data, and context stays bounded. Wake only for actionable events: `task.awaiting_input`, `task.awaiting_advance`, failed `run.finished`, `task.revision_requested`, `task.merge_handoff_missing`, and debounced `task.runtime_settled`. Suppress wakes caused by the manager's own actions.

Before committing to the client layer, cheaply test whether Claude Code surfaces an arbitrary server-initiated MCP notification to the model and whether notifications/progress emitted during a backgrounded call do anything beyond update UI.
